# フットプリント

内部の記録。日本語のみ。**予算・測り方・実測値の台帳。**

TinyGFX の存在理由はここ。**数字が入っていない主張は書かない。**

## 1. 何のための文書か

1. 「この機能を足すと CH32V003 でフラッシュが何バイト増えるか」を**実測して残す**
2. 増分が予算を超えたときに気づく
3. 利用者向け GUIDE に載せる**値札の元データ**にする

**測っていない機能は追加しない**（[DECISIONS.ja.md](DECISIONS.ja.md) D6）。

## 2. 基準

| 項目 | 値 |
| --- | --- |
| 基準機 | **CH32V003**（Flash 16KB / SRAM 2KB） |
| FQBN | `ch32-riscv-arduino:ch32riscv:CH32V003_EVT`（最適化は既定の `-Os`） |
| アーキ | **rv32ec / ilp32e — 乗除算命令を持たない。** 除算はソフトウェアルーチン呼び出しになる |
| ビルドオプション | `-ffunction-sections -fdata-sections -Wl,--gc-sections` はコア既定で有効（確認済み）。`-fno-rtti -fno-exceptions -fno-threadsafe-statics` も既定 |
| Bus | `TinyGFXBusSoftSPI`（このコアに SPI ライブラリが無い。[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E2） |
| 参考機 | ESP32（`esp32:esp32`）、AVR UNO（`arduino:avr:uno`） |
| パネル | ST7789 240x240 |
| 測る対象 | **スケッチ全体のビルドサイズ**（Arduino Core 込み）。ライブラリ単体ではない |

**ライブラリ単体のサイズは測らない。** 実際に効くのは「そのスケッチが載るか」だけなので、常に完成品の数字で判断する。

## 3. 測り方

```sh
arduino-cli compile --fqbn <FQBN> --output-dir build --warnings none <sketch>
```

- `arduino-cli compile` の出力する Flash / RAM の数値を記録する
- 差分を見るときは**必ず同じコア・同じバージョン・同じ最適化オプション**で測る。コアを上げたら基準行を測り直す
- シンボル単位で追うときはマップまたは `nm --size-sort` を使う

**自動化**: `tests/footprint/` がこの手順を回して、予算超過で fail する（[TEST_PLAN.ja.md](TEST_PLAN.ja.md) Tier 0）。

## 4. 構成の定義

積み上げで測る。**各行は「前の行 + その機能」**で、増分が読めるようにする。
実体は `tests/constructs/<name>/<name>.ino`。

| 構成 | 内容 |
| --- | --- |
| **base** | 空の `setup`/`loop` のみ（コアだけの下駄） |
| **A** | base + BusSoftSPI + DriverST7789 + `begin` + `fillScreen` |
| **B** | A + `fillRect` / `drawPixel` / `drawFastHLine` / `drawFastVLine` |
| **C** | B + `drawLine` / `drawRect` / 円 / 角丸 / 三角 |
| **D** | C + `setFont` / `drawString`（TinyFont 固定ピッチ・連続、データ 208 B を含む） |
| **E** | D + `pushImage`（不透明版と transparent 版） |
| **T** | E + `TinyGFXTileCanvas`（240px × 1 行の帯バッファ 480 B を含む） |
| **P1** | D + `TinyGFX/Print.h` の `println(const char*)` / `println(int)` |
| **P2** | P1 + `println(float)` |

**A〜T がコア。P1 / P2 は「値札」を出すための構成**で、予算の対象外（超えて当然）。
ただし**数字は必ず載せる。**

## 5. 予算と実測（CH32V003）

**2026-08-30 再測定。** `tests/footprint/` が毎回この表と同じ数字を出す。
**予算はどのコアでも満たすこと**（§6.1 の新コアでも同じ予算で通る）。

| 構成 | Flash | Δ Flash | Δ 予算 | RAM | Δ RAM | Δ 予算 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| base | 5,892 | — | — | 504 | — | — | — |
| A | 7,684 | **+1,792** | 1,900 | 576 | +72 | 96 | OK |
| B | 7,844 | +1,952 | 2,200 | 576 | +72 | 96 | OK |
| C | 10,732 | +4,840 | 5,200 | 576 | +72 | 96 | OK |
| D | 11,992 | +6,100 | 6,400 | 576 | +72 | 96 | OK |
| E | 12,580 | **+6,688** | 7,200 | 576 | +72 | 96 | OK |
| T | 13,524 | +7,632 | 8,400 | 1,132 | +628 | 700 | OK |
| P1 | 12,396 | +6,504 | 参考 | 592 | +88 | 参考 | 参考値 |
| P2 | **リンク失敗** | 約 +8,650 | 参考 | — | — | 参考 | FLASH 超過 |

**この表は UTF-8 込み**（既定。D26）。`-DTINYGFX_FONT_UTF8=0` で D 以降が
148〜164 B、P1 が 292 B 戻る。

### 読み取れること

- **フル機能（構成 E）で +6,784 B。** 16KB のうち base が 5,892 B を食っているので、
  残り 10,492 B に対して 63%。**載る。**
- **いちばん高いのは構成 C（全プリミティブ）で +2,892 B。** 使わない人はここを払わない。
- **文字は +1,260 B**（数字 10 字のフォントで。うち UTF-8 の復号が 164 B）。
  `-DTINYGFX_FONT_SPARSE=0 -DTINYGFX_FONT_RECORDS=0` で 164 B 取り戻せるが、
  **落とすと疎索引が使えず CJK が入らない**（[FONT_FORMAT.ja.md](FONT_FORMAT.ja.md) §2）。
- **使っていないフォント形式は 0 バイト。** u8g2 のデコーダを持つ TinyGFX でも、
  CellFont しか使わないスケッチには 1 バイトも載らない（`tests/linkprune/` が検査）。
- **`pushImage` は +588 B。**
- **TileCanvas は +944 B / RAM +556 B。**
- **`Print`（float なし）は +404 B**（P1 − D）。うち 128 B は UTF-8 の状態機械で、
  `Print::write(uint8_t)` が 1 バイトずつ渡してくる以上避けられない（D26）。
- **`println(float)` は約 8,650 B。** CH32V003 のフラッシュの半分以上。

### 予算改定の記録

- 2026-08-27 初版。当初の予算（総量ベースで A=4KB など）は**間違い**だった。
  base だけで 5,892 B あるので、総量では意味がある数字にならない。
  **base からの増分**に置き換えた。
- 2026-08-27 フォントを TinyFont に変えて D 以降が 236 B 減った。**予算は据え置き**
  （余裕ができただけ）。
- 2026-08-28 フォントを **CellFont**（外部仕様 v1）に移して D 以降が **248 B 増えた**。
  **予算は据え置き**（E で 6,784 / 7,200、まだ 416 B 余っている）。
  増分の中身は頭ブロック・形式内連鎖・U+FFFD 退避（64 B）・ベースライン基準で、
  **データ側で 690 B 以上返ってくる**。内訳は [FONT_FORMAT.ja.md](FONT_FORMAT.ja.md) §2。
- 2026-08-28 D 以降が **172 B 減った。** 内訳は 2 つ:
  **形式をまたぐ連鎖（`TinyGFXFontRef::next`）を外して −40 B**（同じフォントでの A/B 実測）と、
  **フォントを CLI の出力に替えて −126 B**（つなぎの 5x7 32 字 → 数字 10 字）。**予算は据え置き。**
- 2026-08-30 全体を再測定した。**構成 A〜T は 1 バイトも動いていない** ——
  改名（`Panel*` → `Driver*` / `Target`）は名前だけで、構成はドライバを直接
  使うため。動いたのは **examples**（パネルヘッダに移してオフセットが入った）と、
  **モノクロ側**（§6.4）。**新コアと AVR の表（§6.1 / §6.2）は古かったので直した。**
- 2026-08-29 文字列を UTF-8 として読むようにして D 以降が **+164 B**、P1 が **+292 B**
  増えた（D26）。**予算は据え置き**（E で 6,688 / 7,200、まだ 512 B 余っている）。
  `-DTINYGFX_FONT_UTF8=0` で 1 バイトも違わない元の値に戻る。
- 2026-08-29 `drawRaw565` を窓経路にして **−32 B**（ESP32 は −108、AVR だけ +118）。
  写真 1 枚あたりのバス転送が **13 B/画素 → 2.3 B/画素**（D27）。
  AVR で増えるのはクリップ計算が 32bit だから。16bit 版は基準機で +116 になったので
  採らなかった —— **また逆転した**（[OPTIMIZE.ja.md](OPTIMIZE.ja.md) §J の「注意」）。
- 2026-08-29 `rlepal4` のパレット索引に範囲検査を入れて **+16 B**。壊れたヘッダが
  配列の外を読んでいた（[TEST_PLAN.ja.md](TEST_PLAN.ja.md) の `tests/image_oracle/`）。
- 2026-08-28 `TinyGFXBus::readData()`（パネルからの読み戻し）を足して **+8 B**
  （構成 A。D 以降は +4 B）。vtable の枠ぶんだけで、**ソフト SPI の実体は空**。
  読み戻しを使わないスケッチはこれ以上払わない。用途は §7 の下。
- 2026-08-27 A を 1,800 → 1,900、B を 2,100 → 2,200 に緩めた。
  回転オフセットの導出（`setGramSize`）を入れたぶんと、開発中の新コア（§6.1）でも
  同じ予算で通るようにするため。**予算はコアに依らず 1 本にする**方針。

> **構成 A が 1,900 / 1,900 でちょうど。** 新コアは base が小さいぶん増分側に

- **TinyGFX 側の増分はほぼ同じ**（E で +6,540 vs +6,588）。増分はコアに依らない =
  我々の数字として信用できる。**予算表 1 本で両方のコアを守れている**
- **コアの下駄が 5,268 B 減る。** 使える余地が 10,492 B → 15,760 B に増える（1.5 倍）
- **`TinyGFXBusSPI`（ハードウェア SPI）がリンクできる。**
  [EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E2 / E3 はこのコアで解消する

### 6.2 Arduino Uno R3（`arduino:avr:uno`）

**全構成ビルドが通る。** フラッシュ 32KB / RAM 2KB。

| 構成 | Flash | Δ | RAM | Δ | RAM（PROGMEM 対応前） |
| --- | --- | --- | --- | --- | --- |
| base | 444 | — | 9 | — | 9 |
| C | 5,820 | +5,376 | 118 | +109 | 118 |
| D | 7,468 | +7,024 | **142** | +133 | 534 |
| E | 8,388 | +7,944 | **150** | +141 | 542 |
| T | 9,780 | +9,336 | 719 | +710 | 1,111 |

読み取れること:

- **フラッシュは余裕。** 構成 E で 32KB の 23%
- **効くのは RAM。** フォントを PROGMEM に置く対応（[DECISIONS.ja.md](DECISIONS.ja.md) D19）で
  構成 D の RAM が **511 → 119 B** になった。これが無いと 95 文字のフォントで
  1.2KB（2KB の 60%）を持っていかれて実用にならない
- 8bit なので同じ機能でもフラッシュは CH32 より 1 割ほど大きい（16bit 演算のぶん）
- 構成 T の RAM 695 B は 240px 幅の帯が支配的。UNO で使うなら 128px の ST7735 あたりで
  帯は 256 B になる

**AVR で残っている制約**: `pushImage` の画像データは RAM 上のもののみ。
**この制約は AVR だけ**（他はフラッシュがアドレス空間に見えている）。
フラッシュに置きたいときは `drawImage` を使う（[DECISIONS.ja.md](DECISIONS.ja.md) D27）。

### 6.4 I2C + モノクロ OLED（SSD1306 128x64）

同じ描画を SPI のカラーパネルとモノクロ OLED でやったときの差。

**2026-08-30 実測**（`fillRect` シームと `drawPixel` の寄せ込みの後。
[OPTIMIZE.ja.md](OPTIMIZE.ja.md) の A/I・D/E/F）。

| 構成 | CH32V003 flash | Δ flash | RAM | RAM / 2KB |
| --- | --- | --- | --- | --- |
| A 相当（`fillScreen`） | 8,000 | +2,108 | 1,616 | 79% |
| C 相当（全プリミティブ） | 11,052 | +5,160 | 1,616 | 79% |
| D 相当（+文字） | **12,332** | **+6,440** | **1,616** | **79%** |
| D 相当・`TINYGFX_MONO_FAST_FILL=0` | 11,924 | +6,032 | 1,616 | 79% |
| **D 相当・帯（1 ページ 128 B）** | **12,408** | **+6,516** | **720** | **35%** |
| （参考）SPI + ST7789 の D | 11,992 | +6,100 | 576 | 28% |

### 帯で描くと RAM が 1/2 以下になる

フレームバッファを持たず、**1 ページ（横 1 行 x 8 画素、128 バイト）だけ**を持って
シーンをページごとに描き直す（`setBandPage()`）。カラーの `TileCanvas` と同じ考え方。

| | 全面バッファ | 帯（1 ページ） |
| --- | --- | --- |
| RAM | 1,616 B（**79%**） | **720 B（35%）** |
| flash | 12,332 | 12,408（**+76**） |
| 全画面を描き直す転送量 | 1,024 B | 1,024 B（**同じ**） |
| 1 ページだけ変える転送量 | **128 B** | 1,024 B（**8 倍**） |
| 絵 | — | **完全に同じ**（`tests/i2c/` が検査） |

**RAM と転送量のどちらを取るかの選択で、絵は変わらない。**

- **時計のように一部だけ書き換える用途は全面バッファ。** 変わったページだけ流せる
  ので、I2C 400kHz で 128 B（約 3ms）対 1,024 B（約 23ms）と大差がつく
- **毎フレーム作り直す用途、あるいは RAM が足りない場合は帯。** CH32V003 で
  79% → 35% は「アプリが乗らない」と「乗る」の差
- 帯の代金は **flash +76 B**。ページ数を増やせば（2 ページ 256 B など）
  転送の粒度と RAM の間を取れる

- **バイト単位の塗り（`TINYGFX_MONO_FAST_FILL`、既定 1）に 408 バイト**。
  2026-08-30 に測り直した値。`fillRect` がシームになったので、off にすると
  SSD1306 は基底の既定（窓 + 画素ごとの `put`）に落ちる
  8 画素が 1 バイトに詰まっているので、ページを丸ごと覆う矩形はバイトで塗れる。
  128x64 の全面消去が **約 6.8ms → 約 0.9ms**（CH32V003 24MHz の見積り）。
  ただし `display()` の転送が I2C 400kHz で **約 23ms** かかるので、
  **1 フレーム 30ms のうち 6ms、2 割**にしかならない。要らなければ 0 にする
- **切ると SPI + ST7789 より 68 バイト小さい**（11,924 対 11,992）。
  初期化列が短く、画素の転送がバッファへのビット書き込みで済むため
- **RAM は +1,036 バイト**（フレームバッファ 1,024 + Wire の分）
- CH32V003 で 1,608 / 2,048 = **79%。載るが残り 440 バイト**
- Uno R3 で 1,412 / 2,048 = 69%
- **128x32 のパネルならフレームバッファが 512 バイト**になるので、どちらも余裕が出る

## 7. 速度 — **2026-08-28、初めて測った**

M5Stack Core（ESP32 240MHz）/ 内蔵 ILI9342C 320x240 / **SPI 24MHz** /
`TINYGFX_FILL_CHUNK` **無効** / `tests/manual/m5stack` のページ 9。

| 項目 | 実測 | 1 回あたり | 画素あたり |
| --- | --- | --- | --- |
| `fillScreen` x5 | 892 ms | 178 ms | **2.32 µs** |
| `fillRect` 100x100 x200 | 4,652 ms | 23.3 ms | **2.33 µs** |
| `fillCircle` r100 x200 | 17,778 ms | 88.9 ms | **2.83 µs** |
| `drawLine` 対角 x200 | 1,269 ms | 6.35 ms | **19.8 µs** |
| `drawString` 10 文字 x200（倍角 2） | 600 ms | 3.0 ms | 1 文字 0.30 ms |
| `TileCanvas` 全画面 x20 | 3,870 ms | 194 ms | 2.52 µs |

### 読み取れること

- **塗りは 2.3 µs/画素。理論値の 3.5 倍。** 24MHz で 16 ビットなら 0.67 µs のはず。
  差はぜんぶ**1 バイトずつ `SPI.transfer()` を呼んでいるオーバーヘッド**。
  → `TINYGFX_FILL_CHUNK` を直した（§7.1）。**再測定待ち。**
- **点を打つのは 19.8 µs/画素。塗りの 8.5 倍。** `drawPixel` は毎回
  CASET/RASET/RAMWR（11 バイト）を送り、DC ピンを 6 回上げ下げする。
  **斜め線と円周が高いのはこれ。** 水平ランにまとめれば縮むが、フラッシュと引き換え。
- **文字は速い。** 1 文字 0.30 ms。ビットのランを `fillRect` で描いているので、
  点を打つ実装より 1 桁速い。
- **ちらつきを消す代金は 9%。** `TileCanvas` の全画面 194 ms に対し、
  素の `fillScreen` が 178 ms。**帯に描く CPU 時間は SPI 待ちにほぼ隠れている。**
  ただし全画面 194 ms は **5 fps**。動かすなら描き換える範囲を絞ること。

### 7.1 `TINYGFX_FILL_CHUNK` は効かない実装だった（直した）

上の数字を見て気づいた。**直す前の実装は速くならない。**

```cpp
// 直す前: バッファに詰めて writeData() に渡していた
while (count >= CHUNK) { writeData(buf, sizeof(buf)); ... }
// その writeData は…
void writeData(const uint8_t* d, size_t n) { while (n--) _spi->transfer(*d++); }
```

**結局 1 バイトずつ送っている。** バッファに詰め替えるぶん、むしろ無駄だった。

直した版は Arduino 標準の **`SPI.transfer(buf, len)`（ブロック転送）**を使う。
`writeColor` だけでなく **`writePixels`（TileCanvas と pushImage の経路）**にも入れた。

**注意点が 1 つ。** `transfer(buf, len)` は**受信データでバッファを上書きする**ので、
チャンクごとに詰め直さないと 2 回目以降が化ける。`tests/fillchunk/` が
「まとめ書きしても線に出るバイトが 1 つも変わらない」ことを検査していて、
詰め直しを外すと 885 画素が壊れて落ちる（確認済み）。

**速くなるかはまだ測っていない。** 実機で `TINYGFX_FILL_CHUNK=32` と 40MHz を
入れて測り直したら、ここに 2 列目を足す。

## 9. 載っていてはいけないシンボル

**未使用機能が落ちること自体はリンカ（`--gc-sections`）に任せる。** ここで検査するのは、**落ちるはずのものが参照の連鎖で残っていないか**。`tests/linkprune/` が最終バイナリの `nm` 出力で守る（`noalloc` はそこへ統合済み）。

### 8.1 構成別（「まわりまわって載る」の検出）

| 構成 | 使う機能 | このシンボルが出たら fail |
| --- | --- | --- |
| **A** | `fillScreen` のみ | `drawLine` / `drawCircle` / `fillRoundRect` / `fillTriangle` / `drawChar` / フォントデータ / `pushImage` / `TileCanvas` / `TinyGFXPrint` |
| **B** | + 矩形・点・直線系 | 円・三角・文字・フォントデータ・`Print` |
| **C** | + 全プリミティブ | 文字・フォントデータ・`Print` |
| **D** | + 文字 | `Print` / `pushImage` |
| **E** | + `pushImage` | `Print` |

**この表がライブラリ構造の実効的な仕様になる。** 1 行でも落ちたら、原因は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.4 の R1〜R9 のどれかを破っている。

### 8.2 全構成共通（A〜E。拡張ヘッダを入れた P1 / P2 は対象外）

**判定は base との差で行う。** `_malloc_r` のようにコア側が最初から持ち込んでいるものを
TinyGFX のせいにしないため（CH32V003 の base には実際に `_malloc_r` が入っている）。

| 分類 | シンボル例 |
| --- | --- |
| 動的確保 | `_Znwj`（operator new）/ `_Znaj`（base に無い場合のみ） |
| 浮動小数点演算 | `__addsf3` / `__mulsf3` / `__divsf3` / `__floatsisf` |
| 浮動小数点書式化 | `printFloat` / `_dtoa` / `vfprintf` |
| シリアル出力 | `Print` / `HardwareSerial`（R4 の担保） |
| C++ ランタイム | `__cxa_guard_acquire`（関数内 static、R9 の担保）/ 例外関連 |

**要確認（Phase 0）**: CH32V003 のコアが乗除算命令を持たない構成なら、`__udivsi3` / `__umodsi3` もこのリストに入れる。描画アルゴリズムから除算を排除できているかの指標になる。

## 10. 削減のときに見る順番

増えてしまったときのチェックリスト。**上から効く。**

1. **virtual を増やしていないか。** vtable 参照は `--gc-sections` を無効化する（[DECISIONS.ja.md](DECISIONS.ja.md) D1）
2. **関数内 `static` を書いていないか。** ガード変数と初期化コードが載る
3. **除算・剰余を使っていないか。** ソフトウェアルーチンが載る
4. **`int` で計算していないか。** `int16_t` で足りる箇所を 32bit で回していないか
5. **同じ処理が inline 展開で複製されていないか。** 大きい関数は `inline` を外す
6. **`const` データが `.rodata` に正しく置かれているか**（AVR は別途 PROGMEM が要る）
7. **拡張ヘッダの中身がコアから参照されていないか。** 参照した瞬間に全員が払う
