# 最適化バックログ

開発用の作業リスト。方針が決まった項目から潰していく。

数値はすべて **空スケッチからの増分**（絶対値ではない）。計測環境は
`arduino:avr:uno`、比較対象は U8g2 2.36.19。同じ絵（枠・塗り・円・線・
三角・`12:34`）を描くスケッチで測った。

「実測」と書いていないものは見積り。潰すときに必ず測り直すこと。

## 全体の位置づけ

| | flash | 静的 RAM |
| --- | --- | --- |
| TinyGFX 全面バッファ | **8,030** | 1,410 |
| TinyGFX 帯 | **8,214** | **514** |
| U8g2 全面 (`_F_`) | 10,920 | 1,628 |
| U8g2 ページ (`_1_`) | 11,020 | 732 |
| Adafruit SSD1306 | 13,720 | 344 (別途 malloc 1,024) |

合計では 2.9 KB 勝っている。ただし分解すると評価が変わる。

| | 何もしない | +図形 | +文字 |
| --- | --- | --- | --- |
| TinyGFX | 5,066 | +1,374 | **+1,590** |
| U8g2 | 8,114 | +1,560 | +1,246 |

- 起動時点で 3,048 B 勝ち（U8g2 は u8x8 層と 60 種以上のコントローラ記述を持つ）
- 図形はほぼ互角（186 B 勝ち）
- **文字は負け。** しかも U8g2 のフォントデータは 804 B / 95 字、こちらは
  63 B / 13 字。データを引くとコードは **1,527 B 対 442 B**

## A / I. パネルが `fillRect` を奪える形にする → **済（2026-08-28）**

`TinyGFXPanel` に `fillRect` を 8 個目の仮想関数として追加し、`TinyGFX::fillRect`
はクリップ後にそこへ投げるだけにした。既定は従来どおり窓 + `writeColor` なので、
**何もしないパネルは何も書かなくていい。**

`TinyGFXPanelSSD1306` がそれを奪う。以前は `writeColor` の中で
「窓ぜんぶを 1 色で塗る呼び出しか？」を判定して `fillWindow` に分岐していたが、
その判定と窓の保存（`_xs/_ys/_xe/_ye`、カーソル、`windowPixels()`）が丸ごと
不要になった。

| | 変更前 | 変更後 |
| --- | --- | --- |
| `PanelSSD1306::writeColor` | 736 | **76** |
| `PanelSSD1306::fillRect` | — | 580 |
| `TinyGFX::fillRect` | 280 | 220 |

### 結果は**モノクロが得をしてカラーが損をする**

| | CH32V003（基準機） | AVR |
| --- | --- | --- |
| モノクロ（SSD1306）`o_a`/`o_c`/`o_d`/`o_band` | **−76 〜 −92** | **−138** |
| カラー（ST7789）`a`〜`e`/`t` | **+40 〜 +56** | **+14 〜 +46** |

カラーが増えるのは、`TinyGFX::fillRect` → `panel->fillRect`（既定）→
`setWindow` + `writeColor` と**間接呼び出しが 2 回から 3 回に増える**ため。

**カラーパネル側にも `fillRect` を持たせて中で自分の `setWindow` /
`writeColor` を呼ぶ案を試したが、効果なし**（`t` はむしろ +68）。GCC は
`this` 経由の仮想呼び出しを解決してくれなかった。

### 判断

モノクロの得がカラーの損の約 2 倍。加えて**これが無いとパネル単位の最適化が
一切できない**（H の分析はすべてこのシームの上に乗る）。48 B は CH32V003 の
フラッシュの 0.3%。

**採用する。** カラーだけを使うプロジェクトにとっては純粋な退行なので、
そこが問題になるなら差し戻せる（この 1 コミットで完結している）。

ホストテスト 49 本すべて通過（描画結果は不変）。

## B. フォント形式にランを持たせる → **却下（2026-08-28、実測）**

同じ実装の中で形式だけ差し替えた比較（`tgfx_full` のフォントを CellFont から
u8g2 形式に替えただけ）:

| | CellFont（生ビットマップ） | u8g2 形式（RLE） |
| --- | --- | --- |
| `draw` | 878 | 624 |
| 索引 | `indexIn` 194 | `glyphData` 198 + `Bits::get` 110 + `getSigned` 32 + `makeWord` 30 |
| `advance` | 122 | 146 |
| `ascent` / `lineHeight` | 24 | 30 |
| **計** | **1,218** | **1,170** |

**差は 48 B。** ビットスキャンが消えて `draw` は 254 B 減るが、ビット読み出しと
索引に 370 B 取られて相殺する。

**CellFont 仕様 §13.2 の「圧縮しない」判断はこちらの実測でも支持された。**
LGFXFontToolJs への仕様変更依頼は**出さない**。

## J. `tinygfx_cell::draw` の実装

### 済: ビットストリームの読み方（2026-08-28）

グリフのビット列の歩き方は**機械によって最適が違う**。両方実測:

| | AVR `draw` | AVR 合計 | CH32V003 |
| --- | --- | --- | --- |
| ビットカウンタで索引（元） | 878 | 8,030 | 基準 |
| カウンタを uint16 に | 780 | 7,932 | **+16** |
| **バイト単位で食う** | **716** | **7,868** | **+16** |
| **`#if defined(__AVR__)` で分岐（採用）** | **716** | **7,868** | **±0** |

- AVR はバレルシフタも 32 ビットレジスタも無いので、画素ごとの可変シフトが高い。
  ストリームを 1 バイトずつ食えば **162 B 小さい**
- RISC-V はシフトが 1 命令で 32 ビットが自然なので、カウンタのほうが安い。
  16 ビットへの切り詰めがゼロ拡張を呼び、どちらの変種も **+16 B**
- 払う代償が同じなので、AVR で −162 を取る側を `#if` で選ぶ

**ホストテスト 45 本すべて通過（描画結果は不変）。**

### 済: グリフのループから「先頭列か？」の判定を外した（2026-08-29）

ビット読みを `CellBits` に括り出し、行の先頭画素をループの外で読むように
した。画素ごとの `if (c == 0)` が消える。

| | CH32V003 | AVR |
| --- | --- | --- |
| `o_d` / `d` / `t` | **−8 〜 −12** | **+12** |

基準機が縮み AVR が同じだけ増える。**基準機を優先**して採用した。
ビット読みが 1 箇所にまとまるので、`#if defined(__AVR__)` の分岐も
2 箇所から 1 箇所になった。

C++11 の落とし穴をひとつ踏んだ: 既定メンバ初期化子を持つ構造体は
**集成体ではない**ので `CellBits bits = {src};` が通らない
（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §6.1）。コンストラクタにした。

### 残り 716 B の内訳（AVR、削って測った診断）

| | |
| --- | --- |
| **コア（走査 + ラン描画）** | **約 502 B** |
| 背景セル（`hasTextBg`） | 130 B |
| `textSize` 倍率 | 74 B |
| `next` 連鎖 | 10 B |
| （別シンボル）`indexIn` | 194 B |

U8g2 のデコード一式は約 310 B。ただし **U8g2 に `textSize` 相当は無い**
（大きい字は別フォントを積む）ので、同機能で比べるとコア 502 対 310。
**3 倍ではなく 1.6 倍。**

背景セル・`textSize`・`next` はマクロで落とせる候補（C と同じ扱い）。

### 注意: この比較は AVR で測っている

U8g2 との比較はすべて `arduino:avr:uno`。だが
[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §6 では AVR は
**「フラッシュは余裕、効くのは RAM」**であり、基準機は CH32V003。

**上の 162 B は、拘束条件になっていない board での利得。**
CH32V003 では `t` 構成が 7,596 / 予算 8,400 で余裕がある。

以後の最適化は**必ず両アーキテクチャで測る**こと。AVR で効くものが
RISC-V で逆効果になる例が既に出ている。

## C. デコーダの切り落としマクロ → **済（2026-08-28）**

`src/TinyGFX/FontCell.h` のマクロを 5 つに増やした。既定は全部 on なので
**何も指定しなければ挙動もサイズも従来どおり**（AVR 7,868 / CH32V003 の
`t` = 7,596、どちらも変化なしを実測）。

| マクロ | 落とすもの | AVR | CH32V003 |
| --- | --- | --- | --- |
| `TINYGFX_FONT_SPARSE` | 疎索引（コード表・頭ブロック） | フォント次第 | フォント次第 |
| `TINYGFX_FONT_RECORDS` | 可変ピッチ（グリフ表） | フォント次第 | フォント次第 |
| `TINYGFX_FONT_BG` | グリフ背後の背景セル | 130 | **108** |
| `TINYGFX_FONT_SCALE` | `setTextSize()` の倍率 | 74 | **116** |
| `TINYGFX_FONT_CHAIN` | `CellFont::next` の連鎖 | 34 | **16** |
| **BG + SCALE + CHAIN** | | **216** | **220** |

- `SPARSE` / `RECORDS` は**フォントと一致していないと違うグリフを描く。**
  符号化は実行時データなのでコンパイラには見えない。生成ヘッダの
  `Format :` 行（`fixed/sparse` など）が唯一の手がかり
- `BG` / `SCALE` が落とすのは**スケッチ側の機能**。off にすると
  `setTextColor()` の第 2 引数と `setTextSize(2)` 以上が効かなくなる

**`tests/build_matrix` に `test_font_macros_build` を追加。** 1 つずつと
全部 off をコンパイルし、削減量を出し、増えていたら落ちる。off の経路は
既定のビルドに現れないので、これが無いと静かに腐る。

## D / E / F → **済（2026-08-29）**

### D. `TINYGFX_MONO_FAST_FILL` の実コストを測り直した

シーム化で意味が変わった。off にすると SSD1306 は `fillRect` を奪わなくなり、
基底の既定（窓 + `writeColor` → 画素ごとの `put`）に落ちる。

| | CH32V003 | AVR |
| --- | --- | --- |
| このマクロの代金 | **428** | **596** |

（ヘッダのコメントにあった 512 は古い値。）**既定は on のまま。**
off にすると塗りが画素単位になり、フレーム時間の 2 割を失う。

### E. `put()` の per-pixel 経路

- 範囲判定を符号なし比較 1 組にまとめた（`x < 0` と `x >= _width` が 1 回で済む）
- バッファ添字の 32 ビット演算を 16 ビットに。ページ方式のパネルは
  最大でも数百 x 8 ページなので溢れない
- `fillRect` のマスク生成をループから `(0xFF << lo) & (0xFF >> (7 - hi))` に

**CH32V003 −20 / AVR ±0。**

`clearBuffer` と `display()` の 32 ビット演算も同じように狭めてみたが、
**CH32V003 で +32 になったので戻した**（RISC-V は 32 ビットが自然で、
`int16_t` のループはゼロ拡張を呼ぶ）。AVR では −66 だった。
**基準機を優先する。**

### F. `drawPixel` を `fillRect` に寄せた ← いちばん効いた

```cpp
void drawPixel(int16_t x, int16_t y, uint16_t color) { fillRect(x, y, 1, 1, color); }
```

クリップの記述が 1 箇所になり、`setWindow` + `writeColor(1)` の経路が消え、
**`fillRect` を奪ったパネルが `drawPixel` も面倒を見る**ようになる。

| | CH32V003 | AVR |
| --- | --- | --- |
| カラー（`b` / `d` / `t`） | **−88 〜 −92** | **−88 〜 −108** |
| モノクロ（`o_d`） | **−88** | **−154** |

**これで A/I のカラー退行が消えた。** 差し引きでカラーも作業前を下回る。

## I. パネルが `fillRect` を奪える形にする

### シームは 3 つしかない

`Gfx.h` がパネルに触るのは、ライフサイクルを除くと **3 形**だけ:
`drawPixel` / `fillRect` / `pushImage`（いずれも `setWindow` + `writeColor`
または `writePixels`）。線・矩形・円・角丸・三角・**文字**はすべて
`fillRect` の上に乗っている（`FontCell.h` が呼ぶのは `g.fillRect` と
`g.startWrite` / `g.endWrite` だけ）。

**この 3 つをパネルが奪えれば、パネル単位の最適化はすべて可能。**

### 実装は仮想関数 3 つ

```cpp
class TinyGFXPanel {
  // 既定は今と同じ。パネルが override して奪う
  virtual void fillRect(uint16_t x, uint16_t y, uint16_t w, uint16_t h, uint16_t c) {
    setWindow(x, y, x + w - 1, y + h - 1);
    writeColor(c, (uint32_t)w * h);
  }
  ...
};
```

| | |
| --- | --- |
| 代償 | vtable スロット 3 個 = パネルあたり 6 B + 既定実装 60 B 程度（**未計測**） |
| スケッチの変更 | **なし** |
| フォント ops | **触らない** |

### テンプレート化は却下（2026-08-28）

`TinyGFX` をパネル型でテンプレート化する案を検討したが、**取り下げた。**

- 確実に消えるのは vtable 本体 18 B（パネル）+ 20 B（バス）と仮想呼び出しの
  間接分。**数十バイト**
- 代償は CRTP の定型、`TinyGFXPrint` もテンプレート化、パネルごとのエイリアス、
  `TinyGFX&` が渡せなくなる、`.ino` 25 ファイルの書き換え、`override` 53 箇所の削除
- **フォント ops が `TinyGFX&` を受け取っている**ため ops もテンプレート化が必要になり、
  C++11 に変数テンプレートが無い（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §6.1）ので
  スケッチが書く行まで波及する
- **A・J・C はどれもテンプレート化を必要としない**

`tgfx_none` の 1,288 B は「描画しないスケッチ」の数字であって、実際に描く
スケッチでは全部使われている。**無駄ではない。**

将来、仮想呼び出しのコストを実測して効くと分かったら再検討する。

## H. 最適化の軸は「モノクロ／カラー」ではない

U8g2 の低レベル書き込みは **2 つだけ**で、名前が色深度ではなく
**バッファ配置**を指している。

| 層 | 実装 | サイズ |
| --- | --- | --- |
| クリップ | `u8g2_DrawHVLine` 1 本 | 342 |
| 回転 | `draw_l90_r0/r1/r2/r3` + `mirrorr_r0` | 32 (r0) |
| **バッファ配置** | `u8g2_ll_hvline_vertical_top_lsb` / `..._horizontal_right_lsb` | 218 |

「モノクロ用」という層は存在しない。あるのは「この並びのバッファにランを
書く」層だけ。

### モノクロは 1 つの形式ではない

| パネル | 並び | 1 ラン書くと |
| --- | --- | --- |
| SSD1306 / SH1106 | 1bpp **縦**ページ | 縦ラン = 1 バイトストア / 横ラン = ビット演算 × len |
| Sharp Memory / ST7305 | 1bpp **横** | 横ラン = memset / 縦ラン = ビット演算 × len |
| SSD1327 | 4bpp 横 | ニブル |
| ST7789 / ILI9342 | 16bpp 直接 GRAM | 窓 + ストリーム |

SSD1306 と Sharp は、お互いの距離が RGB565 との距離と同じくらい離れて
いる（縦ランと横ランでコストが逆転する）。「モノクロだから」で一括りに
できるのは、色の配管が消えることだけ。

### 2 種類は逆のプリミティブを欲しがる

- **バッファ持ち（SSD1306）**: ランが正解。窓プロトコルを挟むと、縦 8px =
  1 バイトのはずが `toBuffer` の座標計算 + `put` の per-pixel になる。
  実測 1,288 B（A 参照）
- **直接 GRAM（ILI9342）**: **ランは損。** 1 ラン = `setWindow` の SPI
  コマンド 11 バイト。5×7 グリフを 10 ランに分解した場合の概算:

  | | バイト数 |
  | --- | --- |
  | ラン分解（現状の `fillRect` × 10） | 窓 110 + 画素 40 ≒ 150 |
  | グリフ枠を 1 回窓取りして 35px 流す | 11 + 70 = 81 |

  **未計測。** 窓プロトコルは矩形に対して償却が効く仕組みで、ランに刻むと
  その利点を捨てる。ただし枠ごと流すと背景を描くことになり、透過文字が
  できなくなる（意味論の変更）

### 軸の整理

- **第 1 軸 = バッファ持ちか直接か** → プリミティブの形（ラン / 矩形ストリーム）
- **第 2 軸 = 画素の詰め方** → その実装（縦バイト / 横バイト / ニブル / uint16）

色深度は第 2 軸の一項目にすぎない。TinyGFX の現行パネルは第 1 軸で綺麗に
2 つに割れる（SSD1306 / ST7789 + ILI9342）。

**A を設計するときは「モノクロ専用エンジン」ではなく、この 2 軸で切ること。**
