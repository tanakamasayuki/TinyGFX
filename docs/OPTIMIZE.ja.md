# 最適化バックログ

開発用の作業リスト。方針が決まった項目から潰していく。

数値はすべて **空スケッチからの増分**（絶対値ではない）。計測環境は
`arduino:avr:uno`、比較対象は U8g2 2.36.19。同じ絵（枠・塗り・円・線・
三角・`12:34`）を描くスケッチで測った。

「実測」と書いていないものは見積り。潰すときに必ず測り直すこと。

## 全体の位置づけ

| | flash | 静的 RAM |
| --- | --- | --- |
| TinyGFX 全面バッファ | **8,030** | 1,410 |
| TinyGFX 帯 | **8,214** | **514** |
| U8g2 全面 (`_F_`) | 10,920 | 1,628 |
| U8g2 ページ (`_1_`) | 11,020 | 732 |
| Adafruit SSD1306 | 13,720 | 344 (別途 malloc 1,024) |

合計では 2.9 KB 勝っている。ただし分解すると評価が変わる。

| | 何もしない | +図形 | +文字 |
| --- | --- | --- | --- |
| TinyGFX | 5,066 | +1,374 | **+1,590** |
| U8g2 | 8,114 | +1,560 | +1,246 |

- 起動時点で 3,048 B 勝ち（U8g2 は u8x8 層と 60 種以上のコントローラ記述を持つ）
- 図形はほぼ互角（186 B 勝ち）
- **文字は負け。** しかも U8g2 のフォントデータは 804 B / 95 字、こちらは
  63 B / 13 字。データを引くとコードは **1,527 B 対 442 B**

## A. 窓プロトコル → ラン (HVLine) プリミティブ

**いちばん大きい。** モノクロパネルを「窓を持つカラーパネル」として扱う
翻訳コスト。

実測（`tgfx_none` = パネルを構築して一切描画しないスケッチ）:

| | |
| --- | --- |
| `PanelSSD1306::writeColor` | 736 |
| `PanelSSD1306::put(bool)` | 320 |
| `PanelSSD1306::toBuffer` | 112 |
| `PanelSSD1306::writePixels` | 84 |
| `PanelSSD1306::setWindow` | 36 |
| **計** | **1,288** |

**一度も描画していないのに 1,288 B 載る。** `TinyGFXPanel` の vtable が
この 3 スロットを持つのでリンカが落とせない（D1）。

U8g2 の同等品は `u8g2_DrawHVLine` 342 + `u8g2_ll_hvline_vertical_top_lsb`
218 = **560 B**。

- 見込み: **約 700 B**、加えて速度（垂直 8px ラン = 1 バイトストアになる）
- 範囲: モノクロ大 / カラー中（窓設定のコマンド往復が減る）
- リスク: **`TinyGFXPanel` 基底の変更 = 全パネル書き換え。** 分離を
  `TinyGFX` の層だけでやるとこの 1,288 B は残る
- 未計測: カラー側でランプリミティブにしたときの差。**次に測るならここ**

## B. フォント形式にランを持たせる → **却下（2026-08-28、実測）**

同じ実装の中で形式だけ差し替えた比較（`tgfx_full` のフォントを CellFont から
u8g2 形式に替えただけ）:

| | CellFont（生ビットマップ） | u8g2 形式（RLE） |
| --- | --- | --- |
| `draw` | 878 | 624 |
| 索引 | `indexIn` 194 | `glyphData` 198 + `Bits::get` 110 + `getSigned` 32 + `makeWord` 30 |
| `advance` | 122 | 146 |
| `ascent` / `lineHeight` | 24 | 30 |
| **計** | **1,218** | **1,170** |

**差は 48 B。** ビットスキャンが消えて `draw` は 254 B 減るが、ビット読み出しと
索引に 370 B 取られて相殺する。

**CellFont 仕様 §13.2 の「圧縮しない」判断はこちらの実測でも支持された。**
LGFXFontToolJs への仕様変更依頼は**出さない**。

**未調査。** 何が 3 倍を作っているか分かっていない。次にやること。

## C. デコーダの機能スイッチの既定値見直し

疎索引と可変ピッチを 1 つのデコーダで扱う代金。

実測: `-DTINYGFX_FONT_SPARSE=0 -DTINYGFX_FONT_RECORDS=0` で
デコーダ 1,072 → **808 B**、総計 8,030 → 7,756。

- 見込み: **264 B（実測）**
- 範囲: 両方
- リスク: 低。今もマクロで落とせる。既定値をどうするかだけの話
- **すぐ潰せる。** B より先にやってよい

## D. `TINYGFX_MONO_FAST_FILL` の見直し

`writeColor` 736 B の大半がこれ（既定 ON、+512 B）。

- 見込み: 512 B（OFF にすれば）
- 範囲: モノクロ
- リスク: 速度とのトレードオフ
- **A をやると不要になる可能性が高い。** A の後に判断する

## E. `PanelSSD1306::put(bool)` の per-pixel 経路

実測 320 B。**A に吸収される見込み**なので単独では触らない。

## F. `TinyGFX::fillRect` / `drawPixel`

実測 280 / 180 B。A の設計次第で形が変わる。

## G. `TinyGFXBus` 基底のスタブ

実測 2 B × 8 + vtable 20 B = 36 B 程度。**小さいので優先度低。**

## I. パネルが `fillRect` を奪える形にする

### シームは 3 つしかない

`Gfx.h` がパネルに触るのは、ライフサイクルを除くと **3 形**だけ:
`drawPixel` / `fillRect` / `pushImage`（いずれも `setWindow` + `writeColor`
または `writePixels`）。線・矩形・円・角丸・三角・**文字**はすべて
`fillRect` の上に乗っている（`FontCell.h` が呼ぶのは `g.fillRect` と
`g.startWrite` / `g.endWrite` だけ）。

**この 3 つをパネルが奪えれば、パネル単位の最適化はすべて可能。**

### 実装は仮想関数 3 つ

```cpp
class TinyGFXPanel {
  // 既定は今と同じ。パネルが override して奪う
  virtual void fillRect(uint16_t x, uint16_t y, uint16_t w, uint16_t h, uint16_t c) {
    setWindow(x, y, x + w - 1, y + h - 1);
    writeColor(c, (uint32_t)w * h);
  }
  ...
};
```

| | |
| --- | --- |
| 代償 | vtable スロット 3 個 = パネルあたり 6 B + 既定実装 60 B 程度（**未計測**） |
| スケッチの変更 | **なし** |
| フォント ops | **触らない** |

### テンプレート化は却下（2026-08-28）

`TinyGFX` をパネル型でテンプレート化する案を検討したが、**取り下げた。**

- 確実に消えるのは vtable 本体 18 B（パネル）+ 20 B（バス）と仮想呼び出しの
  間接分。**数十バイト**
- 代償は CRTP の定型、`TinyGFXPrint` もテンプレート化、パネルごとのエイリアス、
  `TinyGFX&` が渡せなくなる、`.ino` 25 ファイルの書き換え、`override` 53 箇所の削除
- **フォント ops が `TinyGFX&` を受け取っている**ため ops もテンプレート化が必要になり、
  C++11 に変数テンプレートが無い（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §6.1）ので
  スケッチが書く行まで波及する
- **A・J・C はどれもテンプレート化を必要としない**

`tgfx_none` の 1,288 B は「描画しないスケッチ」の数字であって、実際に描く
スケッチでは全部使われている。**無駄ではない。**

将来、仮想呼び出しのコストを実測して効くと分かったら再検討する。

## H. 最適化の軸は「モノクロ／カラー」ではない

U8g2 の低レベル書き込みは **2 つだけ**で、名前が色深度ではなく
**バッファ配置**を指している。

| 層 | 実装 | サイズ |
| --- | --- | --- |
| クリップ | `u8g2_DrawHVLine` 1 本 | 342 |
| 回転 | `draw_l90_r0/r1/r2/r3` + `mirrorr_r0` | 32 (r0) |
| **バッファ配置** | `u8g2_ll_hvline_vertical_top_lsb` / `..._horizontal_right_lsb` | 218 |

「モノクロ用」という層は存在しない。あるのは「この並びのバッファにランを
書く」層だけ。

### モノクロは 1 つの形式ではない

| パネル | 並び | 1 ラン書くと |
| --- | --- | --- |
| SSD1306 / SH1106 | 1bpp **縦**ページ | 縦ラン = 1 バイトストア / 横ラン = ビット演算 × len |
| Sharp Memory / ST7305 | 1bpp **横** | 横ラン = memset / 縦ラン = ビット演算 × len |
| SSD1327 | 4bpp 横 | ニブル |
| ST7789 / ILI9342 | 16bpp 直接 GRAM | 窓 + ストリーム |

SSD1306 と Sharp は、お互いの距離が RGB565 との距離と同じくらい離れて
いる（縦ランと横ランでコストが逆転する）。「モノクロだから」で一括りに
できるのは、色の配管が消えることだけ。

### 2 種類は逆のプリミティブを欲しがる

- **バッファ持ち（SSD1306）**: ランが正解。窓プロトコルを挟むと、縦 8px =
  1 バイトのはずが `toBuffer` の座標計算 + `put` の per-pixel になる。
  実測 1,288 B（A 参照）
- **直接 GRAM（ILI9342）**: **ランは損。** 1 ラン = `setWindow` の SPI
  コマンド 11 バイト。5×7 グリフを 10 ランに分解した場合の概算:

  | | バイト数 |
  | --- | --- |
  | ラン分解（現状の `fillRect` × 10） | 窓 110 + 画素 40 ≒ 150 |
  | グリフ枠を 1 回窓取りして 35px 流す | 11 + 70 = 81 |

  **未計測。** 窓プロトコルは矩形に対して償却が効く仕組みで、ランに刻むと
  その利点を捨てる。ただし枠ごと流すと背景を描くことになり、透過文字が
  できなくなる（意味論の変更）

### 軸の整理

- **第 1 軸 = バッファ持ちか直接か** → プリミティブの形（ラン / 矩形ストリーム）
- **第 2 軸 = 画素の詰め方** → その実装（縦バイト / 横バイト / ニブル / uint16）

色深度は第 2 軸の一項目にすぎない。TinyGFX の現行パネルは第 1 軸で綺麗に
2 つに割れる（SSD1306 / ST7789 + ILI9342）。

**A を設計するときは「モノクロ専用エンジン」ではなく、この 2 軸で切ること。**
