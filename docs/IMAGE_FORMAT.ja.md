# 画像フォーマットの検討

**まだ決まっていない。** ブラウザと CLI で変換ツールを作る前提で、
どの形式を出力させるべきかを実測から詰める。開発中の文書なので日本語のみ。

形式の仕様そのものは、CellFont と同じく**ツール側（LGFXFontToolJs 相当）が
持ち、TinyGFX はその描画器の 1 実装になる**のが筋だと思う。

## フォントとは結論が逆になる

CellFont では「圧縮しない」が正解だった。**画像では逆**で、理由は 1 つ。

| | データ量 | デコーダ |
| --- | ---: | ---: |
| フォント（数字 13 字） | **63 B** | 約 1,000 B |
| 画像（64x64 の UI アイコン） | **8,192 B**（生 RGB565） | 約 300 B |

**フォントはデコーダがデータの 16 倍。画像はデータがデコーダの 27 倍。**
償却の向きが逆なので、同じ判断にはならない。

### デコーダの実費（CH32V003、実測 2026-08-29）

`fillRect` の上に素直に書いた場合。**どれもほぼ同じ。**

| 形式 | デコーダ |
| --- | ---: |
| 1bpp ビットマップ（実装済み `drawBitmap`） | 284 |
| 生 RGB565（PROGMEM から） | 312 |
| 4bpp パレット | 264 |
| RLE（長さ 1B + 色 2B） | 280 |
| RLE + 4bit パレット | 320 |

**形式選択はデコーダ側では決まらない。データ量だけで決まる。**

## データ量（実測）

代表的な絵を実際に符号化して測った。

| 画像 | 寸法 | 色数 | 生 RGB565 | 4bpp パレット | RLE(16bit) | **RLE+4bit パレット** |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| UI アイコン | 64x64 | 3 | 8,192 | 2,080 | 699 | **400** |
| UI アイコン | 32x32 | 3 | 2,048 | 544 | 237 | **116** |
| グラデーション | 64x64 | 2,560 | **8,192** | — | 7,680 | — |
| 疑似写真 | 64x64 | 3,218 | **8,192** | — | **12,285** | — |
| モノクロ絵 | 32x32 | 2 | 2,048 | — | — | **128**（1bpp） |
| SSD1306 全面 | 128x64 | 2 | 16,384 | — | — | **1,024**（1bpp） |

### ここから読めること

**1. UI 的な絵では RLE + パレットが圧倒的。** 64x64 で 8,192 → 400 と
**20 分の 1**。基準機 CH32V003 は flash 16KB・base 5,892 B なので、
**生 RGB565 の 64x64（8KB）はそもそも載らない。** 圧縮は「あると嬉しい」
ではなく「無いと使えない」。

**2. 写真では RLE が逆効果。** 疑似写真で 12,285 B と、生より 5 割大きい。
**形式は必ず生も持つ必要がある。**

**3. 写真は基準機の対象外。** 64x64 の生で 8KB は flash の半分。
**ESP32 では問題にならない**ので、生の経路は残すが基準機向けには勧めない。

**4. モノクロは 1bpp 一択。** 横詰め・縦詰めでデータ量は同じ（128 B）。
違うのは**どのパネルが速く貼れるか**だけ。

## 形式の案

CellFont と同じ考え方 —— **ツールが最小の符号化を選び、描画器は「何が
来るか」をヘッダから知る。** 利用者は選ばない。

```c
struct CellImage {
  const void*    data;        // 画素データ
  const uint16_t* palette;    // NULL なら直接色
  uint16_t       width, height;
  uint16_t       dataLen;     // RLE の終端判定に要る
  uint8_t        format;      // 下記
  uint8_t        paletteCount;
  uint16_t       transparent; // 透過色。使わないなら 0xFFFF などの番兵
};
```

`format` の候補:

| 値 | 形式 | 向き |
| --- | --- | --- |
| 0 | 生 RGB565 | 写真、色数の多い絵 |
| 1 | 4bpp パレット | 色数 16 以下でランが短い絵 |
| 2 | 8bpp パレット | 色数 256 以下 |
| 3 | RLE（長さ 1B + 色 2B） | 色数が多くフラットな絵 |
| 4 | **RLE + 4bit パレット** | **UI アート。いちばん効く** |
| 5 | 1bpp 横詰め | モノクロ。`drawBitmap` と同じ並び |
| 6 | **1bpp 縦詰め** | **SSD1306 / SH1106 向け。下記** |

**CellFont と同じくマクロで落とせるようにする**（`TINYGFX_IMAGE_RLE` /
`TINYGFX_IMAGE_PALETTE` など）。7 通りを 1 つのデコーダで扱うと、
CellFont の `draw` が 4 通りで 264 B 取られたのと同じことが起きる。

**あるいは形式ごとに別ヘッダにする**（`FontCell.h` / `FontU8g2.h` と同じ
形）。デコーダの実費がどれも 264〜320 B と近いので、**7 通り入りの 1 本より、
使う 1〜2 本を include するほうが小さい可能性が高い。** ここは実測して決める。

## モノクロの縦詰めについて

**データ量は横詰めと同じ**（32x32 でどちらも 128 B）。効くのは貼る速さ。

| | ページ方式パネルに貼るとき |
| --- | --- |
| **横詰め** | ランごとに `fillRect(len, 1)`。1 行ぶんのマスクは 1 ビットしか立たないので、**列ごとにビットの read-modify-write** が要る。w×h 回 |
| **縦詰め**（y がページ境界） | 1 バイトが縦 8 画素そのもの。**バッファへの store 1 回**で済む。w×h/8 回 |

**8 倍の差**。ただし条件が付く。

- **y がページ境界（8 の倍数）に乗っていること**
- **パネル固有の経路が要る。** 汎用の `TinyGFX` からは書けない

置き場所は `TinyGFXPanelPaged` の**非仮想メソッド**が筋だと思う
（`TinyGFXPanelDcs::readPixels()` と同じ扱い）。

```cpp
panel.pushVBitmap(x, y, w, h, data);   // SSD1306 / SH1106 だけ
```

仮想関数にするとカラーパネルが払う（`fillRect` シームで +40 B 払ったのと
同じ構図）。非仮想なら**呼ばない人は 0 バイト**。

### 全面画像という特別な場合

**128x64 のモノクロ全面画像を縦詰めで出せば、それは SSD1306 の
フレームバッファそのもの。** 貼るのは `memcpy` 1 回で、デコーダは要らない。

```cpp
memcpy(fb, splash, 1024);
panel.display();
```

スプラッシュ画面や固定の背景ではこれが最速かつ最小。**ツールが
「パネルのバッファ形式でそのまま出す」モードを持つ価値がある。**

## 決めたいこと

1. **形式ごとに別ヘッダか、1 本 + マクロか。** 実測で決める。CellFont の
   経験から、1 本に詰め込むと使わない分岐の代金が乗る
2. **`transparent` を形式に持たせるか、描画時の引数にするか。**
   `pushImage` は引数、`drawBitmap` は「0 は触らない」で固定。揃えたい
3. **PROGMEM の扱い。** `pushImage` は現在 RAM 専用（Q6）。画像は定数なので
   **PROGMEM が既定であるべき**。`drawBitmap` は既に `tinygfx_rd8` 経由に
   してある。生 RGB565 だけは `writePixels` の速い経路が RAM 前提なので、
   **PROGMEM 版を足すか、そこだけ遅いのを許容するか**を決める必要がある
4. **ツールが自動で最小を選ぶか、利用者が指定するか。** CellFont は自動。
   同じにするのが自然だが、「必ず生で」と言いたい場面はありそう

## 私の推し

**RLE + 4bit パレットを主力に、生 RGB565 と 1bpp（横・縦）を持つ。**
4bpp/8bpp の非圧縮パレットは、RLE 版があれば出番が少ない
（UI アイコン 64x64 で 2,080 対 400）。まずは 4 形式で始めて、
足りなければ足す。

**縦詰めは `TinyGFXPanelPaged` の非仮想メソッドとして。** 汎用 API には
入れない。
