# 画像フォーマット

**描画器は実装済み**（`src/TinyGFX/Image.h`）。**変換ツールは実験用の最小
実装**（`tools/img2h.py`）で、正式なものはブラウザ + CLI で別途作る。
この文書はそこへの申し送りで、判断の根拠になった実測を全部載せてある。
**ツール側の設計**（他の GFX が受け取る形式、asset ツールとの切り分け、
名前）は [IMAGE_TOOL.ja.md](IMAGE_TOOL.ja.md)。
開発中の文書なので日本語のみ。

形式の仕様そのものは、CellFont と同じくツール側が持ち、TinyGFX はその
描画器の 1 実装になるのが筋だと思う。

## フォントとは結論が逆になる

CellFont では「圧縮しない」が正解だった。**画像では逆。**

| | データ量 | デコーダ |
| --- | ---: | ---: |
| フォント（数字 13 字） | **63 B** | 約 1,000 B |
| 画像（64x64 の UI アイコン） | **8,192 B**（生 RGB565） | 約 400 B |

**フォントはデコーダがデータの 16 倍、画像はデータがデコーダの 20 倍。**
償却の向きが逆なので、同じ判断にはならない。

## データ量（実画像を符号化して実測）

| 画像 | 寸法 | 色数 | 生 RGB565 | RLE(16bit) | **RLE+4bit パレット** | 1bpp |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| UI アイコン | 16x16 | 3 | 512 | 135 | **55** | — |
| UI アイコン | 32x32 | 3 | 2,048 | 357 | **157** | — |
| UI アイコン | 64x64 | 3 | 8,192 | 741 | **416** | — |
| モノクロ絵 | 32x32 | 2 | 2,048 | 399 | 149 | **132** |
| スプラッシュ | 128x64 | 2 | 16,384 | 1,263 | **816** | 1,028 |
| グラデーション | 64x64 | 2,560 | **8,192** | 7,680 | — | — |
| 疑似写真 | 64x64 | 3,218 | **8,192** | 12,285 | — | — |

**1. UI 的な絵では RLE + パレットが 20 分の 1。** 基準機 CH32V003 は
flash 16KB・base 5,892 B なので、**生 RGB565 の 64x64（8KB）は載らない。**
圧縮は「あると嬉しい」ではなく「無いと使えない」。

**2. 写真では RLE が生より 5 割大きい。** 形式は必ず生も持つ必要がある。

**3. 写真は基準機の対象外。** 64x64 の生で flash の半分。ESP32 では問題に
ならないので生の経路は残すが、基準機向けには勧めない。

**4. 非圧縮パレット（4bpp / 8bpp）は実装していない。** 測った全画像で
RLE+パレットに負けたため（64x64 で 2,054 対 416）。必要になったら測り直す。

## デコーダの実費（実測、`-Os`）

**`src/TinyGFX/Image.h` の本実装での値。** 使い捨ての実験実装より 60〜90 B
高い —— PROGMEM 経由のヘッダ読み、透過の判定、ops の間接呼び出しぶん。

| 形式 | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| `raw565` | 400 | **638** ←最安 | 492 |
| `rle565` | **387** ←最安 | 663 | **467** ←最安 |
| `rlepal4` | 395 | 679 | 483 |
| `bitmap1h` | 400 | 654 | 592 |
| `bitmap1v` | 392 | 690 | 592 |
| 1bpp 両方 | 504 | 864 | 696 |

**アーキテクチャで順位が入れ替わる。** AVR では生 RGB565 が最安、
CH32V003 と ESP32 では RLE が最安。ESP32 では逆に 1bpp が高い。
**ツールは MCU を知らないと選べない。**

### ここで見つけた最適化

最初の実装は RLE の通し位置から `pos / w` で行を出していた。**CH32V003 は
rv32ec で除算命令が無く、AVR は 32 ビット除算がソフトウェアルーチンになる。**
行と列を持ち回る形に変えた結果:

| | |
| --- | ---: |
| **AVR** | **−248 / −270** |
| CH32V003 | +4 |
| ESP32 | +16 / +20 |

基準機が +4 と誤差の範囲で AVR が 27% 減るので採用した。

## 実装した形式

**形式タグは持たない。** ops ポインタが形式を表す（CellFont が「連続／疎」
「固定／可変」をポインタの null で表しているのと同じ）。形式タグを持って
実行時に分岐すると、使わない分岐までリンクされる。

| 形式 | 向き |
| --- | --- |
| `raw565` | 写真、色数の多い絵 |
| `rle565` | 色数が多くフラットな絵 |
| **`rlepal4`** | **UI アート。いちばん効く** |
| `bitmap1h` | 1bpp 横詰め |
| `bitmap1v` | 1bpp 縦詰め。ページ方式パネルのバッファ形式そのもの |

### 事前の有効化は要らない

**`#define` もマクロも不要。** 生成ヘッダが ops を指すだけで、使う形式の
デコーダだけがリンクされる。実測: **デコーダを 2 つ include して 1 つしか
使わない場合の増分は +0 B**（使うと +1,188 B）。

```cpp
static const TinyGFXImageRef myIconRef = {&myIcon, &tinygfxImageRlepal4Ops};
lcd.drawImage(&myIconRef, 10, 10);
```

### 1bpp の横詰めと縦詰めは 1 本のデコーダ

ビットの取り出し方が 1 行違うだけなので共有できる。**向きは呼び出し側で
定数**（生成ヘッダが形式を知っている）なので、コンパイラが特殊化して
使わない側を消す。

| | CH32V003 |
| --- | ---: |
| 横のみ | 400 |
| 縦のみ | 392 |
| **両方使う** | **504** |
| 別関数 2 本で両方 | 792（**288 B 損**） |

**「両対応にすると無駄」は起きない。**

## 透過

**実行時に見る**（形式と扱いが違う）。ops で分ける案も測ったが差が付か
なかった。CH32V003、`rlepal4`:

| | 透過なしのみ | 透過ありのみ | 両方 |
| --- | ---: | ---: | ---: |
| **実行時に見る**（採用） | 576 | 576 | **784** |
| ops で分ける | **544** | **560** | 796 |

**どの使い方でも 32 バイト以内。** 均一なら分割が僅かに得、混在なら実行時が
僅かに得。差が小さいのでデコーダが 1 本で済むほうを採った。

判定そのものの実費:

| 形式 | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| `raw565` | +32 | +66 | +44 |
| `rle565` | +24 | +54 | +36 |
| `rlepal4` | +32 | +50 | +36 |
| `bitmap1h` / `1v` | **+0** | +14 | **+0** |

**1bpp は 0 のビットが元から透過**なので、この仕組みを使わない。

## 縦詰めの速い経路

`TinyGFXPanelPaged::pushVBitmap()`。ページ境界に揃った縦詰めは、この
パネルのバッファそのものなのでバイト複写で貼れる。

| | CH32V003 |
| --- | ---: |
| **`pushVBitmap`** | **244** |
| 汎用 `drawImage` | 408 |

**見積もりは 24 B だったが実測は 10 倍。** ページ境界・回転・帯・パネル外の
判定と dirty の追跡が残るため。**縮むのは 164 B だけ**で、サイズでは
`rlepal4` に負けることがある。**速い経路の価値はサイズではなく速度**
（ラン展開ではなくバイト複写）。

揃っていないときは**描かずに `false` を返す。** 呼び手が汎用経路に落とせる
ほうが、黙って間違った位置に描くよりいい。仮想関数にしていないので、
カラーパネルは 1 バイトも払わない。

## 正式ツールへの申し送り

### 1. **一括で変換すること。1 枚ずつ最小を選ぶと損をする**

デコーダ代は**形式ごとに 1 回**であって画像ごとに 1 回ではない。1 枚ずつ
最小を選ぶと形式が散らばってデコーダを何本も積む。

実測（モノクロ 4 枚、2 値化後）:

| MCU | 1 枚ずつ | まとめて | 差 |
| --- | ---: | ---: | ---: |
| CH32V003 | 1,911 | **1,568** | **−343** |
| AVR | 2,449 | **1,852** | **−597** |
| ESP32 | 2,191 | **1,656** | **−535** |

形式は少ないので、**使う形式の組み合わせを総当たり**すればいい
（`tools/img2h.py` の `pick_set`）。

### 2. **MCU を指定させること**

上記のとおり順位が入れ替わる。デコーダ代の表を MCU 別に持つ。

### 3. **「データ + デコーダ」で比べること**

CellFont 仕様 §13.4 と同じ。データ量だけで選ぶと間違える。

### 4. **2 値化とディザリングが要る**

PNG の文字はアンチエイリアスされるので、そのままだと 128x64 の
スプラッシュが **54 色**になり 1bpp に落ちない。閾値の指定は必須で、
ディザリングの選択肢もほしい。

### 5. **1bpp の横／縦はデータ量が必ず同じ**

貼る先でしか決まらない。ツールに選ばせるなら別の入力が要る
（`tools/img2h.py` は `--prefer` と `--aligned`）。

## 決まっていないこと

- **一括変換での透過の指定。** 画像ごとに違う透過色があり得る。ファイル名の
  規約か、別ファイルの設定か
- **生 RGB565 の PROGMEM 経路。** いまは画素ごとにランをまとめて `fillRect`
  に投げている。`writePixels` の速い経路は RAM 前提なので、PROGMEM から窓へ
  直接流す経路を足すかどうか。**写真を扱うなら効くはずだが未計測**
- **ディザリングの方式**（Floyd-Steinberg / Bayer / なし）
