# 画像フォーマット

**描画器は実装済み**（`src/TinyGFX/Image.h`）。**変換ツールは実験用の最小
実装**（`tools/img2h.py`）で、正式なものはブラウザ + CLI で別途作る。
この文書はそこへの申し送りで、判断の根拠になった実測を全部載せてある。
**ツール側の設計**（他の GFX が受け取る形式、asset ツールとの切り分け、
名前）は [IMAGE_TOOL.ja.md](IMAGE_TOOL.ja.md)。
開発中の文書なので日本語のみ。

形式の仕様そのものは、CellFont と同じくツール側が持ち、TinyGFX はその
描画器の 1 実装になるのが筋だと思う。

## フォントとは結論が逆になる

CellFont では「圧縮しない」が正解だった。**画像では逆。**

| | データ量 | デコーダ |
| --- | ---: | ---: |
| フォント（数字 13 字） | **63 B** | 約 1,000 B |
| 画像（64x64 の UI アイコン） | **8,192 B**（生 RGB565） | 約 400 B |

**フォントはデコーダがデータの 16 倍、画像はデータがデコーダの 20 倍。**
償却の向きが逆なので、同じ判断にはならない。

## データ量（実画像を符号化して実測）

| 画像 | 寸法 | 色数 | 生 RGB565 | RLE(16bit) | **RLE+4bit パレット** | 1bpp |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| UI アイコン | 16x16 | 3 | 512 | 135 | **55** | — |
| UI アイコン | 32x32 | 3 | 2,048 | 357 | **157** | — |
| UI アイコン | 64x64 | 3 | 8,192 | 741 | **416** | — |
| モノクロ絵 | 32x32 | 2 | 2,048 | 399 | 149 | **132** |
| スプラッシュ | 128x64 | 2 | 16,384 | 1,263 | **816** | 1,028 |
| グラデーション | 64x64 | 2,560 | **8,192** | 7,680 | — | — |
| 疑似写真 | 64x64 | 3,218 | **8,192** | 12,285 | — | — |

**1. UI 的な絵では RLE + パレットが 20 分の 1。** 基準機 CH32V003 は
flash 16KB・base 5,892 B なので、**生 RGB565 の 64x64（8KB）は載らない。**
圧縮は「あると嬉しい」ではなく「無いと使えない」。

**2. 写真では RLE が生より 5 割大きい。** 形式は必ず生も持つ必要がある。

**3. 写真は基準機の対象外。** 64x64 の生で flash の半分。ESP32 では問題に
ならないので生の経路は残すが、基準機向けには勧めない。

**4. 非圧縮パレット（4bpp / 8bpp）は実装していない。** 測った全画像で
RLE+パレットに負けたため（64x64 で 2,054 対 416）。必要になったら測り直す。

## デコーダの実費（実測、`-Os`）

**`src/TinyGFX/Image.h` の本実装での値。** 使い捨ての実験実装より 60〜90 B
高い —— PROGMEM 経由のヘッダ読み、透過の判定、ops の間接呼び出しぶん。

| 形式 | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| `raw565` | 400 | **638** ←最安 | 492 |
| `rle565` | **387** ←最安 | 663 | **467** ←最安 |
| `rlepal4` | 395 | 679 | 483 |
| `bitmap1h` | 400 | 654 | 592 |
| `bitmap1v` | 392 | 690 | 592 |
| 1bpp 両方 | 504 | 864 | 696 |

**アーキテクチャで順位が入れ替わる。** AVR では生 RGB565 が最安、
CH32V003 と ESP32 では RLE が最安。ESP32 では逆に 1bpp が高い。
**ツールは MCU を知らないと選べない。**

### ここで見つけた最適化

最初の実装は RLE の通し位置から `pos / w` で行を出していた。**CH32V003 は
rv32ec で除算命令が無く、AVR は 32 ビット除算がソフトウェアルーチンになる。**
行と列を持ち回る形に変えた結果:

| | |
| --- | ---: |
| **AVR** | **−248 / −270** |
| CH32V003 | +4 |
| ESP32 | +16 / +20 |

基準機が +4 と誤差の範囲で AVR が 27% 減るので採用した。

## デコーダ代は実数で持たなくていい（2026-08-29 検証）

上の表を「MCU 別・形式別」に持つ設計にしていたが、**それが必要かを確かめたら
不要だった。**

### 実測プロファイル vs 固定値 400

同じ画像集合を、実測の表で選んだ場合と、**全形式を一律 400 B とみなして**
選んだ場合で比べた（共有デコーダの割引だけは 1.3 倍で残した）。

| 画像集合 | MCU | 実測プロファイルの選択 | 固定値 400 の選択 |
| --- | --- | --- | :-: |
| モノクロ 4 枚 | ch32v003 / avr / esp32 | `rlepal4` | **一致** |
| カラー 7 枚 | 同上 | `raw565, rle565, rlepal4` | **一致** |
| アイコンのみ | 同上 | `rlepal4` | **一致** |

**9 ケースすべてで選択が同じ。**

### 感度も低い

固定値を振っても答えがほとんど動かない。

| 集合 | 0 | 50 | 100 | 200 | 400 | 800 | 1600 | 4000 |
| --- | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| モノクロ 4 枚 | 2 | 2 | **1** | 1 | 1 | 1 | 1 | 1 |
| カラー 7 枚 | 4 | **3** | 3 | 3 | 3 | 3 | **2** | 2 |
| 小アイコン 2 枚 | 1 | 1 | 1 | 1 | 1 | 1 | 1 | 1 |

（数字は選ばれた形式の数）**100〜800 の間ならどこでも同じ答え。**
実測値（387〜690）はその真ん中にある。

### なぜそうなるか

**同じ MCU の中では形式間の差が小さい。**

| MCU | 形式間の幅 |
| --- | --- |
| CH32V003 | 387〜400（**3%**） |
| AVR | 638〜690（8%） |
| ESP32 | 467〜592（27%） |

対して**データ量の差は桁で違う**（64x64 の UI アイコンで生 8,192 対
RLE+パレット 416）。デコーダの数十バイトの違いが決定をひっくり返す余地がない。

### ツール側への申し送り（改訂）

**MCU 別・形式別の表は要らない。**

| 要る | 要らない |
| --- | --- |
| **1 形式あたりのおおよその代金**（1 つの数字。400 前後） | 形式ごとの表 |
| **共有デコーダの割引**（1bpp 横+縦 = 1.3 倍程度） | MCU ごとの表 |
| `--decoder-cost <N>` での上書き | 実測値への追随 |

**これで「TinyGFX の計測スクリプトから JSON を生成する」という宿題も消える** ——
転記すべき表が無くなるので。

**ただし 2 点は残る。**

1. **桁が変わったら見直す。** いま 400 前後なのは「デコーダがランを `fillRect`
   に投げるだけ」だから。デコーダの作りが変われば桁が動きうる
2. **`aligned-vblit` は別扱いのまま。** 244 対 408 で、これは形式選択ではなく
   **サイズか速度かの選択**。平均に混ぜてはいけない

上の形式別・MCU 別の表は**根拠として残す**が、ツールが持つ必要はない。

## 実装した形式

**形式タグは持たない。** ops ポインタが形式を表す（CellFont が「連続／疎」
「固定／可変」をポインタの null で表しているのと同じ）。形式タグを持って
実行時に分岐すると、使わない分岐までリンクされる。

| 形式 | 向き |
| --- | --- |
| `raw565` | 写真、色数の多い絵 |
| `rle565` | 色数が多くフラットな絵 |
| **`rlepal4`** | **UI アート。いちばん効く** |
| `bitmap1h` | 1bpp 横詰め |
| `bitmap1v` | 1bpp 縦詰め。ページ方式パネルのバッファ形式そのもの |

### 事前の有効化は要らない

**`#define` もマクロも不要。** 生成ヘッダが ops を指すだけで、使う形式の
デコーダだけがリンクされる。実測: **デコーダを 2 つ include して 1 つしか
使わない場合の増分は +0 B**（使うと +1,188 B）。

```cpp
static const TinyGFXImageRef myIconRef = {&myIcon, &tinygfxImageRlepal4Ops};
lcd.drawImage(&myIconRef, 10, 10);
```

### 1bpp の横詰めと縦詰めは 1 本のデコーダ

ビットの取り出し方が 1 行違うだけなので共有できる。**向きは呼び出し側で
定数**（生成ヘッダが形式を知っている）なので、コンパイラが特殊化して
使わない側を消す。

| | CH32V003 |
| --- | ---: |
| 横のみ | 400 |
| 縦のみ | 392 |
| **両方使う** | **504** |
| 別関数 2 本で両方 | 792（**288 B 損**） |

**「両対応にすると無駄」は起きない。**

## 透過

**実行時に見る**（形式と扱いが違う）。ops で分ける案も測ったが差が付か
なかった。CH32V003、`rlepal4`:

| | 透過なしのみ | 透過ありのみ | 両方 |
| --- | ---: | ---: | ---: |
| **実行時に見る**（採用） | 576 | 576 | **784** |
| ops で分ける | **544** | **560** | 796 |

**どの使い方でも 32 バイト以内。** 均一なら分割が僅かに得、混在なら実行時が
僅かに得。差が小さいのでデコーダが 1 本で済むほうを採った。

判定そのものの実費:

| 形式 | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| `raw565` | +32 | +66 | +44 |
| `rle565` | +24 | +54 | +36 |
| `rlepal4` | +32 | +50 | +36 |
| `bitmap1h` / `1v` | **+0** | +14 | **+0** |

**1bpp は 0 のビットが元から透過**なので、この仕組みを使わない。

## `raw565` だけは窓経路（2026-08-29）

**RLE 系と raw565 では、正しい流し方が逆になる。**

他の復号器は「連（ラン）」を `fillRect` に渡す。連が長いことを形式が保証して
いるので、それが正しい。**raw565 は逆を保証している** —— 写真の連長は 1 である。

連ごとに `fillRect` を呼ぶと、**画素ごとに窓を開く**ことになる。
窓 1 つが CASET + RASET + RAMWR で 11 バイト、画素が 2 バイト。

**実測**（32x32 の雑音、`TinyGFXBusCapture` のコマンド数）:

| | コマンド数 | 1 画素あたり |
| --- | ---: | ---: |
| 連ごとに `fillRect`（元） | **3,072** | 13 B |
| 1 行 1 窓（現在） | **96** | 2.3 B |

2,048 バイトの画像を送るのに 13,312 バイト流していた。

`drawRaw565` は行ごとに窓を 1 つ開いて流し込む。透過色があるときは
**不透明な区間ごと**に窓を開く —— 窓は開いたら埋め切る必要があるので、
途中を飛ばすと後ろが全部ずれる。

窓経路はクリップしないので、**クリップは復号器側で行う**
（`g.clipX0()` などを公開した。[API.ja.md](API.ja.md)）。

**費用**（写真 1 枚を描くだけのスケッチ全体で比較）:

| | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| フラッシュ | **−32** | +118 | **−108** |

AVR だけ増えるのは、クリップ計算が 32bit だから。**`clipX0 - x` は
x = -32768 で 32768 になり、int16_t に収まらない。**
16bit で正しく書く版も測ったが、基準機で +116 / AVR で −146 と逆転したので、
規則どおり基準機を採った（[DECISIONS.ja.md](DECISIONS.ja.md) D27）。

`tests/image_fmt/` が固定しているもの:

- **窓の数 == 行数。** 元の実装に戻すと落ちる（窓 1,024 個）
- **極端な座標で 1 画素も送らないこと。** 桁溢れさせた版では
  **1,050,624 画素**（画像データの手前を読んでいた）

## 縦詰めの速い経路

`TinyGFXDriverPaged::pushVBitmap()`。ページ境界に揃った縦詰めは、この
パネルのバッファそのものなのでバイト複写で貼れる。

| | CH32V003 |
| --- | ---: |
| **`pushVBitmap`** | **244** |
| 汎用 `drawImage` | 408 |

**見積もりは 24 B だったが実測は 10 倍。** ページ境界・回転・帯・パネル外の
判定と dirty の追跡が残るため。**縮むのは 164 B だけ**で、サイズでは
`rlepal4` に負けることがある。**速い経路の価値はサイズではなく速度**
（ラン展開ではなくバイト複写）。

揃っていないときは**描かずに `false` を返す。** 呼び手が汎用経路に落とせる
ほうが、黙って間違った位置に描くよりいい。仮想関数にしていないので、
カラーパネルは 1 バイトも払わない。

## 正式ツールへの申し送り

### 1. **一括で変換すること。1 枚ずつ最小を選ぶと損をする**

デコーダ代は**形式ごとに 1 回**であって画像ごとに 1 回ではない。1 枚ずつ
最小を選ぶと形式が散らばってデコーダを何本も積む。

実測（モノクロ 4 枚、2 値化後）:

| MCU | 1 枚ずつ | まとめて | 差 |
| --- | ---: | ---: | ---: |
| CH32V003 | 1,911 | **1,568** | **−343** |
| AVR | 2,449 | **1,852** | **−597** |
| ESP32 | 2,191 | **1,656** | **−535** |

形式は少ないので、**使う形式の組み合わせを総当たり**すればいい
（`tools/img2h.py` の `pick_set`）。

> **2026-08-31: 本番ツールで動くようになった。** フォルダを渡すと候補が全部
> 出て、集合として選ばれる。rle565 でしか表せない画像を 1 枚足すと、他の 3 枚が
> rlepal4 から rle565 に移る —— 3 本目のデコーダ 400 B より、少し大きい符号化の
> ほうが安いため。**これがこの節が言いたかったことそのもの。**

### 2. **MCU 別の表は要らない。1 つの数字でいい**

**当初は「MCU を指定させること」と書いていたが、検証して取り下げた。**
上の「デコーダ代は実数で持たなくていい」を参照。9 ケースすべてで、
実測の表と固定値 400 が同じ選択になった。

ツールが持つべきなのは:

- **1 形式あたりのおおよその代金**（1 つの数字。100〜800 ならどこでも同じ答え）
- **共有デコーダの割引**（1bpp の横+縦を両方使うときだけ 1.3 倍程度）
- **`--decoder-cost <N>` での上書き**

MCU 別・形式別の実測表は**根拠として残す**が、ツールに持たせる必要はない。

### 3. **「データ + デコーダ」で比べること**

CellFont 仕様 §13.4 と同じ。データ量だけで選ぶと間違える。

### 4. **2 値化とディザリングが要る**

PNG の文字はアンチエイリアスされるので、そのままだと 128x64 の
スプラッシュが **54 色**になり 1bpp に落ちない。閾値の指定は必須で、
ディザリングの選択肢もほしい。

### 5. **1bpp の横／縦は、寸法によって同点にも桁違いにもなる**

**当初「データ量が必ず同じ」と書いていたが誤り**（2026-08-29 訂正）。
試験画像が 16x16 / 32x32 / 128x64 と**すべて 8 の倍数**だったため同点しか
見ておらず、そこから一般化していた。

| | |
| --- | --- |
| 横詰め | `ceil(width / 8) * height` |
| 縦詰め | `width * ceil(height / 8)` |

**両辺が 8 の倍数のときだけ同量。** 細長い画像では桁で違う（実測）:

| 寸法 | 横詰め | 縦詰め | |
| --- | ---: | ---: | --- |
| 1x64 | 68 | **12** | 縦が 56 B 小さい |
| 64x1 | **12** | 68 | 横が 56 B 小さい |
| 20x12 | **40** | 44 | |
| 32x32 | 132 | 132 | 同点 |

つまり**多くの場合はデータ量で決まる。** 同点になったときだけ貼り先で
決める必要があり、そこにツールへの入力が要る（`tools/img2h.py` は
`--prefer` と `--aligned`）。

- ページ方式パネル（SSD1306 / SH1106）と `aligned-vblit` → 縦詰め
- それ以外 → 横詰め

## 検証の受け皿（`tests/image_oracle/`）

変換ツールの出力を検証する仕組みを用意してある。GfxImageToolJs 仕様書 §15.2 が
指定するオラクル。

`images/` に PNG を置いて `images/.imagesconfig` に書き、`regen.py` を 1 回
走らせると、比較の両側が同時に出る —— TinyGFX がコンパイルする `images.h` と、
突き合わせる `expected/*.png`。**画像を足すのにコードは書かない。**

構成は**ツールのプロジェクト構成そのもの**にしてある（`images/` の隣に
`images.h`）。利用者のスケッチと同じ並びなので、**検査している include が
利用者の書く include と同じ**になる。

**期待画像は変換側からもらうこと。** 自作の encode と decode の往復では、
両者が同じ勘違いをしていたら一致してしまう。`expected/` は元画像ではなく、
ツールの `--preview` が出した**減色・2 値化・ディザを通した後の画素**。

**2026-08-31、本番 CLI の出力で 5 デコーダ全部・11 枚が一致した。**
そのうち 2 枚は**この方法でなければ検証できない** —— ディザ（127 階調 → 2、
誤差拡散の実装依存）と減色（2,304 色 → 16、どの色を残すかの選択）。
3 枚は**寸法が 8 の倍数でない** —— 31x17 は 1 行が 3 バイトと 7 ビット、13x13 は
1 ページと 5 行。**行末の端数バイトで次の行に踏み込むデコーダなら、ここで落ちる。**
**`gradData` の 1 バイトを反転すると 8/4096 画素、`quantPalette` の 1 色を
ずらすと 128/2304 画素の差を検出する。**

**透過を持つ絵はマゼンタの上に描く。** 黒の上では、透過画素を黒で塗るデコーダと
そのまま残すデコーダが同じ絵になってしまい、何も検出できない。`hasTransparent`
を 1 → 0 にすると 268/576 画素の差が出る。ここで **フォルダ変換だと透過が既定で
落ちる**ことが見つかった（[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E11）。

### ここで見つけた穴 — パレット索引の範囲検査

検証中に、**壊れたヘッダがパレットの範囲外を読む**ことが分かった。
`rlepal4` の索引は 4 ビット（0..15）だが、パレットは 3 色しか無いことがある。
`pal[15]` がそのまま通っていた（たまたま 0 が読めて絵が一致し、破壊が
検出されないという形で露見した）。

**索引を `paletteCount` で丸めるようにした。実費 16 B**（395 → 411、CH32V003）。
手で書いたデータや壊れたヘッダでも配列の外を読まない。

## 1 枚の画像の大きさの上限

**形式によって違う。** `CellImage.dataLen` は `uint16_t` だが、**読むデコーダは
5 つのうち 2 つだけ**なので、上限が掛かるのもその 2 つだけ。

| 形式 | データ長の上限 | 実効的な上限 |
| --- | --- | --- |
| `raw565` | **無し** | 幅・高さが `uint16_t`。実際にはフラッシュ容量 |
| `bitmap1h` / `bitmap1v` | **無し** | 同上 |
| `rle565` / `rlepal4` | **65,535 バイト** | RLE の終端判定に `dataLen` を使うため |

`Image.h` の `d.len` 参照は `drawRle565` と `drawRlePal4` の 2 箇所だけ。
**raw565 と 1bpp は寸法だけで走査する。**

### 実測して固定してある

`tests/image_fmt/` が、**同じバイト列を `dataLen` 0 で描いて**確かめる。

| | dataLen 0 での差 |
| --- | ---: |
| `raw565` | **0 画素** |
| `bitmap1h` | **0 画素** |
| `rle565` | **616 画素** |

3 行目が要る。**rle565 まで 0 画素なら、上の 2 つは「誰も dataLen を読んで
いない」だけで何も言えていない**ことになるので。

### なぜこれが効くか

240x240 の raw565 は 115,200 バイト。**TinyGFX が preset を同梱している
ST7789 の全画面寸法**で、ESP32 なら普通に載る。変換ツールが当初これを
一括で弾いていて、**看板パネルの全画面絵が作れなかった**
（[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E18。修正済み）。

## バンドルヘッダの索引配列

**2026-08-31。** GfxImageToolJs はプロジェクトの全画像を 1 本のヘッダにまとめ、
あわせて索引配列を出す —— `images_file_count` / `_names` / `_data` / `_sizes` /
`_widths` / `_heights` / `_formats`、そして TinyGFX 向けに **`images_file_refs`**
（`TinyGFXImageRef*` の配列。そのまま `drawImage` に渡せる）。

### 使わないものは 0 バイト

11 枚のバンドルを include して **1 枚だけ描く**ときの実測:

| | CH32V003 | AVR |
| --- | ---: | ---: |
| 1 枚だけのバンドル | 8,240 | 4,132 |
| 11 枚のバンドル、描くのは 1 枚 | **8,240** | **4,132** |
| `images_file_refs[3]`（定数）で描く | **8,240** | **4,132** |
| `images_file_names[0]` を渡す | +8 | +8 |

**残り 10 枚も索引配列も 1 バイトも残らない。** 定数添字は畳まれるので、
`images_file_refs[3]` も直接参照と同じ。`tests/linkprune/` が
`photoData` などが**シンボル表に出てこないこと**で見張っている。

### ただし、実行時の添字を書いた瞬間に全部載る

| | 1 枚 | 実行時添字 | 差 |
| --- | ---: | ---: | ---: |
| CH32V003 | 8,240 | 14,660 | **+6,420（16,384 の 39%）** |
| AVR | 4,132 | 11,342 | +7,210 |
| ESP32 | 259,940 | 266,520 | +6,580 |

```cpp
lcd.drawImage(images_file_refs[n], 0, 0);   // n がコンパイル時に決まらない
```

**欠陥ではない** —— どれが選ばれるか分からない以上、全部残すしかない。
**「無料」と「フラッシュの 3 分の 1」の境目がここにある**というだけの話で、
リファレンス基板では効く。`tests/linkprune/` に両方向とも入れてある。

## 決まっていないこと

- **一括変換での透過の指定。** 画像ごとに違う透過色があり得る。ファイル名の
  規約か、別ファイルの設定か
- **生 RGB565 の PROGMEM 経路。** いまは画素ごとにランをまとめて `fillRect`
  に投げている。`writePixels` の速い経路は RAM 前提なので、PROGMEM から窓へ
  直接流す経路を足すかどうか。**写真を扱うなら効くはずだが未計測**
- **ディザリングの方式**（Floyd-Steinberg / Bayer / なし）—— ツール側は 4 種類とも
  実装済み。TinyGFX として既定をどれにするかは未決
