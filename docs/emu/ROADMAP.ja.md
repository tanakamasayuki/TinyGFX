# 計画 — 課題・既存資産・段階・未決

内部の記録。日本語のみ。概念は [CONCEPTS.ja.md](CONCEPTS.ja.md)。

## 1. いまの課題（2026-09-03 実測。= 既存が覆っていない証拠）

| # | 課題 | 証拠 |
| --- | --- | --- |
| P1 | フックが 1 スロットで観測と応答が排他 | Wire / SPI とも各 1 個。TinyM5Board はロガーの中から模型を呼んで手動連結 |
| P2 | 模型が再利用できない | 同じ SSD1306 が 4 テストに計 376 行 |
| P3 | 模型が表示範囲しか持たない | SH1106 の 2 列オフセットが絵に写らない |
| P4 | 標準の読み出し口が無い | 撮れるのは模型を書いたテストだけ（17 スケッチ 63 枚は全部自前） |
| P5 | 宛先の振り分けが無い | (bus, addr) → デバイスは各自書く |
| P6 | 応答方向が未使用 | `readId` / `readPixels` は実機でしか検査されない |
| P7 | イベントの正準形が無い | GPIO / Wire / SPI の口がばらばら。順序は各テストが文字列整形で自作 |
| P8 | **刺激が存在しない** | `setPinValue` があるだけ。時刻つき台本・UART 受信・割り込み発火は無い |
| P9 | **時間が実時間** | `millis()` = steady_clock、`delay(100)` は実際に眠る |
| P10 | 障害注入が無い | NACK・短読を作る口が無い |
| P11 | すべてが特定ホストのフック型に直結 | 環境を替えると模型も整形も golden も書き直し |

## 2. 既存資産の位置づけ —— 全部「合わせる側」

| 既存 | 生き残るもの | 作り直すもの |
| --- | --- | --- |
| host-arduino-core | Arduino API の実装本体 | フック層・時計。環境の 1 実装として E1〜E4 を実装 |
| TinyGFX のテスト | golden の PPM（受け入れ条件そのもの） | 4 つの自前モデル（計 376 行）→ カタログの模型へ |
| TinyM5Board | `RegFile` の考え方・golden trace | トレース整形・手動連結 → 契約のリスナーへ |
| I2CDeviceDB | **データ柱という役割**・capture / profile / scenario という区分 | 形式は契約側が決まってから合わせ直す。リポジトリごと作り直しもあり得る |

## 3. 段階と受け入れ条件

| 段階 | 系統 | 作るもの | 受け入れ条件 |
| --- | --- | --- | --- |
| 1 | B+S | **契約**（イベント・リスナー・時計。エンドポイント・刺激は宣言のみ）＋**再生環境** | 記録イベント列の再生でリスナー多重・golden 比較が動く。**環境ゼロ・模型ゼロでログ解析が成立**（B の独立）。**関数一覧 v0 の凍結** |
| 2 | S | **Arduino ポート第 1 号** = host-arduino-core のバインディング（E1〜E4・仮想時計） | 既存リポジトリのテストが新しい口で通り、`delay` を含むテストが**速くなる** |
| 3 | A | I2C バス＋register-map 解釈器＋文字トレース読み出し | TinyM5Board 相当の golden が新経路で一致 |
| 4 | A | command 型解釈器（表示）＋PPM 読み出し | **TinyGFX の既存 PPM が 1 画素も変わらない**。376 行が消える。SH1106 の 2 列が RAM の絵に写る |
| 5 | A | SPI 枠組み＋応答方向 | `readId` / `readPixels` がホストで検査できる（初） |
| 6 | A | 刺激スケジューラ＋レベル型・ストリーム型 | ボタン台本と UART 台本のテストが立つ |
| 7 | A | 障害注入（データ駆動のデコレータ） | 検出分岐の両側・NACK・短読が台本で書ける |
| 8 | A+B | scenario ランナー＋データ柱との形式合意 | 同じ scenario が模型に対して通る。capture 形式 = イベント直列化形式 |
| 9 | A+B | 実機系（スレイブポート = A、実機タップ = B） | 別基板の模型に実機がアクセスし、段階 8 と同じ scenario が通る |

**段階 1 を「契約＋再生」にしたのが要点。** 最小の環境が再生であることで、
契約が最初から host 専用でないことを強制される。

## 4. 未決

- **名前とリポジトリ構成。** 契約＋核で 1 リポジトリ、模型カタログの同居/分離
- **イベントの表現と直列化形式。** データ柱の capture 形式と**同時に**決める
- **ビジーループ時の時計の進め方**（`while (millis() < x)` の粒度）
- **仮想時計の既定**を全テスト仮想にするか opt-in にするか
- **波形ドメインの実装時期。** 語彙と直列化形式には初日から席。実装は最初に
  要るデバイスが現れた段階（サーボは解釈層のパルス幅だけで足りる見込み）
- **割り込みの細目。** ネスト・優先度。最初は「ネスト無し・FIFO」
- **共有 INT 線**（wired-AND）の合成。当面 1 線 1 駆動者
- **UART の Serial（USB コンソール）の扱い** —— テスト報告と刺激対象を分ける線
- **ESP-IDF ポートの時期。** 語彙の中立性検査（CONCEPTS §4.2）はイベントを
  足すたびに紙上で行う —— ポートが無い間に語彙が Arduino に寄るのが
  いちばん静かな腐り方
- **固有名の掃除。** 分冊は具体のリポジトリ名を説明の足場に使っている。
  凍結（段階 1）で、正式定義からは役割名に置き換える（README の注記）。
  例示として残すのは可 —— 消すのは「定義が固有名に依存している」形だけ
- **プローブの中身。** 役割は決めた（CONCEPTS §4.10 —— E1 だけの環境、出力は
  共通形式）。API プローブと線プローブのどちらをどのデバイスに使うかは
  デバイスの仕様次第で、最初の実対象が決まってから
- **pytest 側の共有**（HTML レポート等）をプラグインに切り出す時期
