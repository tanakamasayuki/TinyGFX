# 計画 — 決定台帳・段階・未決

内部の記録。日本語のみ。2026-09-03 改訂。

## 1. 決定台帳

✔ = 決定（議論で合意済み・各冊に反映）、△ = 提案（未承認）、？ = 未決。

### 時間と進行

| | 決定 |
| --- | --- |
| ✔ | 主時計は µs の単調カウンタ 1 本。**タイミングの検証はしない。順序と進行の座標としてだけ持つ** |
| ✔ | tick = 可変の刻み（既定はフレームワーク中間層の規約: Arduino 1ms / ESP-IDF 10ms） |
| ✔ | loop 1 周 = 1 tick。**すべての待ちが主時計を進め、tick 境界を越えるときだけ tick 処理が走る**（`delay` は `delayMicroseconds` の糖衣。未来の予定表を持つ者は居ない） |
| ✔ | tick 内の順序: **①進行役 ②保留 ISR ③アプリ ④歩進**（試験が先 —— setup フックとの対称） |
| ✔ | **tick コンテキスト（進行役・ISR）で待ち API 禁止**。違反は診断イベント + no-op（「ISR で delay 禁止」と同型） |
| ✔ | 実時間・倍率は opt-in の別モード（非決定的と明示） |
| ？ | `micros()` だけ見張る生ビジーウェイトの扱い（`yield()` が時計口を通るので一部緩和。残りは境界として文書化 + 将来の読み取り微小加算 opt-in） |

### 進行役と注入

| | 決定 |
| --- | --- |
| ✔ | 台本（時刻つき宣言データ）は**廃案**。世界を動かすのは**進行役 = テスト側のもう 1 本の loop 風関数**。毎 tick 呼ばれ、単発注入だけを行う |
| ✔ | 進行役は契約に明示登録 1 本。Arduino では weak 関数の糖衣（`serialEvent()` 方式） |
| ✔ | setup 対応フックも同様（tick 設定・attach・仕込み・進行役登録の置き場） |
| ✔ | 注入先は 4 つ: 線・物理量チャネル・通知チャネル・UART 受信。**すべて契約経由でイベントに写る**（出どころタグつき。golden はフィルタで除外 —— 「注入したのに反応しない」が証拠に残る） |
| ✔ | 割り込みは経路ではなく帰結。同一 tick 内の連続注入で縁が立つ。発火点は注入の切れ目と tick 境界。最初はネスト無し・FIFO |
| ？ | 進行役からのバス操作の可否（タグ付き許可案） |

### デバイス

| | 決定 |
| --- | --- |
| ✔ | **完全受動**（自前タイマー無し —— 再生・実機スレイブで成立しないため）。呼ばれたときだけ動く |
| ✔ | 受け口チャネル 2 種: **物理量**（値つき: 温度）と**通知**（値なし: 「NMEA を出せ」）。周期などの知識はデバイスが**データとして公開**し、回すのは進行役 |
| ✔ | busy 系は「呼ばれたとき now を見る」の遅延評価で書く（now は読める） |
| ✔ | 検分: ハンドル直の const は無記録。**契約経由の `dump`（文字列・書式自由・改行禁止）は記録**。初期状態は postSetup での dump |
| ✔ | デバイスは世界の線番号もポート番号も知らない（0 始まりの役割番号だけ。束縛は attach が持つ） |

### 記録

| | 決定 |
| --- | --- |
| ✔ | **1 イベント 1 行**（改行禁止。dump 文字列も同じ縛り） |
| ✔ | イベント列 = トレース = キャプチャ = golden の 1 形式（直列化可能・連番・時刻・文脈タグ・出どころタグ） |
| ？ | 直列化の書式そのもの（テキスト行の中身）。データ柱の capture 形式と同時に決める |

### 環境

| | 決定 |
| --- | --- |
| ✔ | **ホスト実装は Protocol を知らない。** 汎用拡張点（E22 = 1.7.0）: ライフサイクル 4 点・時計口（now + wait スライス）・`Serial1/2`・既存タップ続投 |
| ✔ | 「onTick と待ち上書きは同一機構」——待ちスライスの上書き先が tick 処理そのもの |
| ✔ | 取り込み（runtimePoll）は postLoop の後 = 外部入力は次の周に属す |
| ✔ | `Serial`（コンソール）でデバイスと喋るアプリは**境界**（必要になったら切り離し opt-in を追加依頼） |
| ✔ | ハングの条件は「期限の時計と待ちの時計の不一致」（steady_clock の grep は必要条件ですらない）—— 環境適合の検査観点 |

## 2. 配布とデバイスの出どころ（△ 提案）

| △ | 提案 |
| --- | --- |
| △ | **本体は Arduino ライブラリとして登録・配布する。** 理由: 利用側（各リポジトリのテスト・アプリ作者）の道具立てが arduino-cli + sketch.yaml で統一されている／実機スレイブ（U16）でも同じ形で入る／核は純粋 C++ のままなので、ESP-IDF ポートは同じ核を component で包めばよい |
| △ | **最初は 1 ライブラリ**（契約 + Arduino 中間層 + 汎用解釈器 + 少数の標準デバイス）。分割は「両側が独立に変わる」ようになってから（継ぎ目の基準と同じ） |
| △ | **デバイスの出どころは 3 つ**: ①自作（DEVICE.ja.md のキット。register-map 型は表だけ） ②**知識の持ち主のライブラリから**（表示の模型は TinyGFX 側が育てる —— 「模型はそのプロトコルを知っているライブラリの持ち物」は host コア 1.5.0 の設計原則でもある） ③**データ柱からの生成**（profile → register-map 模型） |
| △ | 模型はまず利用リポジトリのテスト共通ライブラリで育て、2 つ目の利用者が現れたらカタログへ昇格 |

## 3. 段階

| 段階 | 状態 | 中身 |
| --- | --- | --- |
| 1 | **済** | ホストの汎用拡張点（E22 → 1.7.0）。tick モデルの実証 `accept_emu_tick` 込み |
| 2 | **次** | **Arduino 中間層の最小実装**: 契約 ctx・イベント列とリスナー・attach（I2C）・進行役・仮想時計。受け入れ = TinyM5Board 相当のトレース golden が新経路で一致 |
| 3 | | register-map 解釈器 + dump + scenario の最小形（データ柱と形式合意） |
| 4 | | command 型解釈器（表示）+ PPM 読み出し。**TinyGFX の既存 PPM が 1 画素も変わらない**。376 行が消える |
| 5 | | SPI 枠組み + 応答（`readId`/`readPixels` をホストで検査） |
| 6 | | 障害注入デコレータ・UART デバイス（GPS/モデム） |
| 7 | | 実機系（スレイブポート・実機タップ = プローブ） |

## 4. 未決（台帳の ？ 以外）

- **命名の一括決定**（ライブラリ名・接頭辞・進行役/フックの関数名。`emu` は不採用見込み）
- 契約の関数一覧の凍結（v0 案は各冊に分散。凍結時に 1 枚へ）
- 共有 INT 線（wired-AND）の合成
- 波形ドメインの実装時期（語彙には席あり）
- ESP-IDF ポートの時期（語彙の中立性検査はイベント追加のたび紙上で）
- pytest 側の共有（HTML レポート等）の切り出し時期
- 固有名の掃除（凍結時に役割名へ）
