# 概念 — あるべき姿・ユースケース・概念モデル・規約

内部の記録。日本語のみ。**全読者共通の 1 冊。** 役割別の義務は
[ENVIRONMENT](ENVIRONMENT.ja.md) / [DEVICE](DEVICE.ja.md) / [USER](USER.ja.md)。

## 1. あるべき姿

**組込みアプリケーションを、書かれたフレームワークのまま無改造で、実機なしで・
決定的に・観察可能な形で走らせ、実機とデータで裏を取れる基盤。**
Arduino スケッチも ESP-IDF アプリも同じ基盤に乗る。テストはこう書ける:

```
用意する   デバイスの模型を置く。刺激（ボタン押下・センサ値の変化・受信データ）を
          時刻つきで仕込む
走らせる   アプリをそのまま実行する（アプリもライブラリも一切改造しない）
確かめる   起きたこと（イベント列）と、残ったもの（画面・レジスタ・状態）を
          ゴールデンや scenario と突き合わせる
```

基盤の動詞は 4 つ。**この 4 つが直交していることが設計の芯。**

| 動詞 | 何か | 例 |
| --- | --- | --- |
| **観測** | 起きたことを 1 本の順序つき列として見る | トレース・golden・カウンタ |
| **応答** | スケッチの相手をする | PMIC が ID を返す、表示が画素を受ける |
| **刺激** | スケッチへ入力を与える | t=100ms でボタン押下、センサ値の傾斜、NMEA の着信 |
| **時計** | 上の 3 つを 1 本の決定的な時間軸に載せる | `delay(100)` は仮想で進む。刺激は時刻で発火する |

### 1.1 要件は 2 系統 + 共通基盤

| 系統 | 動詞 | 単独で成立する使い方 |
| --- | --- | --- |
| **A. エミュレーション** | 応答・刺激 | スケッチの相手をする世界を作る。ログを一切取らなくても「動く」 |
| **B. ログ解析** | 観測 | 起きたことを調べる。**模型ゼロでも成立** —— 実機キャプチャの解析、golden 比較 |
| **S. 共通基盤** | 時計・環境 | 両系統が同じ時間軸・同じ環境の上に乗る |

独立の証拠: TinyM5Board のトレース golden はほぼ B だけで書け、I2CDeviceDB の
キャプチャ解析は A が 1 行も無くても成立する。**環境への要求は 1 枚の票に
まとめて出す**（[ENVIRONMENT.ja.md](ENVIRONMENT.ja.md)）—— 同じ場所に開ける
穴を 2 度頼まないため。

境界の規約: **B はイベント列（直列化形式）だけを読む。模型の内部を覗かない。**
これを守る限り A と B は別々に版を上げられる（§6-10）。

## 2. アクター —— この仕様の登場者一覧（正本）

アクターは 2 水準に分ける。**「役者」= 人、「登場物」= 実行時の構成要素。**
役割別の 3 冊に出てくるアクターは、すべてこの表の抜粋。

### 2.1 役者（人）

| 役者 | 立場 | 読む文書 |
| --- | --- | --- |
| **環境の実装者** | 契約の上側を実装する | [ENVIRONMENT](ENVIRONMENT.ja.md) |
| **デバイスの作者・生成器** | 契約の下側を実装する | [DEVICE](DEVICE.ja.md) |
| **ライブラリ作者** | 利用者。ドライバの回帰・分岐網羅・golden | [USER](USER.ja.md) |
| **アプリ作者** | 利用者。**製品スケッチを丸ごとホストで** —— 最大の空白（いまの資産は全部ライブラリ作者向け） | [USER](USER.ja.md) |
| **チップデータの整備者** | データ柱。キャプチャ → profile → 模型と scenario | データ柱側の文書（未着手） |
| **実機での検証者** | 同じ資産を実機との突き合わせに使う | USER + プローブ |
| **CI** | 全部をヘッドレス・決定的・並列で回す | USER |
| **教育・解析** | 再現可能なトレースを教材・証拠に | USER（観測だけで足りる） |

### 2.2 登場物（実行時の構成要素）

| 登場物 | 側 | 能動か | 何をするか |
| --- | --- | --- | --- |
| **アプリ** | MCU 側 | 能動 | **被験体。** 無改造でフレームワークの API を呼ぶ |
| **環境** | MCU 側 | 能動 | アプリの操作を契約へ写す（タップ・委譲・注入・時計 = E1〜E4） |
| **契約（ランタイム）** | 中立 | **場**（行為しない） | イベント列・エンドポイント表・刺激スケジューラ・時計の置き場 |
| **デバイス** | デバイス側 | 受動 | チップの模型。呼ばれて答え、役割番号で線を引く |
| **世界** | コネクタの外 | 能動（**台本 = データが動かす**） | 温度・光・指。物理面を駆動する。実験室なら恒温槽やテスターの指 |
| **テストコード** | 試験者側 | **走行前後のみ** | 確保・仕込み・attach・台本の登録（前）／検分・golden 照合（後） |
| **リスナー** | 試験者側 | 受動 | 観測の消費者（ログ・golden・カウンタ）。**応答を変えられない** |
| **適合キット** | 試験者側 | 開発時のみ | 環境と利用者の代役を演じ、契約の順守を検査する |

### 2.3 派生形と部品

主要 8 つの特殊形。**新しい種類のアクターではない**（規約 2 —— 列挙を作らない
ための整理）。

| 親 | 派生形 |
| --- | --- |
| 環境 | host 実装（Arduino×host が第 1 号）／**再生環境**（記録を流す）／**プローブ**（E1 だけ・実機から捕る）／**スレイブポート**（実機でデバイス側に立つ） |
| デバイス | **デコレータ**（障害注入 —— デバイスを包むデバイス）／カタログの模型／profile から生成された register-map 模型 |
| （部品） | 枠組み・解釈器（デバイスの中身）、**持ち上げ器・引き下げ器**（線層⇄解釈層の変換。§4.3） |

### 2.4 データ（行為しない。登場物が使い、作る）

| データ | 使う者 → 向き | 中身 |
| --- | --- | --- |
| **台本（刺激）** | テストコード → 世界 | 時刻つきの世界の変化 |
| **scenario（適合）** | 適合キット → バス面 | バス操作と期待応答の列 |
| **capture（記録）** | プローブ → 再生環境・データ柱 | 実機産のイベント列 |
| **golden（期待）** | リスナーの出力 ↔ テストコード | 文字トレース・PPM |
| **profile** | データ柱 → 生成器 | register-map の定義 |

台本・scenario・capture・golden は**すべてイベント直列化形式か、そこへ写せる
形式**にする（§4.2 —— 道具を 1 セットで済ませるため）。

## 4. 概念モデル

### 4.0 作っているのは Protocol —— 使い方は別の話

成果物は**契約（Protocol）そのもの + 適合キット**。両側に実装者が居る仕様として
振る舞う。

| 側 | 誰が実装するか | IF |
| --- | --- | --- |
| 呼び出し側（上） | **環境**（Arduino×host、ESP-IDF×host、実機、再生 …） | **プラットフォームごとに違う。** 差分の吸収が環境の仕事 |
| デバイス側（下） | 模型の作者・生成器 | **共通。** 一度書けば適合するどの環境でも使える |

**デバイスは環境を選ばない。環境はデバイスを選ばない。** 適合キット
（環境の適合検査とデバイスの適合検査）が仕様を健全に保つ。どう使うか
（pytest 統合・golden 運用）は利用側の各リポジトリが決める。

```
          アプリ（無改造 —— Arduino スケッチ / ESP-IDF アプリ / …）
                            │ そのフレームワークの API
              ┌───── 環境（差し替え可能な 1 実装）─────┐
              │  host 実装 / 実機ブリッジ / 再生 / 将来の別実装  │
              └──── バインディング 1 枚で契約を満たす ────┘
                            │
   ┌─────────────────── 中立の契約 ───────────────────┐
   │  イベント列（連番・時刻・直列化可能）      ← 観測。リスナー N 個   │
   │  エンドポイント表（宛先 → 応答者 1）       ← 応答               │
   │  刺激スケジューラ（時刻 → 注入）           ← 刺激               │
   │  時計（仮想／実／記録）                                        │
   └────────────────────────────────────────────────┘
                            │
        バス・デバイス（枠組み＋解釈器＋状態）・読み出し・データ柱
```

### 4.1 観測と応答と刺激は別の口

| | 観測（リスナー） | 応答（エンドポイント） | 刺激（スケジューラ） |
| --- | --- | --- | --- |
| 数 | 何個でも | 宛先につき 1 | 台本 1 本（時刻順） |
| 向き | 出来事 → 外 | 問い → 答え | 外 → スケッチ |
| 時制 | **事後でも成立** | その場のみ | 時刻で発火 |
| 変更 | **できない**（読み取り専用） | 応答を決める | 入力を作る |

刺激が注入するものもイベントになる（トレースに写らない操作を作らない）。

### 4.2 イベント列 = トレース形式 = キャプチャ形式

**ライブの観測・保存した golden・実機のキャプチャ・再生の入力が、全部同じ
1 つの直列化形式**になる。道具（整形・diff・集計）が 1 セットで済む。

**語彙はハードウェアの言葉で書き、API の言葉で書かない。**
`pinMode(INPUT_PULLUP)` ではなく「GPIO 設定: 方向=入力・プル=上」。
**新しいイベントの合格条件は「Arduino と ESP-IDF の両方から、意味を失わずに
写れること」。**

| ドメイン | イベント |
| --- | --- |
| GPIO | 設定（方向・プル）/ 出力 / 入力（結果込み）/ 割り込み発火 |
| I2C(bus) | トランザクション 1 件（addr・R/W・データ・ACK/NACK・stop） |
| SPI(bus) | 設定（モード・クロック）・CS 上げ下げ・転送（往復） |
| UART(port) | 設定・送信列・受信列 |
| アナログ | **電圧的な数値**: DAC の出力値、ADC の読み（結果込み） |
| PWM | **周波数と比**: 設定（周波数・分解能）と duty の出力。tone（周波数だけの矩形波）もここ |
| **波形** | 時刻つきレベル列（シンボル列 = (レベル, 継続 µs) の並び）。**語彙には初日から居るが、実装は後段階** |
| **時間** | 待ち・時刻ジャンプ（**待ちも手順の一部**として写す）。単位は µs |
| 刺激 | 注入の記録（何を・いつ・どこへ） |
| 診断 | バス衝突・宛先不在・模型が検出した契約違反 |

全イベントは**連番・時刻・文脈タグ**（main ／ 割り込み中）を持つ。

### 4.3 線層と解釈層 —— イベントは 2 層あり、間に持ち上げ・引き下げが立つ

**すべての電気的な接点は線であり、バスは線の束に載せた解釈にすぎない。**

| 層 | イベント | どこから生まれるか |
| --- | --- | --- |
| **線層** | レベルの変化、シンボル列 | ビットバン、GPIO、RMT のような「波形を宣言する API」 |
| **解釈層** | トランザクション・バイト列・duty・パルス幅 | ハードウェア周辺 API のタップ、または線層からの**持ち上げ** |

変換器は**持ち上げ（decode: 線層→解釈層。ソフト SPI の復号）**と
**引き下げ（render: 解釈層→線層）**。どちらも普通の部品で、契約の特別扱いではない。

1. **ハードウェア周辺のタップは解釈層に直接入る。** Wire のトランザクションの
   裏に線イベントは存在しない（捏造しない）
2. **ビットバンは線層にだけ入り、持ち上げ器が解釈層を作る。** 同じ模型が
   どちらの経路でも動く
3. **バスの宣言は「役割 → 線」の割り当て表**（任意・**多対一可**）。
   割り当てが無ければ抽象バス（host の Wire）。MOSI と MISO が同じ線
   （3 線 SPI・半二重）は 2 つの役割が 1 本の線を指すだけで、方向の切り返しは
   枠組みの知識

「ピンで分けるかバスで分けるか」の答えは**両方**: 意味はバス（役割の束）が持ち、
線は割り当て表で対応づく。

### 4.4 エンドポイントの 4 つの形

| 形 | 宛先 | 例 |
| --- | --- | --- |
| アドレス型 | (bus, addr) | I2C の PMIC・センサ・OLED |
| 選択型 | (bus, cs 線) | SPI の TFT・SD・タッチ |
| ストリーム型 | (チャネル) | UART の GPS・モデム。持ち上げ後のシンボル・ビット列も同じ形 |
| レベル型 | (線集合) | ボタン・エンコーダ・1 線もの |

デバイスは解釈層に接続するのが基本形。レベル型だけは線層に直接付く。
登録の細目（一意性・容量・番号写像）は [USER.ja.md](USER.ja.md)。

### 4.5 デバイス = 枠組み + 解釈器 + 状態、面は 2 つ

| 層 | 何をするか | 変わる軸 |
| --- | --- | --- |
| 枠組み | バイトを「コマンド／データ」に分ける | バスで変わる |
| 解釈器 | コマンドを実行して状態を書き換える | デバイスで変わる |
| 状態 | RAM・レジスタ。**呼び出し側が確保** | — |

解釈器は 2 型: **register-map 型**（データ駆動 —— profile から生成できる）と
**command 型**（手書きの状態機械）。両対応チップは同じ解釈器を両枠組みから使う。

デバイスの面は 2 つ。**バスと線は別の面ではなく、IO 面の中の役割**。

| 面 | 中身 | 相手 |
| --- | --- | --- |
| **IO 面** | 役割の集合（SCK・MOSI・CS も INT・RESET・DC も同じ枠）。役割は線に割り当てられる（任意・多対一可） | 環境 |
| **物理面** | 測定量（温度・押下）と動作量（モータ速度・画面の絵）。**電気ではないもの** | 台本と読み出し |

**物理面が「走行中にデバイスの状態が変わる」の正しい入り口。** 温度が変わるのは
レジスタを裏から書くからではなく、**測っている世界が変わるから**。

#### 名前は 3 種 —— 共通な名前と、環境が決めてよい名前

「デバイスの PWM1 はこの GPIO」のような対応づけを、どの名前空間で書くかを
固定する。**契約が固定するのは型で、番号の意味は所有者が決める。**

| 名前 | 所有者 | 型 | 可搬性 |
| --- | --- | --- | --- |
| **役割番号**（デバイスのピン・チャネル） | デバイス作者。**0 始まりの局所番号** | uint8_t | **全環境・全プラットフォーム共通** |
| **世界の線**（EmuLine） | **型は契約が固定**（余裕幅・規約 11）。**番号の意味は環境が宣言**（Arduino 中間層ならピン番号、ESP-IDF なら gpio_num、host は任意） | uint16_t | その環境の中でだけ有効 |
| **物理チャネル** | デバイス作者。名前つき | 文字列 → 番号 | 共通 |

役割 → 線の対応は **attach 時の束縛表**が持つ（SPI の DC、レベル型の線集合、
PWM 入力の複数チャネルすべて同じ）。**デバイスは世界の線番号を見ない・
保存しない** —— デバイスが知るのは自分の役割番号だけで、だから全環境で共通の
まま居られる。

これが「共通ルールの中の、破ってよい場所」の正体: **型は必ず通る**（契約が
固定）、**番号の意味だけが環境ごとに変わる**（環境が宣言）。線番号を直接使う
台本（`emu_at_line`）はその環境・その板に束縛される —— 実物のピン番号が板ごとに
違うのと同じで、正当。可搬にしたい台本は物理チャネル（名前）を使う。

### 4.6 時計 —— 離散イベントシミュレーションの意味論

**スケッチが待つと、時計は「次に予定がある時刻」まで跳ぶ。** `delay(100)` は
実に眠らず、間に刺激の予定があればそこで発火してから進む。時計は差し替え:
仮想（既定・決定的）／実時間／記録。

### 4.7 線と割り込みの意味論 —— デバイスは線を駆動するだけ

**デバイスの世界は線で終わる。** INT を「上げる」のではなくレベルを変える。
その先は環境側の帰結: 掛かっていればハンドラ、無ければポーリングで拾われるか、
誰も見ない —— それでも線は変わり、イベントには写る。

線が変わる元は 3 つ（台本・デバイスの役割駆動・テストコードの直接操作）で、
**全部同じ注入点を通る**。注入点がやることは ①レベル更新 ②イベント記録
③ハンドラが掛かっていれば発火の**予約**。①②は無条件、③だけ条件つき ——
**割り込みは経路ではなく帰結**。発火点の運転は [ENVIRONMENT.ja.md](ENVIRONMENT.ja.md)。

共有 INT 線（オープンドレイン wired-AND）は当面 1 線 1 駆動者。2 つ目は
診断イベントで報せる。

### 4.8 環境は 2 軸 —— フレームワーク × 実行形態

| | ホスト実行 | 実機 | 記録 |
| --- | --- | --- | --- |
| **Arduino** | host-arduino-core（**同梱ポート第 1 号**） | 実機タップ（= プローブ §4.10）／スレイブ | — |
| **ESP-IDF** | IDF の linux ターゲット（将来） | 同上 | — |
| （フレームワーク無し） | — | — | 再生環境 |

バインディングは組ごとに 1 枚。環境は**能力を宣言**し（観測・応答・刺激・時計の
それぞれについて）、テストは要る能力を宣言して足りなければ skip。
**部分実装が正当な姿**（E1 だけの環境 = 解析専用。実機タップがそれ）。

### 4.9 層の実体 —— 何枚あって、それぞれ何を知っているか

```
  アプリ（無改造）
      │ フレームワークの API
  ① フレームワーク実装（host-arduino-core / 将来の別実装）
      │ タップ IF                           …まだフレームワークの言葉
  ② フレームワーク中間層（共有ライブラリ。Arduino 用が同梱第 1 号）
      │ 契約                                …ここからハードウェアの言葉
  ③ 契約（イベント列・エンドポイント表・刺激・時計）
      │ プロトコル別 ops（4 形）
  ④ 枠組み（I2C 制御バイト / SPI+DC / ストリーム / レベル）
      │ コマンド・データの列
  ⑤ 解釈器（register-map 型 / command 型）
      │
  ⑥ 状態（呼び出し側が確保した RAM・レジスタ）
      └→ 読み出し（RAM・表示窓・レジスタダンプ → PPM・トレースはホスト側の道具）
```

**継ぎ目は、両側が独立に変わるときだけ置く。**

| 継ぎ目 | 独立に変わる両側 |
| --- | --- |
| ①/② | 実装が変わる（host / 別ホスト / 実機タップ）× フレームワークの意味論は固定 |
| ②/③ | フレームワークが変わる（Arduino / ESP-IDF）× 契約は固定 |
| ③/④ | プロトコル 4 形 × デバイスの種類 |
| ④/⑤ | バスが変わっても解釈器は変わらない（実測: 376 行の重複が証拠） |
| ⑤/⑥ | 確保の場所が変わる（ホストの静的領域 / MCU の RAM） |

この表に **2 軸を書けない継ぎ目は作らない**。

### 4.10 プローブ —— 実デバイスからイベント列を得る（役割だけ決める）

模型は何から作るのか。答えは**実デバイスの観測**で、その観測装置がプローブ。
位置づけは「**E1（タップ）だけを実装した解析専用の環境**」の実機版であり、
新しい種類の部品ではない。

| 形 | どこで捕るか | 入る層 | 例 |
| --- | --- | --- | --- |
| **API プローブ** | 実 MCU の中。リスナー付きの Wire / SPI 実装を挟み、実アプリと実デバイスをそのまま通信させる | 解釈層 | 自作 Wire クラス経由のキャプチャ |
| **線プローブ** | 線の上。外部の計測器 | 線層（持ち上げて解釈層へ） | ロジックアナライザ（I2CDeviceDB の流儀） |

どちらも**出力は同じイベント直列化形式**（§4.2）。だから捕ったものはそのまま
再生環境の入力・golden・データ柱の capture になり、模型の準備はこの輪で回る:

```
プローブで捕る → capture → profile に整理（データ柱）
  → 模型（register-map 型は生成、command 型は手書き）
  → 同じ capture を模型に再生して突き合わせ（適合）
```

どちらの形をどのデバイスに使うかは**デバイスの仕様次第**（線に触れるか・速度・
分解能）なので、中身の定義はまだしない。**先に固定するのは役割と置き場所だけ**
—— E1 だけの環境であること、出力が共通形式であること。

## 5. 拡張しても破綻させないための規約

**ここが本体。** 機能は後から足せるが、規約は後から直せない。

1. **イベントは追加のみ。** 種類もフィールドも増やすだけ。リスナーは知らない
   種類を読み飛ばす。守る限りバージョン番号は要らない
2. **デバイス種・環境種の列挙を作らない。** すべて ops（vtable）＋状態の開いた集合
3. **観測は応答を変えられない。** リスナーに戻り値を持たせない
4. **契約にどのフレームワークの型も API 名も入れない。** 語彙はハードウェアの
   言葉（§4.2）。検査は「Arduino と ESP-IDF の両方から意味を失わず写れるか」
5. **核は純粋 C++。** どのフレームワークのヘッダも含めない・動的確保なし・
   例外/RTTI なし・I/O なし・C から呼べる。バッファは常に呼び出し側が渡す
6. **中心に固有名詞を溜めない。** 模型はカタログに置いてよいが、核はどの
   デバイスの名前も知らない。register-map の中身はデータ柱が正本
7. **golden は人が読める形式を既定に。** 文字トレースと PPM
8. **プロトコルを無理に統一しない。** 4 形はそれぞれの語彙で。共有するのは
   解釈器と読み出しであって、口ではない
9. **台本（刺激・障害・scenario）はコードでなくデータ**
10. **ログ解析はイベント列だけを読む。** 模型の内部・エンドポイント表・
    スケジューラに触る解析道具を作らない
11. **上限は 2 段。** IF 上の上限は型幅が決め、これは Protocol の一部
    —— **型幅は「追加のみ」では広げられない**（唯一の破壊的変更になる）ので、
    最初に余裕を持って切る（I2C アドレスは 10 ビットが入る幅、線番号は
    IO 拡張器が入る幅）。**実際の上限は環境と ctx が規定してよい**（表の容量・
    観測できる線の数・リスナー数）。ただし申告と失敗は義務 —— 能力として
    見えること、超過は黙らず失敗を返すこと

## 6. スコープの境界

- **タイミングの検証はしない。** 待ちが「あったこと」は記録するが、「足りて
  いるか」は実機でしか分からない
- **サイクル精度の再構成はしない。** 境界は「アプリが API で宣言した時系列か、
  計算の副産物か」。RMT のシンボル列・パルス幅・duty は宣言された時系列なので
  対象。ビットバンの NOP 数で作るタイミングは対象外
- **電気層の模倣はしない。** クロックストレッチ・バス調停は対象外。ただし
  API に漏れてくる帰結（タイムアウト・busy NACK）は応答と時計で表現できる
- **性能・フットプリントの測定はこの基盤の仕事ではない**
