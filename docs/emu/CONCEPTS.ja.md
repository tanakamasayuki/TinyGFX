# 概念 — あるべき姿・アクター・意味論・規約

内部の記録。日本語のみ。**全読者共通の正本**（2026-09-03 全面改訂）。
役割別の義務は [ENVIRONMENT](ENVIRONMENT.ja.md) / [DEVICE](DEVICE.ja.md) /
[USER](USER.ja.md)。決定か提案か未決かは [ROADMAP](ROADMAP.ja.md) の台帳が持つ。

## 1. あるべき姿

**組込みアプリケーションを、書かれたフレームワークのまま無改造で、実機なしで・
決定的に・観察可能な形で走らせ、実機とデータで裏を取れる基盤。**

```
用意する   デバイスの模型を置き、進行役（テスト側のもう 1 本の loop）を書く
走らせる   アプリをそのまま実行する（アプリもライブラリも一切改造しない）
確かめる   起きたこと（イベント列）と残ったもの（画面・レジスタ）を golden と突き合わせる
```

基盤の動詞は 4 つで、直交している。

| 動詞 | 何か | 担い手 |
| --- | --- | --- |
| **観測** | 起きたことを 1 本の順序つき列として見る | リスナー（何個でも・読むだけ） |
| **応答** | アプリの相手をする | デバイス（受動） |
| **注入** | 世界を変える（線・物理量・通知・受信） | **進行役**（単発のみ） |
| **時計** | 全部を 1 本の決定的な時間軸に載せる | tick モデル（§4） |

要件は 2 系統 + 共通基盤に分かれ、別々に作れて別々に使える:
**A. エミュレーション**（応答・注入）、**B. ログ解析**（観測 —— 模型ゼロでも
成立）、**S. 共通基盤**（時計・環境）。B はイベント列だけを読み、模型の内部を
覗かない —— この線が A と B を別々に版上げできる根拠。

## 2. アクター（正本）

### 2.1 役者（人）

| 役者 | 立場 | 読む文書 |
| --- | --- | --- |
| 環境の実装者 | 契約の上側 | ENVIRONMENT |
| デバイスの作者・生成器 | 契約の下側 | DEVICE |
| ライブラリ作者／**アプリ作者** | 利用者（アプリ作者が最大の空白） | USER |
| チップデータの整備者 | データ柱 | （データ柱側・未着手） |
| 実機での検証者／CI／教育・解析 | 運用と消費 | USER |

### 2.2 登場物（実行時）

| 登場物 | 側 | 能動か | 何をするか |
| --- | --- | --- | --- |
| **アプリ** | MCU 側 | 能動 | 被験体。無改造 |
| **環境** | MCU 側 | 能動 | アプリの操作を契約へ写す。**Protocol を知らない汎用拡張点 + 中間層**の 2 枚 |
| **契約** | 中立 | 場 | イベント列・エンドポイント表・時計 |
| **デバイス** | デバイス側 | **受動** | 模型。呼ばれて答え、役割番号で線を引く |
| **進行役** | 試験者側 | 能動（毎 tick） | テストの走行中の顔。もう 1 本の loop。単発注入と検分 |
| **テストコード** | 試験者側 | 走行前後 | 確保・仕込み・attach（前）／golden 照合（後） |
| **リスナー** | 試験者側 | 受動 | 観測の消費者。応答を変えられない |
| **適合キット** | 試験者側 | 開発時 | 環境・利用者の代役として契約順守を検査 |

旧「世界（台本が動かす）」は**進行役に統合**した。世界（温度・指・衛星）は
概念として残るが、それを動かす手はデータ（台本）ではなく**コード（進行役）**。

派生形（新しい種類ではない）: 環境 ← host 実装・再生・プローブ（観測だけの
実機環境）・スレイブポート。デバイス ← 障害注入デコレータ・カタログの模型・
生成された register-map 模型。部品: 枠組み・解釈器・持ち上げ器/引き下げ器。

データ（行為しない）: **scenario**（適合検査の入力）・**capture**（記録）・
**golden**（期待値）・**profile**（生成元）。すべてイベント直列化形式か、
そこへ写せる形式。

## 3. イベント列 —— 1 形式・1 行・2 層

**ライブの観測・golden・実機キャプチャ・再生の入力が同じ 1 つの直列化形式。**

- **1 イベント = 1 行。改行禁止**（dump の文字列も同じ縛り）。grep / diff /
  行単位 golden がそのまま効く
- 全イベントが連番・時刻（µs）・**文脈タグ**（main／割り込み中）・
  **出どころタグ**（アプリ／注入／デバイス）を持つ。golden はタグで濾せる ——
  「注入したのに反応しなかった」が証拠として残る
- **語彙はハードウェアの言葉**で書く。合格条件は「Arduino と ESP-IDF の
  両方から意味を失わず写れること」

| ドメイン | イベント |
| --- | --- |
| GPIO | 設定（方向・プル）／出力／入力（結果込み）／割り込み発火 |
| I2C(bus) | トランザクション 1 件（addr・R/W・データ・ACK/NACK・stop） |
| SPI(bus) | 設定・CS 上げ下げ・転送（往復） |
| UART(port) | 設定・送信列・受信列 |
| アナログ | **電圧的な数値**: DAC 出力値・ADC の読み（結果込み） |
| PWM | **周波数と比**: 設定と duty。tone もここ |
| 波形 | 時刻つきレベル列（(レベル, 継続 µs) の並び）。**語彙に席あり・実装は後** |
| 時間 | 待ち・歩進（待ちも手順の一部として写す） |
| 注入 | 何を・いつ・どこへ（出どころつき） |
| 検分 | `dump` の文字列 |
| 診断 | バス衝突・宛先不在・tick 内の待ち API 違反 など |

**線層と解釈層の 2 層**がある。ハードウェア周辺 API のタップは解釈層に直接
入り（Wire のトランザクションの裏に線イベントを捏造しない）、ビットバンは
線層に入って**持ち上げ器**が解釈層を作る。バスの宣言は「役割 → 線」の割り当て表
（任意・**多対一可** —— 3 線 SPI は 2 役割が 1 線を指すだけ）。

## 4. 時間と tick —— 検証しない。座標としてだけ持つ

タイミングの正しさ（15ms で足りるか）は対象外のまま。要るのは**順序**と
「次の周」が定義できることで、時計はその座標にすぎない。

- **主時計は µs の単調カウンタ 1 本**。`micros()` はこれを返す
- **tick = 可変の刻み**（既定は中間層の規約: Arduino 1ms / ESP-IDF 10ms）
- **loop 1 周 = 1 tick。すべての待ちが主時計を進め、tick 境界を越えるときだけ
  tick 処理が走る。** `delay(n)` は `delayMicroseconds(n×1000)` の糖衣。
  未来の予定表を持つ者は居ない
- tick 内の順序: **①進行役 ②保留 ISR ③アプリの持ち分 ④歩進**。
  外部入力の取り込みは④の後 = 次の周に属す
- **tick コンテキスト（進行役・ISR）では待ち API 禁止**（違反は診断イベント +
  no-op。「ISR で delay 禁止」と同型）。進行役は待たずに tick を数える
- 実時間・倍率は opt-in の別モード（非決定的と明示）
- 境界: 待ちを呼ばず `micros()` だけ見張る生ループは進まない
  （ライブラリ内のポーリングは時計口経由で救われる。`yield()` も時計口を通る）

## 5. 注入 —— 単発のみ、必ず写る

世界を変える手は**進行役の単発注入だけ**。宛先は 4 つ:
**線**（ボタンはデバイスではなく GPIO 操作）・**物理量チャネル**（温度 = 80）・
**通知チャネル**（「NMEA を出せ」）・**UART 受信**。

- スケジューラは無い。「20ms 後に HIGH」は進行役が 20 tick 数える
- 割り込みは**経路ではなく帰結**: 注入点は ①レベル更新 ②イベント記録
  ③掛かっていれば発火予約、の 3 つをやる。①②は無条件
- 同一 tick 内の連続注入（LOW→HIGH）で縁が 2 つ立つ —— 割り込みは時間と無関係
- 発火点は注入の切れ目と tick 境界。最初はネスト無し・FIFO

## 6. デバイス —— 完全受動

**呼ばれたときだけ動く。** 自前のタイマーは持たない（再生環境・実機スレイブで
成立しないため。「デバイスは環境を選ばない」の帰結）。

- デバイス = **枠組み**（バス別の薄い皮）+ **解釈器**（本体）+ **状態**
  （呼び出し側が確保）。解釈器は **register-map 型**（データ駆動・生成可能）と
  **command 型**（手書きの状態機械）
- 受け口チャネル 2 種: **物理量**（値つき）と**通知**（値なし）。
  「GPS は 100ms ごと」のような知識は**デバイスがデータとして公開**し、
  回すのは進行役。busy は「呼ばれたとき now を見る」の遅延評価
- **名前は 3 種**: デバイスの**役割番号**（0 始まり・全環境共通）／世界の
  **線**（型は契約が固定、番号の意味は環境が宣言）／**チャネル名**。
  デバイスは線番号もポート番号も知らない —— 束縛は attach が持つ
- 検分と仕込み: 環境は中継しない。ハンドル直の const は無記録。
  **契約経由の `dump`（文字列・書式自由・1 行）は記録**。初期状態は
  postSetup の dump。走行中の変化は注入で（裏口を作らない）
- 壊れ方も正規の口で: 応答の故障は**障害注入デコレータ**、世界側の故障
  （電源断）は物理面・RESET 役割への注入

## 7. 環境 —— 2 軸・2 枚・部分実装は正当

環境 = **フレームワーク × 実行形態**。バインディングは 2 枚:
**① 汎用拡張点**（フレームワーク実装が持つ。Protocol を知らない —— host-arduino-core
1.7.0 が実物）と **② 中間層**（フレームワークの意味論を契約へ写す共有ライブラリ）。

環境は能力（観測・応答・注入・時計）を宣言し、テストは足りなければ skip。
**E1（観測）だけの環境も正当** —— 実機タップ（プローブ）がそれ。プローブは
API プローブ（解釈層で捕る）と線プローブ（ロジアナ。線層で捕って持ち上げ）の
2 形で、出力は同じイベント形式。模型の準備は
「捕る → capture → profile → 模型 → 同じ capture を再生して突き合わせ」の輪。

## 8. 規約 —— 拡張しても破綻させないために

1. **イベントは追加のみ**（種類もフィールドも。リスナーは知らない種類を読み飛ばす）
2. **デバイス種・環境種の列挙を作らない**（ops + 状態の開いた集合）
3. **観測は応答を変えられない**（リスナーに戻り値なし）
4. **契約にどのフレームワークの型も API 名も入れない**（語彙はハードウェアの言葉）
5. **核は純粋 C++**（フレームワークヘッダなし・動的確保なし・例外/RTTI なし・
   I/O なし・C から呼べる。バッファは呼び出し側）
6. **中心に固有名詞を溜めない**（模型はカタログ、核はデバイス名を知らない）
7. **golden は人が読める形式**（1 行イベントと PPM。独自バイナリ禁止）
8. **プロトコルを無理に統一しない**（4 形はそれぞれの語彙。共有は解釈器）
9. **注入は必ずイベントに写す**（トレースに写らない世界の変化を作らない。
   scenario・profile・capture はデータのまま）
10. **ログ解析はイベント列だけを読む**（A と B を別々に版上げできる根拠）
11. **上限は 2 段**（IF の上限 = 型幅。余裕を持って切る —— 型幅だけは追加のみで
    広げられない。実際の上限 = 環境と ctx が規定し、申告と失敗は義務）

## 9. スコープの境界

- **タイミングの検証はしない**（待ちの記録まで。足りているかは実機）
- **サイクル精度の再構成はしない**（API で宣言した時系列は対象、計算の副産物は対象外）
- **電気層は模さない**（ストレッチ・調停。API に漏れる帰結 —— タイムアウト・
  busy NACK —— は応答と時計で表現できる）
- **性能・フットプリント測定はこの基盤の仕事ではない**
