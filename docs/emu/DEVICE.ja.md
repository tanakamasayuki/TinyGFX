# デバイスの実装ルール — 受動の模型

内部の記録。日本語のみ。2026-09-03 改訂。概念は [CONCEPTS.ja.md](CONCEPTS.ja.md) が正。

## 0. デバイスとは

**チップの振る舞いの模型。呼ばれたときだけ動く（完全受動）。**
正しい順序で答え、状態を保ち、役割番号で線を引く —— それ以外は何もしない。
誰が観ているか・どの環境か・いま何のテストかを知らない。**自前のタイマーも
持たない**（再生環境・実機スレイブで成立しないため）。

触るアクターは 4 者（正本は CONCEPTS §2。これはデバイスから見える範囲）:

| アクター | 触る面 | 時期 |
| --- | --- | --- |
| 環境（契約経由） | バス面 ops・役割線 | 走行中（正規の交通） |
| **進行役** | 受け口チャネル（物理量・通知）・線 | 走行中（注入 = 必ずイベントに写る） |
| 利用者 | 型付きの口 | 走行前（仕込み）・いつでも（const 検分） |
| 適合キット | バス面 | 開発時 |

**走行中の内部直接変更は例外を作らない。** 応答の故障は障害注入デコレータ、
世界側の故障（電源断）は物理面・RESET 役割への注入で表す —— どちらも
イベントに写るのが裏口との違い。

## 1. デバイスから見える世界 —— 3 つだけ

1. **バス面から来る呼び出し**（ops を実装する）
2. **道具**（attach 時に渡される。世界への唯一の出口）:
   `drive(束縛, 役割番号, レベル)`・`uart_send(束縛, …)`・`now_us(束縛)`
3. **自分の状態**（呼び出し側が確保したメモリ）

**世界の線番号（EmuLine）もポート番号も知らない・保存しない。** 知るのは
自分の 0 始まりの役割番号だけ（束縛表は attach が持つ）。線を知った時点で
その環境に縛られる。busy は `now_us` の遅延評価で書く（例: 測定コマンドで
開始時刻を記録し、読みに来たとき 15ms 未満なら busy を返す）。

## 2. 実装するもの

- **ops（4 形のうち自分のもの）**: I2C はトランザクション単位
  （write/read/reset。0 = ACK、2 = 不在）、SPI はバイト単位
  （select/transfer/role/reset）、UART は tx、レベル型は役割番号で line
- **受け口チャネルの宣言**: 物理量（値つき: 温度）・通知（値なし: 「出せ」）。
  周期などの推奨値は**データとして公開**（回すのは進行役）
- **`dump`（任意・強く推奨）**: 中身を**改行を含まない 1 行の文字列**で描出
  （書式自由: JSON / BASE64 / 独自）。契約経由で呼ばれるとイベントに写る。
  初期状態の記録（postSetup）もこれ
- **検分・仕込みの型付き口**: register-map 型は `get`/`set` が自動。command 型は
  自分で切る（表示なら RAM 全体と表示窓の 2 口 —— オフセットのずれが絵で見える形）。
  const 検分は状態もイベントも変えない

## 3. 中身の分割

**ops を実装するのは枠組み（薄い皮）、本体は解釈器。** SSD1306 なら I2C 枠組み
（制御バイト）と SPI 枠組み（DC 役割）が**同じ解釈器**を呼ぶ。

| 解釈器 | 書くもの |
| --- | --- |
| register-map 型 | **表だけ**（番地・リセット値・副作用 callback）。データ柱の profile から生成できる形 |
| command 型 | 状態機械（ここが本体）。表示・SHT30 系 |

## 4. 出どころ —— 自作・ライブラリ・生成の 3 つ（△ 提案）

| 出どころ | 例 |
| --- | --- |
| **自作** | 下のチェックリスト。register-map 型なら表だけ |
| **知識の持ち主のライブラリ** | 表示の模型は TinyGFX 側が育てる（「模型はそのプロトコルを知っているライブラリの持ち物」）。まず利用リポジトリのテスト共通ライブラリで育て、2 つ目の利用者が現れたらカタログへ昇格 |
| **データ柱からの生成** | profile → register-map 模型 |

## 5. 新しいデバイスのチェックリスト

| # | 準備するもの | 量 |
| --- | --- | --- |
| 1 | 状態の構造体 | 定義だけ（確保は利用者） |
| 2 | 解釈器 | 表（register-map）or 状態機械（command） |
| 3 | 枠組み | 既製から選ぶ。新しい線上の作法のときだけ自作 |
| 4 | 役割の宣言（INT / RESET / DC …） | 列挙 |
| 5 | 受け口チャネル（物理量・通知）と推奨値データ | あれば |
| 6 | `dump` と型付きの検分・仕込み口 | §2 の作法 |
| 7 | 適合検査 + scenario か golden を 1 つ | — |

## 6. 禁止事項

- フレームワークのヘッダ・動的確保・例外/RTTI・I/O（printf・ファイル）禁止
  —— MCU に載る前提（U16）
- 道具（§1-2）以外の道で世界に触れない
- **EmuLine を受け取らない・保存しない**
- 待たない（tick コンテキストで呼ばれる。待ち API は診断イベント + no-op）
- デバイス種の列挙に自分を足す必要が出たら、それは契約側の設計ミス（報告する）
