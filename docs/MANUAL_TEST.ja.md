# 手動テスト（実機）

内部の記録。日本語のみ。**自動テストには含めない。**

ホストのテストで守れないのは次の 3 つ。いずれも**実機でしか分からない**。

1. パネルの初期化列と待ち時間が足りているか
2. SPI のモード・ビット順・クロックが合っているか
3. **MADCTL の値と原点オフセットの導出が正しいか**（`tests/window/` は
   「実装が表どおりか」しか見ていない。表そのものが正しいかは実機で確かめる）

## ブリングアップスケッチ — `tests/manual/bringup/`

**新しいパネルに初めて火を入れるときはこれ。** 直すところは 3 つで、
スケッチの頭に `STEP n of 3` と書いてある。

### STEP 1 — パネル。**2 行を揃える**

`src/TinyGFX/panels/` からヘッダを選び、**ファイル名と、その前に
`TinyGFXPanel` を付けたクラス名**を書く。命名は例外なくこの規則。

```cpp
#include <TinyGFX/panels/SSD1306_128x64.h>
#define PANEL TinyGFXPanelSSD1306_128x64
```

食い違うと `PANEL does not name a type` で止まる。

### STEP 2 — バス。**`//` が付いていない行を 1 つだけにする**

```cpp
// #define USE_SPI          <- コメントアウトして
#define USE_SOFT_SPI
// #define USE_I2C          <- こちらの // を外す、のように
```

| | |
| --- | --- |
| `USE_SPI` | ボードのハード SPI。速い。SCK / MOSI は固定 |
| `USE_SOFT_SPI` | 任意の 4 ピンでビットバン。コアに SPI が無い所（CH32V003）で使う |
| `USE_I2C` | 2 線。**モノクロ OLED（SSD1306 / SH1106）専用** |

### STEP 3 — ピン。**使うバスのぶんだけ**

| バス | 効くもの |
| --- | --- |
| `USE_SPI` | `PIN_DC` / `PIN_CS` / `PIN_RST` |
| `USE_SOFT_SPI` | 上に `PIN_SCK` / `PIN_MOSI` を追加 |
| `USE_I2C` | `I2C_ADDR` だけ（SDA / SCL はボードのもの） |

既定値は ESP32 の開発ボード向け。**リセットピンが無いモジュールは
`PIN_RST = -1`** にすれば、TinyGFX はリセットに触らない。

[PANEL_TUNING.ja.md](PANEL_TUNING.ja.md) §2 の症状が**1 枚に全部出る**ように
してある。

| 絵の要素 | 分かること |
| --- | --- |
| 1 画素の枠 | ガラス全面が使えているか。**端に縦縞のゴミ = 列オフセット** |
| 角のブロック | 原点がどの角か（ミラー・回転） |
| 対角線 | 向きと、両軸が端まで届いているか |
| RGB の帯 | 色順（カラーのみ。**上が赤**。青なら `setRgbOrder`） |
| 黒地に白枠 | 反転しているか |

3 秒ごとに回転が進む。**シリアルに寸法とバスと `begin()` の結果を出す**ので、
画面が真っ暗でも「スケッチは生きていて、問題はパネルか配線かバス」までは分かる。

ページ方式（SSD1306 / SH1106）とダイレクト方式（ST7789 ほか）で必要なものが
違う —— 前者はフレームバッファと `display()` が要る —— が、**ドライバのマクロで
自動的に切り替わる**ので触るのは上の 2 行だけ。`tests/build_matrix/` が
**両方の枝をビルドして**腐っていないことを見ている。

## MCU は何を使っても同じか

**パネルから見れば同じ。** 同じバイト列が出るので、オフセット・COM ピン配置・
色順・回転の確認に MCU は関係しない。違うのは TinyGFX 側の都合だけ。

| | |
| --- | --- |
| **RAM** | ページ方式は `w * h / 8` を持つ。128x64 で 1 KB —— CH32V003（2 KB）では半分、ESP32 では誤差。**ESP32 なら帯描画を考えずに済む** |
| **ハード SPI** | CH32V003 のコアには SPI ライブラリが無い（[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E2）。ESP32 は両方ある |
| **PROGMEM** | **AVR だけフラッシュが別アドレス空間。** `src/TinyGFX/Progmem.h` の `__AVR__` の枝だけ `pgm_read_*` を使う |

**パネルの確認は ESP32 で正解。** RAM もハード SPI もあるので、
**結果が変なら原因はパネルだと言い切れる。**

ただし 1 つだけ穴がある。**AVR の `pgm_read_*` の枝は、どこでも実行されていない**
——ホストも ESP32 も直接参照する枝を通るので、`build_matrix` がビルドしている
だけ。**最後に AVR で 1 回動かすと、そこだけは他で代わりが利かない。**

## 注文したパネルの一覧（2026-09-01）

**25 枚のうち 19 はカタログにある。残り 6 つ。**

| バス | コントローラ | 寸法 | 状況 |
| --- | --- | --- | --- |
| I2C | **SSD1315** | 72x40 / 64x32 / 128x64 | **ドライバ未対応。** 寸法は 3 つとも SSD1306 のプリセットにある |
| I2C | **CH1115** | 48x88 | **ドライバも寸法も未対応** |
| I2C | **SSD1312** | 64x128 | **ドライバも寸法も未対応** |
| I2C | SSD1306 | **96x64** | ドライバはある。寸法が無い |
| SPI | ST7789 | **76x284** | ドライバはある。寸法が無い |

3 つとも SSD1306 系のコントローラなので、**最初に試すのは
`TinyGFXDriverSSD1306` をその寸法で使うこと。** 通ればプリセットは
カタログに 4 行足すだけで済む。

**寸法の側はホストで先に潰してある**（`tests/i2c/`）。48x88 は 11 ページ、
64x128 は 16 ページ、96x64 は 8 ページで、どれも `begin()` が通り、多重比が
高さ − 1 になり、全面転送がちょうど `w * h / 8` バイトになることを検査している。

**残るのは COM ピン配置と列オフセットだけ**で、これは推測できない
（[PANEL_TUNING.ja.md](PANEL_TUNING.ja.md) §3）。ガラスを見てから
カタログに入れる。**値が分かる前にプリセットを足さない。**

## インチ数はコードに入らない

パネルヘッダが運ぶのは解像度・列オフセット・GRAM 寸法・COM ピン配置・色順で、
**物理サイズはどれにも入らない。**

ただし**品種を見分ける札としては効く。** 同じ解像度でも別のガラスなら、
オフセットや配線が違うことがある。

| | |
| --- | --- |
| 0.96 インチ 128x64 | SSD1306。列オフセット 0 |
| **1.3 インチ 128x64** | **SH1106。** RAM 132 列でオフセット 2。「SSD1306」として売られていることが多い |

**同じ 128x64 で、コントローラごと違う。** だから `tools/gen_panels.py` の
カタログの `note` にはインチを書いてある —— 値としてではなく、
**どれを買ったのかを言い当てるため。**

出るはずのもの（1 画面に全部入れてある）:

- [x] 外周 1 ドットの白い枠が**四辺とも**見える（大きさとオフセット）

- [x] まん中の `0123456789` が鏡像でも上下逆でもない（MADCTL の向き）
- [x] 下の円・三角・線が欠けずに出る（プリミティブ）
- [x] 背景が黒（白地なら反転が逆）— **世代による**。下記

**2026-08-28、M5Stack BASIC で正常に描画。** 既定値（`INVON` / BGR / ミラー無し /
回転 0 = 320x240）がそのまま正しかった。当てずっぽうだった MADCTL の表は当たっていた。

違ったときの直し方。**どれもスケッチ 1 行**:

| 症状 | 直す場所 |
| --- | --- |
| 真っ暗 | バックライト GPIO32 が HIGH か。ここが 9 割 |
| 白地に黒 | `panel.invertDisplay(false)`。**`lcd.begin()` の後で**。古い世代の BASIC がこれ |
| 帯が 青・緑・赤 | `panel.setRgbOrder(false)` |
| 数字が鏡像 / 逆さま | `panel.setMirror(mx, my)` を `lcd.begin()` より前に |
| 端が欠ける・ずれる | コンストラクタが 320x240 になっているか |

**MADCTL のベース値・色順・回転 0 の向きは確認できた**（2026-08-28）。既定のまま
正しいので `setRotation()` は変更しない。`tests/ili9342/` の期待値も現状のままでよい。

**反転だけは世代で違う。** 手元の BASIC は `INVON`（既定）で正しく、
**古い世代の BASIC は色が反転した**。パネルクラスの既定は変えず、
スケッチ側で `invertDisplay(false)` を外す形にした
（`examples/M5StackBasic` にコメントアウトで置いてある）。

`invertDisplay()` / `setSleep()` / `displayOn()` は **`lcd.begin()` の後に呼ぶこと。**
前に呼ぶと (1) バスがまだ初期化されておらず、(2) 通っても `init()` の初期化列に
上書きされる。**2 つ重なるので「効かない」ように見える。**

## M2 — 回転 0..3 が正しい向きで出る（**MADCTL の側は自動化済み**）

### 自動で守れるようになった分（2026-08-29）

`tests/hw/m5stack/` の **`test_rotation_maps`**。M5Stack BASIC で**通っている。**

読み戻しで回転を見るには一手要る。**回転 N のまま描いて回転 N のまま読んでも
何も分からない** — RAMRD は書き込みと同じアドレスカウンタを通るので、MADCTL が
間違っていても自己無矛盾に読めてしまう。

なので**回転 N で描いてから回転 0 に戻して読む。** MADCTL はアクセスの写像を
変えるだけで GRAM の中身は動かさないので、回転 0 という固定フレームから
「物理的にどこに入ったか」が見える。

`DriverILI9342.h` の MADCTL 表からの導出（MV が転置、MX が列反転、MY が行反転）。
320x240 の横長 GRAM で:

| 回転 | MADCTL | 論理 (lx, ly) → 物理 |
| --- | --- | --- |
| 0 | 0 | (lx, ly) |
| 1 | MV\|MX | (W−1−ly, lx) |
| 2 | MX\|MY | (W−1−lx, H−1−ly) |
| 3 | MV\|MY | (ly, H−1−lx) |

論理 (5, 2) に 1 画素ずつ、回転ごとに別の色で打つと 4 つとも別の隅に落ちる。
古い画素が残っていても色が違うので偽の合格にならない。**実測 `F800 07E0 001F
FFFF`** — 4 回転とも予測どおりだった。

### 自動では守れない分（目で見るしかない）

- **回転 0 自体の向き。** 上下が逆でも読み戻しは自己無矛盾になる。M0 で一度
  確認済み。ここが固定されている前提で、上のテストが 1〜3 を縛る
- **オフセットのあるモジュール。** M5Stack はオフセットが無いので
  `setGramSize()` からの導出は試せていない

| | |
| --- | --- |
| 機材 | M1 と同じ。**オフセットのあるモジュール**（135x240 など） |
| スケッチ | 左上と右下に別色の矩形を置き、`setRotation(0..3)` を順に |

- [ ] 回転 0..3 で絵が 90 度ずつ回る（飛んだり鏡像になったりしない）
- [ ] どの回転でも端が欠けない・余分が出ない
- [ ] `width()` / `height()` が回転 1/3 で入れ替わる
- [ ] **オフセットのあるモジュールで、回転 2 と 3 がずれない**

最後の項目が本番。`setGramSize()` からの導出（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §5、
`tests/window/` の表）が正しいかはここでしか分からない。
**ずれたら表を直し、`tests/window/` の期待値も直す。**

## 読み戻し（2026-08-28、M5Stack BASIC）

**動くようになった。実機の GRAM がホストのゴールデンと 1 画素も違わないことを、
毎回のテストで確かめている**（`tests/hw/m5stack/`）。

### 配線

| | |
| --- | --- |
| データ線 | **SDA は GPIO23 の 1 本きり**（MOSI と MISO の兼用） |
| SPI の MISO（GPIO19） | **何も来ていない。** どう設定しても FF しか返らない |
| 形式 | ダミー 1 バイト → 1 画素 3 バイトの RGB666（上位 6 ビット） |

### 効く条件は 4 つ。**どれ 1 つ外しても読めない**

全部実測で詰めた。順に、外したときに何が起きるかも書いておく。

| 条件 | 外すとどうなるか |
| --- | --- |
| **待ちを入れない。** 手叩きのループはタイトに | 1 エッジに `delayMicroseconds(1)` を入れるだけで**全バイト FF**。パネルが線を離す |
| **取得は `pinMode` だけ。`SPI.end()` を先に呼ばない** | 呼ぶと**全バイト FF** |
| **1 画素ごとに窓（CASET/RASET）を張り直す** | 連続読みでは**カラムが進まず、同じ画素が返り続ける**（生ダンプで `FC0000` が 5 回） |
| **2 回読んで一致するまで繰り返す** | 20 バイトに 1 回ほどビットが化ける。**クロックを落として直すことはできない**（上記のとおり止まる） |
| **戻すのは `SPI.end()` → `SPI.begin()`** | `begin()` だけだと何も起きず（開始済みなら早期 return）、**以降の書き込みが黙って死ぬ**。同じ絵を描き直すと気づけないので厄介 |

**「安全側に倒して遅くする」が通じない相手だった。** 私が良かれと思って入れた
`delayMicroseconds` が、そのまま読めない原因になっていた。

### 個体差がある（2026-08-29）

**同じ M5Stack Core でも、読み戻せる個体と読み戻せない個体がある。**

| 個体 | 結果 |
| --- | --- |
| `esp32-d0wdq6-840d8e211104` | 読める。上記のレシピで安定 |
| `esp32-d0wdq6-b4e62dfb4631` | **読めない。** `readable=0` |

読めない方の症状:

```
期待 F800 07E0 001F   ← RED / GREEN / BLUE
実際 F800 87E0 801F
```

**差は R バイトの最上位ビットだけ。** 赤（`FC 00 00`）は元から MSB が立って
いるので正しく見え、緑と青で R が `00` のはずが `80` 台になる。

全体が 1 ビットずれているなら緑の値も崩れるが、緑のフィールドは満スケール
（`0x3F`）で来ている。つまり**線の向きを変えた直後の 1 ビットだけが High に
張り付いている**形で、ターンアラウンドのタイミングが個体で違うと見られる。
反転が世代差だったのと同じ類。

**未追求。** 最新世代の端末を新規購入してそちらを標準の検証機にする方針
（2026-08-29 判断）。それまで読み戻しは skip のままにする。

### 読み戻しが skip でも困らない理由

読み戻しは**追加の検証**であって唯一の検証ではない。ライブラリの正しさは
`TinyGFXBusCapture` 経由のゴールデン比較（`test_scene_matches_host_golden`）で
押さえてあり、これは実機のコンパイラ・実機の `int` 幅・実機の PROGMEM を
通った結果を見ている。**線から先だけが範囲外**になる。

読み戻しでしか見られないのは回転の写像（M2）なので、そこだけが個体差の
影響を受ける。

### 効かなかったもの

- `0xF6` Interface Control の `SDA_EN`（0 でも 1 でも変わらない）
- 読み線を GPIO19 にする（何も来ていない）
- ID レジスタ `0x04` / `0x09` / `0x0A` / `0x0C`（基本 FF。**GRAM は読めるのに**）

### 速さ

**1 画素あたり約 150µs。** 1 画素ごとに窓を張り直すので、コマンド 14 バイト +
読み 4 バイトを手で叩くぶん。64x8 の帯で 75ms 程度。
**デバッグと検証のためのもので、描画に使うものではない。**

### これで何が守れるようになったか

`tests/hw/m5stack/` の 4 本のうち、**読み戻しを使う 1 本だけが線の先を見ている。**

| テスト | 見ている範囲 |
| --- | --- |
| `test_scene_matches_host_golden` | 実機の CPU・コンパイラ・PROGMEM を通った描画（`BusCapture`） |
| **`test_readback_matches_golden`** | **パネルの GRAM そのもの。線・SPI・パネルの解釈まで** |
