# 設計決定

内部の記録。日本語のみ。**「なぜそうなっているか」の台帳。**

決定の内容そのものは [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) にある。ここには**理由と、採らなかった選択肢**を書く。

**まだ全部たたき台。** 実測で覆る前提のものには「**要実測**」と書く。

## 1. 確定させたい決定

### D1. 描画 API に virtual を 1 つも置かない

`TinyGFX` の描画メソッドはすべて非 virtual、ヘッダ内 inline。

**理由**: `--gc-sections` は呼ばれない関数を落とすが、**vtable から参照される関数は落とせない**。描画を virtual にすると、`fillRect` しか使わないスケッチにも `fillTriangle` や `drawCircle` が載る。CH32V003 の 16KB では致命的。非 virtual なら [REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §8 の「構成 A〜E の積み上げ」がそのまま成立する。

**採らなかった案**:
- *共通基底クラスに描画 API を virtual で持たせる（Adafruit_GFX 方式）* — パネル追加が楽で構造も素直。だが上記のとおり未使用 API を落とせず、TinyGFX の存在意義（V003 に載ること）を最初に潰す。
- *描画も含めて全部テンプレート* — サイズが読めなくなる。D2 参照。

**関連**: virtual を避けるだけでは足りない。参照の連鎖で落ちなくなる経路を塞ぐ規則が D15。

**代償**: `TinyGFX` を継承して描画を差し替える、という拡張ができない。スプライトのような「別の描画先」を後から足すときに、継承ではなく別クラスを書くことになる。**スプライトは非目標**（D13）なので今は許容する。

### D2. Panel と Bus だけを virtual にする。テンプレートにしない

**要実測。**

**理由**: 間接呼び出しのコストは**速度**であって**サイズ**ではない。速度は多少遅くてよい（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §3）。一方テンプレートはサイズが読めなくなるほうに効く。vtable 2 枚（合計 50 バイト前後）で、構成の見通しとビルドの軽さが買えるなら安い。

**採らなかった案**:
- *`TinyGFX<DriverST7789<BusSPI>>`* — 間接呼び出しが消えて理論上は最小・最速。だが inline 展開が呼び出し箇所ごとに転送ループを複製し、**かえって増えることがある**。「増分を細かく見て増やさない」という運用（[FOOTPRINT.ja.md](FOOTPRINT.ja.md)）と噛み合わない。型名とコンパイルエラーが重くなる副作用もある。
- *関数ポインタ表を手で持つ* — virtual と実質同じコストで、書くのが面倒なだけ。

**逃げ道**: `TINYGFX_STATIC_BUS` / `TINYGFX_STATIC_PANEL` で単一実装に固定し、virtual を消せるようにする（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.3）。**ただし Phase 0 で「virtual のままだと予算に入らない」と実測されるまで入れない。** 数字を見ずに複雑さを足さない。

### D3. Bus インターフェースに `writeColor(color, count)` を入れる

memo の Bus 案（`writePixels` のみ）から**変更**した。

**理由**: `writeColor` がないと `fillScreen` / `fillRect` が「画素数ぶんの `uint16_t` 配列」を要求する。240x320 なら 150KB で、SRAM 2KB の機種では原理的に不可能。数画素ずつのループで回避することもできるが、それは結局「同色連続転送」を上位で再実装しているだけで、Fast Backend が DMA で一気に流す道も塞ぐ。**インターフェースの最小性より、V003 で成立することを優先する。**

**採らなかった案**:
- *`writePixels` だけ残し、上位で小さなバッファを回す* — Bus は狭いままだが、バッファを誰が持つかの問題が上位に移動するだけ。静的バッファを持てば全スケッチが RAM を払う。
- *`fillRect` を Panel の責務にする* — Panel ごとに塗りつぶしを実装することになり、パネル追加のコストが上がる。

### D4. 色は RGB565 固定。型エイリアスを作らず `uint16_t` を生で使う

**理由**: 色深度を抽象化すると、変換テーブルか変換関数分岐が全経路に載る。対象パネルは全部 RGB565 なので、抽象化の対価に見合わない。型エイリアス（`tinygfx_color_t` 等）も、結局 `uint16_t` の別名でしかないなら**利用者が覚える名前が 1 つ増えるだけ**。

**採らなかった案**:
- *強い型（`struct Color565`）* — `fillRect(x, y, w, h, 0xFFFF)` のような取り違えを防げる。だが `pushImage` に渡す配列型まで波及し、`const uint16_t*` を素直に渡せなくなる。組み込みで生バッファを渡す用途が多いので相性が悪い。
- *`setColorDepth()` を持つ* — 1bpp / 8bpp パネルを将来入れるなら要る。だが今の対象に無く、非目標。

### D5. 座標は `int16_t`、転送長は `uint32_t`

**理由**: 座標は画面外・負値を許したいので符号付き。`int16_t` で ±32767、対象解像度に対して十分。一方 240x320 = 76,800 画素なので**転送長は 16bit では足りない**。ここを取り違えると 65,536 画素を超える塗りつぶしが静かに壊れる。

### D6. コストの高い機能は禁止せず、ヘッダで分離して値札をつける

`print` / `printf` / float 引数 / RGB888 変換などは**提供する**。ただしコアには入れず、`TinyGFX/Print.h` のような**別ヘッダ + 派生クラス**で出す。

**理由**: 「V003 に載る」と「便利に使える」は両立できる。要るのは禁止ではなく**選べること**と**選ぶ材料**。`#include` していない翻訳単位はリンクもされないので、ヘッダ分離が最も確実で、条件コンパイルの組み合わせ爆発も起きない。そのうえで「この機能は V003 でフラッシュ +N バイト」を実測して GUIDE に書けば、利用者が自分の予算で判断できる。

**採らなかった案**:
- *float 全面禁止* — 「V003 に載る」だけを守れるが、ESP32 でも `println(3.14f)` が使えないライブラリになる。対象環境の幅を自分で狭めている。
- *マクロで有効化（`TINYGFX_ENABLE_PRINT`）* — 分離はできるが、スイッチの組み合わせ数だけビルド構成が増え、テストで守れなくなる。ヘッダ分離なら構成が自然に 1 本道になる。
- *全部入れて「使わなければ落ちる」に任せる* — `Print` を継承した時点で vtable 経由になり落ちない。D1 と同じ罠。

**運用の義務**: 拡張ヘッダを 1 つ足すたびに、**CH32V003 での増分を実測して [FOOTPRINT.ja.md](FOOTPRINT.ja.md) に記録する。** 測っていない拡張は入れない。

### D7. 回転は MADCTL でやる。ソフトで座標変換しない

**理由**: 座標変換を全プリミティブの入口に置くと、フラッシュも実行時間も全経路で払う。対象コントローラは全部 MADCTL で回転できるので、**Panel が回転ごとの MADCTL 値を持ち、`width()`/`height()` を入れ替えるだけ**で済む。

**代償**: パネルが対応していない回転（一部の e-Paper 等）には使えない。対象外なので問題ない。原点オフセットが回転で変わる個体（ST7789 240x240 など）があるので、**Panel は回転ごとに 4 通りのオフセットを持つ**必要がある。

### D8. クリップ矩形を最初から入れる

MVP に入れる。memo では v0.2 相当だったのを**前倒し**。

**理由**: 画面外への描画をどこで落とすかは、後から足すと**全プリミティブに手が入る**。しかも各プリミティブが個別に画面外判定を書くと、そちらのほうが合計サイズが大きくなる。入口 1 箇所で落とすほうが小さく、正しい。

**逃げ道**: `TINYGFX_NO_CLIP` で判定を省ける。ただし画面外描画は未定義動作になる。**要実測** — 数バイトしか変わらないならスイッチ自体を消す。

### D9. 塗りつぶしは既定でバッファを持たない

`writeColor` の既定実装は 1 画素ずつの 16bit 転送。バッファ 0 バイト。

**理由**: 静的バッファを持つと、使わないスケッチも RAM を払う。SRAM 2KB では数十バイトも惜しい。速度は二番手（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §3）。

**逃げ道**: `TINYGFX_FILL_CHUNK` で**スタック上**の一時配列を使う。静的 RAM は増えない。ESP32 など余裕のある機種向け。

### D10. RST は Panel、CS / DC は Bus が持つ

**理由**: RST の波形（Low 保持時間、解除後の待ち）は**コントローラの初期化列とセット**でしか意味を持たないので Panel の持ち物。CS / DC は転送のたびに叩くもので、Fast Backend では GPIO 直叩きに置き換えたい。よって Bus の持ち物。

**代償**: CS を共有する複数デバイス構成（別チップと SPI を共有）では、Bus を分けるか、Bus 側に外部 CS 制御のフックが要る。**v0.x では未対応。** 要相談（§2）。

### D11. バイトスワップは Bus の責務

`pushImage` / `writePixels` は**ホスト側バイト順の `uint16_t` 配列**を受け取り、MSB first への変換は Bus が行う。

**理由**: 変換位置を上位に置くと、DMA でバッファをそのまま流したい Fast Backend が変換をやり直すことになる。Bus に寄せておけば、**すでに正しい並びのデータを持っている環境では変換を素通しにできる。**

**暫定**: LovyanGFX の `setSwapBytes` に相当する「入力はもう入れ替え済み」を伝える手段が要るかどうか。要相談（§2）。

### D12. フォントは明示的に `setFont()` するまで未設定

**理由**: 既定フォントを暗黙に指すと、文字を一切使わないスケッチにもフォントデータ（6x8 ASCII で約 570 バイト = V003 フラッシュの 3.5%）が載る。

**採らなかった案**:
- *既定フォントを常に持つ* — 使い勝手は良いが、上記のとおり払わない人が払う。
- *`TINYGFX_DEFAULT_FONT` を定義したときだけ既定を持つ* — **こちらのほうが良いかもしれない。** 未設定で `drawString` を呼んで何も出ないのは事故りやすい。要相談（§2）。

### D13. スプライト / オフスクリーンをコアに持たない

**理由**: 全画面バッファは 240x240 RGB565 で 115KB。V003 はもちろん、CH32V20x でも載らない。「ある機種でだけ動く API」をコアに置くと、ライブラリの前提が曖昧になる。

**将来**: やるなら別クラス・別ヘッダ。コアの API は変えない形で足せる。

### D14. 名前は LovyanGFX に寄せるが、互換表も互換レイヤも作らない

**理由**: 名前を寄せるのは**利用者が覚え直さなくて済むように**であって、移植互換のためではない。互換表を作った瞬間、LovyanGFX の仕様変更に追随する義務が生まれる。TinyGFX が背負うものではない。

**具体**: 対応表は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §11。文書では LovyanGFX の仕様を説明しない。

**2026-08-29 改訂 — 対外的には特定の名前を出さない。**

README で「LovyanGFX に似た書き味」と名乗るのをやめ、
**「Arduino のグラフィックスライブラリでおなじみの書き味」**に変えた。

理由は 3 つ。

1. **事実として、寄せている名前は LovyanGFX 固有ではない。**
   `fillRect` / `drawString` / `setRotation` / `startWrite` は
   Adafruit_GFX・TFT_eSPI・LovyanGFX・M5GFX が共通して使う語彙で、
   1 つの名前を出すのは正確でない
2. **互換の期待を招く。** 名指しすると「では `pushSprite` は？」という
   問い合わせが来る。D14 の趣旨（互換表も互換レイヤも作らない）と噛み合わない
3. **相手の看板を借りる形になる。** 提携も承認もない

**技術的な比較で名前を出すのは続ける。**
[COMPARISON.ja.md](COMPARISON.ja.md) は比較が本題だし、
「LovyanGFX はこれを 2 通りで提供しているが、こちらは片方だけにした」
のような**判断の根拠**として挙げるのは、むしろ誠実。
やめたのは**看板としての名指し**だけ。

### D15. 「未使用なら落ちる」をリンカ任せにせず、構造で保証する

未使用機能が最終バイナリに載らないのは **`--gc-sections` の仕事**でよい。TinyGFX 側の責務は、**リンカが落とせる形を壊さないこと**。規則の一覧は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.4（R1〜R9）。

**理由**: 落ちなくなる原因はほぼ「参照の連鎖」で、しかも**気づきにくい**。`fillScreen` しか呼んでいないスケッチが 2KB 太っていても、原因は「コアのどこかに 1 行 `Serial.print` がある」だったりする。増分を細かく見る運用（[FOOTPRINT.ja.md](FOOTPRINT.ja.md)）と組み合わせないと、後から効いてくる。

**採らなかった案**:
- *「小さく書く」という心がけだけで運用する* — レビューで毎回すり抜ける。特に R4（デバッグ出力）と R9（関数内 static）は入れた本人に自覚がないまま入る。
- *全部を `#ifdef` で切る* — 確実だが構成数が爆発してテストで守れなくなる（D6 と同じ理由）。

**守り方**: 構成ごとに「載っていてはいけないシンボル」を最終バイナリで検査する `tests/linkprune/`。たとえば **構成 A（`fillScreen` のみ）のバイナリに `drawCircle` / フォントデータ / `Print` のシンボルが 1 つでもあれば fail。** これが D1 / D6 / D12 / R1〜R9 の実効的な担保になる。

### D16. ちらつき対策は「MemoryTarget を挟む」で実現する。コアは変えない

LGFXVirtualCanvas と同じ帯レンダリングを最初から入れる。ただし**描画コアには一切手を入れない。**

`TinyGFXTarget` を実装した `TinyGFXMemoryTarget`（RAM バッファへ書くパネル）を
実パネルの手前に挟み、`TinyGFXTileCanvas` が帯ごとに「クリア → 描画コールバック → 転送」を回す。

**理由**: フレームバッファが無い以上、消してから描くとちらつく。全画面バッファは
240x240 RGB565 で 115KB あり CH32V20x でも載らない。**帯ならバッファは幅 × 行数 × 2 バイト**で、
240px × 1 行 = 480 B。CH32V003 でも成立する。
そして TinyGFX の層構造では Panel が既に仮想化されているので、**新しい抽象を 1 つも足さずに実現できる**。

**測った値札**（[FOOTPRINT.ja.md](FOOTPRINT.ja.md) §5）: Flash +1,064 B、RAM +560 B（240×1 行）。
使わなければ 0 バイト（別ヘッダなので include しなければリンクされない）。

**副次的な効果**: 描画を `void (*)(TinyGFX&, void*)` の関数にする形になるので、
**同じ描画関数をホストのテストからも呼べる**。`TinyGFXMemoryTarget` を全画面サイズで使えば
そのままフレームバッファ検証になる（[TEST_PLAN.ja.md](TEST_PLAN.ja.md) §2）。

**採らなかった案**:
- *別ライブラリにする* — LGFXVirtualCanvas が別ライブラリなのは LovyanGFX が外部だから。
  TinyGFX は両側とも自分のものなので、**別ヘッダに分ければフットプリント上は外部ライブラリと同じ**で、
  バージョン整合の手間だけが減る。
- *描画コアに仮想の描画先を持たせる* — D1 に反する。
- *ダーティ矩形だけを再描画する* — バッファ 0 で済むが、何が変わったかはアプリしか知らない。
  ライブラリの仕事ではない。**GUIDE で「いちばん安いちらつき対策」として案内する**（不透明背景の文字、
  消さずに上書き）。

**制約**: 描画コールバックは帯の数だけ呼ばれる。重い前処理をコールバックに書くとその回数だけ走る。

### D17. フォント形式は CellFont。**形式の仕様は TinyGFX の外に置く**

**2026-08-28 再改訂。GFXfont → TinyFont（独自）→ CellFont（外部仕様）と 2 度動いた。**

| 日付 | 形式 | 何が変わったか |
| --- | --- | --- |
| 2026-08-26 | GFXfont | 既存資産をそのまま食う案 |
| 2026-08-27 | TinyFont（独自） | 索引とグリフ表を生成時に選ぶ。GFXfont より 236 B 小さい |
| **2026-08-28** | **CellFont v1** | **仕様を LGFXFontToolJs 側の文書に切り出した** |

**仕様を外に置く理由。** 形式は生成器と描画器の**間**の取り決めであって、どちらか一方の
持ち物ではない。TinyGFX の docs に置くと、生成器（LGFXFontToolJs）が TinyGFX の内部文書を
読まないと実装できないことになる。**仕様は
[LGFXFontToolJs `docs/formats/cellfont.ja.md`](https://github.com/tanakamasayuki/LGFXFontToolJs)
が正**で、TinyGFX はその描画器の 1 実装にすぎない。

**名前が TinyFont から変わった理由**は、TinyFont が他所で使われている語だったため。
「全グリフが 1 つのセルを共有し、字ごとに持つのは変わるものだけ」から CellFont。

**TinyFont から実質的に増えたもの**（どれも TinyGFX 側の実装に取り込み済み）:

- **頭ブロック（`headCount`）** — 疎索引でも連続部分にコード表を付けない。ASCII 95 字 + 記号 6 字で −190 B
- **形式内の連鎖（`CellFont::next`）** — セル幅クラスで分けて固定ピッチを立てる。8px 混在 190 字で −690 B
- **U+FFFD への退避** — 豆腐を出すかどうかが「文字集合に U+FFFD を入れるか」という生成時の選択になる
- **ベースライン基準** — 連鎖する各フォントが別々の高さを持てる

代金は **+248 B**（うち U+FFFD 退避が 64 B）。最初の実フォント 1 本で返ってくる。
数字は [FONT_FORMAT.ja.md](FONT_FORMAT.ja.md) §2。

以下は TinyFont を選んだときの理由。**CellFont でもそのまま成立している。**

**理由 1 — GFXfont のグリフ表が重い。** ASCII 95 字の 5x7 固定ピッチで、
ビットマップ 475 B に対しグリフ表が 665 B。しかも固定ピッチなら**中身は全字同一**で
丸ごと冗長。CellFont は固定ピッチならグリフ表を持たない（`glyphs = nullptr`）ので、
**同じフォントが 1,152 B → 499 B（−57%）**になる。

**理由 2 — GFXfont は疎な文字集合を表せない。** `first`〜`last` が連続でなければならず、
CJK のサブセット（U+4E00〜U+9FA5 に散った 500 字）だと 20,902 件のグリフ表 = **146 KB**
が要る。CellFont は昇順のコード表を持てる（`codes != nullptr`）ので 1 KB で済む。

**理由 3 — 両方に対応するコストが小さい。** 索引 2 通り × グリフ表 2 通りの 4 組を
1 つのデコーダが扱い、**分岐のコストは合計 76 バイト**（疎索引 56 B、レコード 24 B）。
節約（ASCII で 653 B、CJK で 145 KB）に対して誤差。しかも**デコーダ全体は
GFXfont 版より 24 バイト小さい**（ascent の走査が消え、レコードが 7 → 4 バイトになったため）。

**選択は実行時ではなく生成時に済ませ、結果をデータで表す。** どちらもポインタが
`nullptr` かどうかで決まるので、利用者がフラグを意識することはない。

**採らなかった案**:
- *GFXfont のまま* — 既存の Adafruit 資産をそのまま使えるのが利点だった。
  だが ASCII で 653 B 損し、CJK は表現できない。**ビットマップの並びは GFXfont と同じ**に
  してあるので、**ツール側で変換できる**（互換は失われない、手順が 1 つ増えるだけ）。
- *u8g2 形式* — データは最小だがデコーダが大きい。圧縮の効きは 16px で 3%、8px で 13%
  しかない（別途の測定）。**割に合わない。**
- *コードの再マップ（連番へ振り直す）* — 疎索引比で 9% しか縮まないうえ、
  **文字列リテラルがそのまま使えなくなる。**
- *グリフごとの bbox（GFXfont 方式）* — 可変ピッチのビットマップは縮むが、
  グリフ表が 4 → 7 バイトに増える。5x7 級では表の増加が勝つ。
  大きな欧文フォントでは逆転しうるので、**必要になったら測って決める**。

**同梱しない理由**: プリセットを持つと、使う人が選んでいないフォントの分まで
リポジトリとレビューの対象になる。フォントは**スケッチ側に置くもの**にしておけば、
サブセット化の運用（プロジェクトで使う文字だけ）と自然に噛み合う。

**残っている作業**: [EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E4（LGFXFontToolJs の
CLI）。**2026-08-28 に公開され、テストと examples のフォントはすべて CLI の出力に
差し替えた。** つなぎだった `tools/gen_font.py` は削除。

### D18. 既定の Bus はハードウェア SPI ではなくソフト SPI にする

`TinyGFXBusSoftSPI`（`pinMode` / `digitalWrite` のビットバン）を第一の実装として持つ。

**理由**: 主ターゲットの CH32V003 で、**Arduino 標準の SPI が使えない**ことが実測で分かった。

| コア | CH32V003 での状況 |
| --- | --- |
| `ch32-riscv-arduino:ch32riscv` | SPI ライブラリが**存在しない** |
| `WCH:ch32v` | SPI はあるが `PinMap_SPI_*` が無く**リンクできない** |
| `UIAP:ch32v` | 同上 |

「Arduino 標準 API だけで成立させる」という原則を突き詰めると、**確実にあるのは
`pinMode` と `digitalWrite` だけ**だった。ソフト SPI はどのコアでも必ず動く。

**代償**: 遅い。だが速度は二番手（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §3）。
速度が要る環境では `TinyGFXBusSPI`（ハードウェア SPI）に 1 行で差し替えられる。

**関連**: [EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E2 / E3。コア側が直れば
`TinyGFXBusSPI` が使えるようになるが、**それを待たずに進める**。

### D19. AVR ではフォントを PROGMEM から読む

フォントのビットマップ・グリフ表・`GFXfont` 構造体を、AVR では `pgm_read_*` 経由で読む。
それ以外のアーキテクチャでは素の参照に展開され、**1 命令も増えない**（実測でむしろ 12 B 減った）。

**理由**: Arduino Uno R3（32KB / 2KB）で全構成のビルドが通ることを確認したが、
**フォントが RAM に載ると使い物にならない**。実測:

| 構成 | RAM（対応前） | RAM（対応後） |
| --- | --- | --- |
| D（文字あり、32 文字フォント） | 511 B | **119 B** |
| E | 519 B | **127 B** |

32 文字で 392 B。ASCII 全域（95 文字）なら 1.2KB で、**2KB の 60%** を持っていかれる。
フラッシュは 32KB あって余裕（構成 E で 23%）なので、**AVR で効くのは RAM だけ**。
ここを塞げば UNO は実用になる。

**採らなかった案**:
- *AVR を対象外にする* — フラッシュに余裕があるのに RAM だけで諦めるのはもったいない。
  対応は `tinygfx_rd8` / `rd16` / `rdptr` の 3 つの inline 関数で済み、非 AVR は 0 コスト。
- *PROGMEM 版の API を別に生やす*（`drawStringP` など）— API が 2 系統になる。
  Adafruit も LovyanGFX も「フォントは常に PROGMEM」で統一しているのでそれに倣う。

**制約**: **AVR ではフォントデータを 4 つとも PROGMEM に置くこと。**
ビットマップ・グリフ表・コード表・**フォント構造体そのもの**。
逆に `TinyGFXFontRef` / `TinyGFXFontOps` は素の const（RAM）に置き、素の参照で読む。

**2026-08-28 に不具合を 1 件直した**（当時のつなぎ生成器 `tools/gen_font.py`。現在は削除）。それが
`TinyGFXFontTiny` **構造体だけ** `TINYGFX_FONT_PROGMEM` を付けずに出していた。
デコーダは `tinygfx_rd16(&f->count)` のように**全フィールドを PROGMEM 経由で読む**ので、
AVR では `pgm_read_word` が RAM のアドレスをプログラム空間として読み、**文字が化ける。**

`avr-nm` で確認した実際の配置:

| シンボル | 修正前 | 修正後 |
| --- | --- | --- |
| `...Bitmaps` | `t`（フラッシュ） | `t` |
| `...Data`（構造体） | **`d`（RAM）** | **`t`（フラッシュ）** |
| `TinyGFXFontRef` | `d`（RAM。正しい） | `d` |

**ホストのテストでは捕まらない。** Tier 1 は `lang-ship:host` で走り、そこでは
`tinygfx_rd*` が素の参照に展開されるため、置き場所の間違いが表に出ない。
Tier 2 は AVR でビルドするだけで実行しない。**AVR の実機（M1 相当）でしか出ない類**。

CellFont 仕様（§12.2）が「4 つすべてに付ける。どれか 1 つでも抜けると化ける」と
明記しているのは、まさにこの失敗の形である。

LGFXFontToolJs 側も付くはず（[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E4-3 で確認中）。

**`pushImage` の画像データは RAM 上のもののみ。** AVR で PROGMEM の画像を渡す道は
用意しない —— フラッシュの画像は `drawImage` に寄せる（D27 で決着）。
なお **AVR 以外ではこの区別が無い**（フラッシュがアドレス空間に見えているので、
`const uint16_t[]` をそのまま `pushImage` に渡せる）。

### D20. フォント形式はフォント側がデコーダを指す（コアは形式を知らない）

`setFont()` に渡すのは `TinyGFXFontRef`（データ + `TinyGFXFontOps` + `next`）。
コアは連鎖をたどって `ops->draw` を呼ぶだけで、**形式を 1 つも知らない。**

**理由**: 複数の形式に対応しつつ、**使っていない形式のデコーダを 1 バイトも載せない**
ための唯一の形だった。コアが形式ごとの `setFont` オーバーロードを持つと、
コアがすべてのデコーダを参照することになり R3 を破る（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.4）。

**実測で確かめたこと**（[FONT_FORMAT.ja.md](FONT_FORMAT.ja.md) §4）:

- CellFont だけのスケッチに u8g2 のシンボルは **0 個**（`nm` で確認、`tests/linkprune/` が常時検査）
- CellFont のスケッチに u8g2 を足すと約 +1,180 B。**使わなければ +0 B**
- 仕組みそのものの代金は **+144 B**。うち 124 B は「定数畳み込みが効かなくなったぶん」で、
  `-DTINYGFX_FONT_SPARSE=0 -DTINYGFX_FONT_RECORDS=0` で取り戻せる（CellFont では −164 B）

**2026-08-28 追記 — この形が仕様に取り込まれた。** CellFont は形式の中にも連鎖
（`CellFont::next`）を持つので、TinyGFX では連鎖が 2 段になる。このとき
**U+FFFD への退避をデコーダの中でやると、その形式に豆腐があるだけで後段の別形式に
到達できなくなる。** 退避は最外（`TinyGFX::drawChar`）でだけ行う。
これは TinyGFX 側から指摘して仕様 §15.2 に入った。

**採らなかった案**:
- *形式ごとの `setFont` オーバーロード* — 素直だが、コアが全形式を参照する。R3 違反。
- *テンプレートで形式を静的に結ぶ* — サイズが読めなくなる（D2 と同じ理由）。
  連鎖で形式を混ぜられなくもなる。
- *形式を 1 つに絞る（CellFont だけ）* — 一番小さいが、CellFont が負ける帯がある
  （H>16 かつ字数が多いとき。CellFont 仕様 §13.5）。その外を扱う道を塞ぐ。

**2026-08-28 追記 — 形式をまたぐ連鎖は外した。** 一時は `TinyGFXFontRef::next` で
「半角 CellFont + 全角 u8g2」を書けるようにしていたが、**フォントツールが
その混合をやってくれる**（文字集合をまるごと 1 回生成すれば、中で幅クラスに割る）ので、
プログラム側に二重に持つ必要が無い。代金は **40 バイト + `TinyGFXFontRef` 4 バイト/本**
（実測）。**形式を選べることは残り、混ぜられることだけが無くなった。**
形式の中の連鎖（`CellFont::next`）は仕様の要求なのでそのまま。

**R2 との関係**: 「関数ポインタの表を持つな」は**全機能を並べた表**（1 つ使うと全部載る）を
禁じたもの。ここの表は形式ごとに 1 枚で、その形式を include した人だけが参照する。
**むしろ R2 の目的を達成するための道具になっている。**

### D21. モノクロパネルは Panel がフレームバッファを持つ。描画 API は RGB565 のまま

I2C のモノクロ OLED（SSD1306）に対応するにあたり、**コアには一切手を入れなかった。**
`TinyGFXBusI2C` と `TinyGFXDriverSSD1306` を足しただけ。

**理由**: 色深度をコアで抽象化すると（`setColorDepth` のような形）、変換の分岐が
全描画経路に載る（D4）。一方、**RGB565 を受け取って 1bpp に落とすのは Panel の仕事**として
閉じ込めれば、カラーパネルの利用者は 1 バイトも払わない。
`TinyGFXTarget` のインターフェースは既にこれを許していた（`writeColor` / `writePixels` を
受け取って何をするかは Panel の自由）。

**フレームバッファは Panel が持ち、バッファは利用者が用意する。** SSD1306 は GRAM を
読み戻せずページ単位でしか書けないので、任意の描画にはビットを手元に持つしかない。
128x64 で 1,024 バイト。**動的確保はしない。**

**転送は `display()` まで遅延する。** 描くたびに 1KB 流すと I2C 400kHz で 25ms かかる。
**変更のあったページだけ**流すので、1 ページに収まる変更なら 128 バイト（実測で確認）。

**採らなかった案**:
- *描くたびに自動で流す* — API は素直になるが、上記のとおり実用にならない。
  `display()` を明示させるのは SSD1306 を使う人には馴染みのある形でもある。
- *TileCanvas で帯ごとに流す* — フレームバッファを持たずに済むが、`MemoryTarget` は
  RGB565 なので 128x8 の帯で 2,048 バイト要る。**1bpp のフレームバッファ 1,024 バイトより大きい。**
  モノクロでは素直に持つほうが小さい。
- *色深度をコアで抽象化する* — D4 のとおり。

**実測**: フラッシュは SPI + ST7789 より **332 バイト小さい**（初期化列が短く、
画素の転送がバッファ書き込みで済むため）。RAM は +1,040 バイト。
CH32V003（2KB）でも Uno R3（2KB）でも載る。

### D22. 実機の 1 台目は M5Stack（ILI9342C）。ガラスの向きは実行時の逃げ道で吸収する

**決定。** 実機確認の最初の 1 台を **M5Stack Core / BASIC** とし、そのために
`TinyGFXDriverILI9342` を用意する。MADCTL のベース値（ガラスの貼り付き向き）と色順は
**実機で確かめるまで確定しない**ので、`setMirror()` と `setRgbOrder()` を残す。

**理由 1 — 切り分けができる。** CH32V003 + ST7789 モジュール（M1）から始めると、
出なかったときに配線・電源・コア・ライブラリのどれが悪いのか分からない。M5Stack は
**配線が無く**、ピンが決まっていて、電源が安定していて、フラッシュにも余裕がある。
「ライブラリは動く」を先に確定させてから、条件の厳しい方へ降りる。

**理由 2 — ILI9342 は ST7789 とコマンドが同じ。** `0x2A/0x2B/0x2C/0x36/0x3A` はそのまま。
差は実質 3 点（色順が BGR、GRAM が最初から横長で回転 0 が 320x240、ガラスの向き）だけ
なので、パネルクラスは 135 行で済む。`BusCapture` もそのまま使えるので、
ホスト側で `tests/ili9342/` として表の検算までできる。

**逃げ道を残す理由。** ILI9342C のモジュールは向きが 1 通りではない。
ここで既定値を当てずっぽうで固めると、外れたときに利用者はライブラリを直すことになる。
`setMirror(mx, my)` を置いておけば**スケッチ 1 行**で直せる。
片軸だけのミラーは回転では作れないので、`setRotation` では代用できない
（両軸ミラーは回転 2 と等価。`tests/ili9342/` がこの関係を検算している）。

**M5Stack で正しい値が分かったら**、`TinyGFXDriverILI9342::setRotation()` の既定に
畳み込み、`tests/ili9342/` の期待値も直す（[MANUAL_TEST.ja.md](MANUAL_TEST.ja.md) M0）。

**採らなかった案**:
- *ST7789 クラスを 320x240 で流用する* — 実際ほとんど動くはずだが、色順が RGB 固定なので
  赤と青が入れ替わる。BGR ビットを ST7789 側に足すと、ST7789 の利用者が使わない分岐を払う。
- *ILI9341 と共通の基底に載せる* — 継承で共有すると vtable 経由で両方の初期化列が
  リンクに残りうる（§7.4 R6）。パネルは**それぞれ独立したヘッダ**にする。
- *M5Unified / M5GFX のピン定義を参照する* — 依存が増える。ピンは 5 本なので例に直書きする。

**実測（2026-08-28、M5Stack BASIC）**: **M0 通過。TinyGFX が初めて実機に絵を出した。**
MADCTL のベース値・色順・回転 0 の向きは**既定のまま正しかった**ので、
`setRotation()` の表は変更しない。

**反転だけ世代で違った。** 手元の BASIC は `INVON`（既定）で正しく、
**古い世代の BASIC は反転していた**。既定は多数派の `INVON` のまま置き、
スケッチ側で `invertDisplay(false)` を 1 行外す形にする
（`examples/M5StackBasic` にコメントアウトで用意した）。
パネルクラスに世代の検出を持ち込むと、読み出し（`0x04` RDDID）が要る。

**2026-08-28 訂正。** ここで当初「バスに読み出しを足すコストのほうが高い」と書いたが、
**測ったら +8 バイトだった**（`TinyGFXBus::readData()` の vtable 枠ぶん。
[FOOTPRINT.ja.md](FOOTPRINT.ja.md) §5 の改定記録）。理由づけが間違っていた。

それでも**自動判別は入れない**。判別のコードと分岐は、そのパネルを使う全員が
`init()` で払うことになる一方、直し方はスケッチ 1 行で、しかも
**利用者は自分の基板の世代を知っている**。読み出しそのものは別の用途
（実機の自動検証。[MANUAL_TEST.ja.md](MANUAL_TEST.ja.md) M0b ページ 10）で使う。

`invertDisplay()` / `setSleep()` / `displayOn()` は **`init()` の後にしか効かない。**
前に呼ぶとバスが未初期化で、通っても `init()` の初期化列に上書きされる。
ヘッダと例の両方に明記した。**設定として先に積めるようにはしない** —
そのための `bool` を持つと、使わない利用者も RAM を払う（D15）。

### D24. SPI / Wire は**初期化済みのインスタンスを受け取る**（2026-08-28）

`TinyGFXBusSPI` と `TinyGFXBusI2C` は、**すでに `begin()` されたバスを受け取る。**
TinyGFX がバスを初期化することはない。

```cpp
TinyGFXBusSPI bus(SPI, /*dc*/27, /*cs*/14);   // 第 1 引数がバス
...
SPI.begin();      // スケッチの責任
lcd.begin();
```

**理由: 同じ線に別のデバイスが居るのが普通だから。** M5Stack では LCD と SD カードが
SPI を共有している。ライブラリが `SPI.begin()` をピン付きで呼ぶと、**先に居た相手の
設定を上書きしてしまう。** どちらが先に `begin()` するかで結果が変わる作りは、
利用者から見て理由の分からない不具合になる。

**共有の仕組みは Arduino 標準のトランザクションに任せる。** `beginTransaction` /
`endTransaction` で囲むのは今までどおりで、これが speed / mode / bit order の
調停をしてくれる。ライブラリが足すべきものは何もない。

**TinyGFX が自分で握るのは DC と CS だけ。** これはこのパネル専用の線なので、
`init()` で `pinMode` する。

**変えた点**:

| | 前 | 後 |
| --- | --- | --- |
| SPI | `TinyGFXBusSPI(dc, cs, freq, SPI, initSpi=true)` | `TinyGFXBusSPI(SPI, dc, cs, freq)` |
| I2C | `TinyGFXBusI2C(addr, chunk, Wire, initWire=true)` | `TinyGFXBusI2C(Wire, addr, chunk)` |

**バスを第 1 引数にした**のは、既定値を持てなくして「渡し忘れ」をコンパイルエラーに
するため。`initSpi` のようなフラグは消した。**フラグで切り替えられると、
どちらの設定が効いているのか読んで分からなくなる。**

**フットプリントは変わらない**（`Wire.begin()` の呼び出しがライブラリから
スケッチへ移っただけ）。

**残っている例外**: `TinyGFXBusSPI::setReadPins()` を使ったときだけ、読み戻しの
ために `SPI.end()` / `SPI.begin()` を呼ぶ（線の向きを変えるのに必要）。
**明示的に呼んだ人だけが踏む**うえ、ヘッダに「他のデバイスと共有している線では
使うな」と書いてある。この経路は実験扱い（D22 の追記）。

**ソフト SPI（`TinyGFXBusSoftSPI`）はこの話の外。** SCK / MOSI / DC / CS を
すべて自分で握る作りで、周辺機を共有していない。

### D25. モノクロは専用エンジンにしない。パネル側で吸収する（2026-08-28）

**決定。** 1bpp 専用の描画エンジンは作らない。`TinyGFX` 1 本のまま、
モノクロ特有の事情は `TinyGFXDriverSSD1306` の中で処理する。

**専用エンジンの代金**: `Gfx.h` の約 450 行（全プリミティブ・クリップ・回転・
文字のディスパッチ）を複製することになる。さらに**フォントのデコーダが
`TinyGFX&` を受け取る**ので、そちらも複製かテンプレート化が要る。
D1（virtual を置かない）と D4（色深度を抽象化しない）で避けた「2 つ持つ」構造が戻る。

**専用エンジンで得られるはずのものは、測ったらパネル側で取れた。**

| 期待した利点 | 実際 |
| --- | --- |
| バイト単位で塗れる | **パネル側で取れる。** 窓と画素数は既に渡っている（`TINYGFX_MONO_FAST_FILL`） |
| 色が 1 ビットで済む | `uint16_t` はレジスタ渡し。ほぼ効かない |
| フレームバッファが要らない | **パネル側で取れる**（`setBandPage()`。RAM 1,612 → 716 B） |

**そして本当に重いのは描画ではなかった。** 128x64 の 1 フレームで、
塗りが約 6.8ms に対し **I2C 400kHz の転送が約 23ms**。エンジンを速くしても
2 割しか動かない。

**実測**（CH32V003、構成 D 相当）:

| | flash | RAM |
| --- | --- | --- |
| 全面バッファ | 12,160 | 1,612（79%） |
| 帯（1 ページ） | 12,340 | **716（35%）** |
| 速い塗りを切る | 11,648 | 1,612 |

数字は [FOOTPRINT.ja.md](FOOTPRINT.ja.md) §6.4。

**採らなかった案**:
- *1bpp 専用エンジン* — 上記。複製に見合わない
- *コアに色深度の抽象を入れる* — D4 のとおり。全描画経路に載る
- *帯を専用クラスにする（モノクロ版 TileCanvas）* — `setBandPage()` + `setClipRect()`
  の 2 行で書けるので、クラスにするほどではない。**利用者が for を書く**ほうが、
  何が起きているか読める

### D26. 文字列は既定で UTF-8 として読む（2026-08-29）

**`drawString` / `textWidth` / `TinyGFXPrint::print` は `char*` を UTF-8 として
読む。`TINYGFX_FONT_UTF8` を 0 にするとバイト単位（Latin-1）に戻る。**

Q12 の決着。

**選んだ理由は「CJK が出したい」ではない。**
スケッチの文字列は、誰かが選んだわけでもなく最初から UTF-8 になっている
（Arduino IDE がそう保存する）。`"25°C"` はソースの時点で 5 バイトである。
バイト単位で読むと**度記号 1 つが 2 文字、仮名 1 つが 3 文字**になり、しかも
黙ってそうなる。つまり既定がバイト単位だと、CJK を使う気のない利用者が
`"25°C"` と書いただけで壊れる。**「使わなければ困らない機能」ではなかった。**

証拠として、テスト側に既に手書きの復号器（`tgfxDrawUtf8`）があり、
`tests/u8g2` と `tests/clifont` が使っていた。**入れる前から 2 か所が必要と
していて、しかもその手書きは切れた列で終端を飛び越える**（コアに入れて削除した）。

**実測**（`TINYGFX_FONT_UTF8=0` との差）:

| | CH32V003 | AVR Uno | ESP32 |
| --- | ---: | ---: | ---: |
| 構成 D（`drawString`） | **+164** | +134 | +116 |
| 構成 T | **+148** | +160 | +120 |
| 構成 P1（`TinyGFXPrint` も） | **+292** | +282 | +308 |
| RAM（P1） | +4 | +4 | 0 |

`TINYGFX_FONT_UTF8=0` は**バイト単位だった頃と 1 バイトも違わない値に戻る**
（11,828 / 7,334 / 262,784 を実測で再現）。切り落としが本当に切り落としで
あることの確認。

`TinyGFXPrint` だけ倍近く高いのは、`Print::write(uint8_t)` が 1 バイトずつ
渡してくるので、**組み立て途中のコードポイントを状態として持つ**必要が
あるから。`drawString` は文字列全体を見られるので状態が要らない。

**決めたこと**:

| 事項 | どうしたか | なぜ |
| --- | --- | --- |
| U+FFFF 超 | U+FFFD を返す。**ただし 4 バイト全部消費する** | フォントの入口が `uint16_t`。消費し損ねると後ろが全部ずれる |
| 途中で切れた列 | U+FFFD。**壊れたバイトの手前で止まる** | 終端を飛び越えると文字列の外を読む |
| 先導のない継続バイト | U+FFFD。1 バイトだけ消費 | 1 バイトの誤りで 1 文字だけ失う。行の残りは無事 |
| 冗長符号化（overlong） | **拒否せず復号する** | 指しているのは元々描ける文字。ここは名前を解釈する構文解析器ではなく描画器なので、弾いても得るものがない |
| `nextCode` を公開する | 静的メンバとして公開 | 折り返しや部分幅を自前で計算するコードが**同じ歩き方**をしないと答えが合わない。呼ばなければ 0 B |

**採らなかった案**:
- *拡張ヘッダに分ける* — `drawString` はコアのメンバなので、別ヘッダから
  差し替えるには仮想化かテンプレートが要る。D1 に反する。マクロなら 0 B で
  外せる
- *`TinyGFXPrint` だけ別マクロにする* — マクロが増えるほうが害。UTF-8 が
  要らない利用者は 1 つ 0 にすれば両方戻る
- *冗長符号化を弾く* — 上表のとおり
- *`uint32_t` でコードポイントを持つ* — 絵文字が入るが、フォント側の入口を
  広げないと意味がない。AVR で 32bit 演算も増える。**上限は形式の話**なので、
  必要になったら `TinyGFXFontOps` ごと変える

### D27. フラッシュの画像は `drawImage` に寄せる。`pushImage` は RAM のみ（2026-08-29）

Q6 の決着。**`pushImagePgm` のような専用の入口は作らない。**

まず範囲を確かめたら、思っていたより狭かった。

| 経路 | PROGMEM | 理由 |
| --- | --- | --- |
| `drawBitmap` / `drawImage` | **対応済み** | `tinygfx_rd8` 経由で読む |
| `pushImage(const uint16_t*)` | **AVR だけ非対応** | `writePixels` に生ポインタを渡す速い経路 |

**CH32V003 と ESP32 では `const uint16_t[]` がそのまま `pushImage` に渡せる。**
どちらもフラッシュがアドレス空間に見えているので、`TINYGFX_IMAGE_PROGMEM` は
空に展開され、`tinygfx_rd8` はただの間接参照になる（`TinyGFX/Progmem.h`）。
**つまり穴は AVR だけ。** そして AVR には既に `drawImage` + raw565 がある。

問題は、その `drawImage` + raw565 が**遅すぎて代替になっていなかった**こと。

**実測**（32x32 の雑音、`TinyGFXBusCapture`）:

| | コマンド数 | 1 画素あたりのバイト数 |
| --- | ---: | ---: |
| 連ごとに `fillRect`（元） | **3,072** | 13 |
| 1 行 1 窓（現在） | **96** | 2.3 |

写真は連長が 1 なので、連ごとに `fillRect` を呼ぶと**画素ごとに窓を開く**ことに
なる。窓 1 つが CASET + RASET + RAMWR で 11 バイト、画素が 2 バイト。
2,048 バイトの画像を送るのに 13,312 バイト流していた。

**直した。** `drawRaw565` だけは `fillRect` を通さず、行ごとに窓を 1 つ開いて
流し込む。透過色があるときは不透明な区間ごとに窓を開く（窓は開いたら埋め切る
必要があるので、途中を飛ばすと後ろがずれる）。窓経路はクリップしないので、
**クリップは復号器側で行う**（そのために `clipX0()` などを公開した）。

**他の形式は直さない。** RLE は連が長いことを保証する形式なので、連ごとに
`fillRect` を呼ぶのが正しい。raw565 だけが「連が無い」ことを保証している。

**費用**（写真 1 枚を描くだけのスケッチ全体で比較）:

| | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| フラッシュ | **−32** | +118 | **−108** |

**基準機と ESP32 では減る。AVR だけ増える。** 増えるのはクリップ計算を 32bit で
やっているからで、これは避けられない —— `clipX0 - x` は x = -32768 のとき 32768 に
なり、**int16_t に収まらない。**

この桁溢れは実際に踏んだ。窓経路にした最初の版は 16bit で計算していて、
`c0` が負に化け、**画像データの手前を読んで 1,050,624 画素を送っていた**
（`tests/image_fmt/` の極端な座標が検出）。`fillRect` を通っていた頃は
コアがクリップしていたので起きなかった種類の間違いで、
**自分でクリップする経路を作るということはこれを引き受けるということ。**

16bit で正しく書く版（符号なしの差で桁溢れを避ける）も書いて測った:

| | CH32V003 | AVR | ESP32 |
| --- | ---: | ---: | ---: |
| 32bit（採用） | **10,124** | 6,076 | **261,780** |
| 16bit | 10,240 | **5,930** | 261,848 |

**基準機で +116、AVR で −146。** また逆転した（[OPTIMIZE.ja.md](OPTIMIZE.ja.md) J と
同じ形）。**基準機が勝つ**規則どおり 32bit を採る。

**採らなかった案**:
- *`pushImagePgm` を足す* — AVR 専用の入口が 1 つ増える。しかも AVR は RAM が
  2KB しかないので、`pushImage` の相手は元々小さなスプライトか、復号器から
  1 ブロックずつ来るデータで、どちらも RAM にある
- *`writePixels` に「PROGMEM か」の引数を足す* — Bus の仮想関数の形が変わる。
  全バス実装に載り、AVR 以外では常に偽の分岐になる

### D28. `TileCanvas::render` は関数ポインタとラムダの両方を取る（2026-08-29）

Q10 の決着。**どちらかを選ぶ話ではなかった。**

```cpp
canvas.render([&](TinyGFX& g) { g.fillCircle(ball.x, ball.y, 16, c); });
canvas.render(drawScene, &ball);   // これも残る
```

テンプレート版は**帯のループを複製しない。** 受け取った callable を
1 行のトランポリン経由で関数ポインタ版に渡すだけなので、2 つ目の呼び出し
箇所が払うのはトランポリン 1 個で、ループの複製ではない。

```cpp
template <class F>
bool render(const F& draw) {
  return render(&callThrough<F>, const_cast<void*>(static_cast<const void*>(&draw)));
}
template <class F>
static void callThrough(TinyGFX& g, void* ctx) { (*(const F*)ctx)(g); }
```

**実測**（構成 T 相当）:

| | CH32V003 | AVR Uno | ESP32 |
| --- | ---: | ---: | ---: |
| テンプレートを足しただけ（使わない） | **±0** | **±0** | **±0** |
| 捕捉なしラムダ vs 関数ポインタ | **±0** | **±0** | **±0** |
| 捕捉ありラムダ vs `void*` + 構造体 | **−16 / RAM −8** | −18 / RAM −6 | −24 / RAM −16 |

**捕捉ありのほうが小さい。** `void*` 版は状態を構造体にまとめて RAM に置く
必要があるが、ラムダは既にある変数を参照で捕まえるだけなので、詰め替えが
消える。実体化されないテンプレートは 0 バイトなので、**足すこと自体の代金も無い。**

関数ポインタ版を残すのは、トランポリンがそれを呼んでいるからでもあるし、
名前のついた関数のほうが読みやすい場面があるからでもある。

`tests/tile/` が「ラムダで渡しても 1 画素も違わない・転送画素数も同じ・
帯の数だけ呼ばれる」を固定している。

### D29. `setSwapBytes` は持たない。呼んだときだけ払う自由関数にする（2026-08-29）

Q4 の決着。**他ライブラリは全社が実行時のモードを持っているが、採らない。**

```cpp
tinygfx_swapBytes565(block, w * h);   // 呼ばなければ 0 B
lcd.pushImage(x, y, w, h, block);
```

**実測**:

| | CH32V003 | AVR Uno | ESP32 |
| --- | ---: | ---: | ---: |
| 実行時モード（`setSwapBytes`）— **使わなくても** | **+44 / RAM +4** | +28 / RAM +1 | — |
| 自由関数 — 使わなければ | **0** | 0 | 0 |
| 自由関数 — 使えば | **+32** | +88 | +24 |

実行時モードの代金は**画素ごとの分岐**である。`writePixels` は
「1 画素 2 バイトを出す」以外に何もしてはいけない唯一のループで、
そこに条件を置くと**バイト順を入れ替えない全員が毎画素払う**。

そのうえ、**TinyGFX が作るものはこれを必要としない。** バイト順は変換ツールが
ヘッダを書く時点で決まっていて、生成された画像は常にバス実装と一致している。
要るのは**外から来たデータ**だけ —— JPEG / PNG のデコーダやカメラが吐く RGB565。
それは必ず RAM 上にあるので、その場で入れ替えられる。

なお入れ替えは `pushImage` の**前**に済ませる。復号器のコールバックが
1 ブロックずつ渡してくる形（TJpg_Decoder など）とそのまま噛み合う。

**採らなかった案**:
- *Bus に `setSwapBytes` を置く* — 上記の実測
- *`writePixels` に引数を足す* — Bus の仮想関数の形が変わり、全実装に載る
- *入れ替え済みを前提にした `pushImage` の多重定義* — クリップの複製になる

`tests/image/` が「2 回かけると戻る」「かけると絵が変わる」「長さ 0 で触らない」
を固定している。

### D30. 色定数は 2 つの綴りを持ち、`TFT_*` は 1 つずつガードする（2026-08-29）

Q2 の決着。**どちらか 1 つを選ぶ問題ではなかった。マクロなので両方持って 0 バイト。**

| 綴り | ガード | 用途 |
| --- | --- | --- |
| `TFT_BLACK` … | **1 つずつ `#ifndef`** | TFT_eSPI / LovyanGFX からの移植がそのまま通る |
| `TINYGFX_BLACK` … | 無条件 | **奪われない名前。** 他ライブラリが先に定義していても TinyGFX の値 |

`TFT_*` をガードするのは共存のため。**その共存こそが `TINYGFX_*` を要る理由に
している** —— 他ライブラリが先に居れば `TFT_RED` は「向こうの」`TFT_RED` である。
いまはどのライブラリも同じ値を使っているが、「いまは同じ」は土台にならない。

**ガードを 1 つずつにしたのはこの作業で直した不具合。** 以前は `#ifndef TFT_BLACK`
1 つで 16 個全部を囲っていたので、利用者が `TFT_RED` だけを自分で定義していると
**再定義になる**（`TFT_BLACK` は未定義なのでブロックごと展開される）。
他ライブラリは 16 個全部を定義するので実害は出ていなかったが、
利用者が 1 つ定義しただけで壊れる形だった。

`tests/constructs/color/` が **static_assert だけのスケッチ**で、
`build_matrix` が 2 通り（素のまま／`-DTFT_RED=0x1234`）でコンパイルする。
**ガードを外すと落ちることを確認済み。** 増分は base と同じ = **0 バイト**。

### D31. 糖衣クラスは用意しない。バス・パネル・描画の 3 オブジェクトのまま（2026-08-29）

Q1 の決着。

**大きさの話ではない。実測でむしろ小さい**（CH32V003 ±0、AVR −70、ESP32 ±0）。
それでも用意しない。

**理由は、バスを利用者が持っていることが TinyGFX の売りだから。**

```cpp
TinyGFXBusSPI bus(SPI, DC, CS);      // ← この行が「このバスは私のもの」を表している
TinyGFXDriverST7789 panel(bus, 240, 240, RST);
TinyGFX lcd(panel);
```

TinyGFX は `SPI.begin()` も `Wire.begin()` も呼ばない（D24）。同じ SPI に SD カードが
ぶら下がっていれば、同じ `SPI` を渡すだけで共存する。**糖衣クラスは中でバスを
作ってしまうので、その関係が表現できなくなる。** 1 行に縮める代わりに、
このライブラリを選ぶ理由そのものを隠すことになる。

副次的な理由:

- **組み合わせが パネル × バス** で、いまでも 5 × 5。しかも構築引数が全部違う
  （ページ方式パネルはフレームバッファ、ILI9342 はミラー、SH1106 は列オフセット）
- **パネル固有の設定が出せなくなる。** `setOffset` / `setInvert` / `setMirror` /
  `setGramSize` を使うには結局 `lcd.panel().setOffset(...)` になり、
  隠したはずのオブジェクトが戻ってくる
- **初期化順が罠。** `class Kit : public TinyGFX` で `TinyGFX(_panel)` と書くと、
  基底は非静的メンバより先に構築されるので**まだ構築されていない `_panel`** を
  参照する。いまは TinyGFX がアドレスしか持たないので動いてしまうが、
  将来 TinyGFX の構築子がパネルを読んだ瞬間に静かに壊れる
- 呼び出し側は 3 行から 1 行になるが、その 1 行は**名前のない数字が 7 個並ぶ**

### D32. 基準機のコア移行は v1.0 の条件にしない（2026-08-29）

Q11 の決着。**移行はもう切り離せている。**

予算を「base からの増分」で持つようにした結果（[FOOTPRINT.ja.md](FOOTPRINT.ja.md) §5）、

### D33. `setTextWrap` は入れる。ただし既定は切（2026-08-29）

[COMPARISON.ja.md](COMPARISON.ja.md) の「この調査で見つかった自分の穴」#3 の決着。
**Adafruit にあって TinyGFX に無い、唯一の実用機能**だった。

`TINYGFX_TEXT_WRAP` を 1 にすると `TinyGFXPrint::setTextWrap()` が現れる。

**なぜ既定にしないか。** 折り返しを正しくやるには、**その文字が入るかを描く前に
知る**必要がある —— 入らない文字は次の行に置くのであって、端で切り取られた形で
描くのではない（Adafruit が描く前に判定しているのもそのため）。
それはフォントデコーダへの **2 本目の入口**（`draw` に加えて `advance`）で、
`write()` が参照した時点でリンカは落とせない。

| | CH32V003 | AVR Uno | ESP32 |
| --- | ---: | ---: | ---: |
| `TINYGFX_TEXT_WRAP=0`（既定） | **±0** | ±0 | ±0 |
| `=1`（折り返さない使い方でも） | **+164** | +190 / RAM +1 | +116 |

**0 の側は入れる前と 1 バイトも違わない**（12,396 / 8,154 / 263,952 を実測で再現）。

これは `setTextDatum` を入れなかったのと**同じ形**である（+204 B を、揃えを
一度も使わない人まで払う）。違うのは、datum が `drawCenterString` で完全に
代替できたのに対し、**折り返しには代替が無い**こと —— `Print` は 1 バイトずつ
来るので、呼び手が事前に幅を測れない。だから「入れない」ではなく
「**値札を見せて選ばせる**」にした。

**採らなかった案**:
- *既定で入れる* — 上の実測。印字する全員が払う
- *描いてから判定する* — 送り幅の照会が要らなくなるが、**入らない文字が端で
  切り取られた形で描かれてから**次の行が始まる。絵が違う
- *送り幅を固定値とみなす* — 可変ピッチのフォントで壊れる。
  `tests/textwrap/` が幅の違う字（数字 4 / '℃' 8）でそこを踏む

### D34. パネルはプリセット。ドライバとは別の層にして、カタログを同梱する（2026-08-30）

**利用者が名前を書くのはバスとパネルの 2 つだけ。** ドライバ・プロトコル・
ターゲットは内部の語で、スケッチには出ない（[GLOSSARY.ja.md](GLOSSARY.ja.md)）。

```cpp
#include <TinyGFX/BusI2C.h>
#include <TinyGFX/panels/SSD1306_128x64.h>

TinyGFXBusI2C bus(Wire);
static uint8_t fb[TinyGFXPanelSSD1306_128x64::kBufferBytes];
TinyGFXPanelSSD1306_128x64 panel(bus, fb);
```

**フォント（D17「データを 1 バイトも同梱しない」）とは方針が逆になる。**
理由が 2 つとも当てはまらないため —— プリセットは約 30 バイトで、
「使う文字」ではなく「買った製品」で決まる有限のカタログであり、
**同梱しないと最初の 1 枚が出ない。**

#### プリセットが実際に運ぶのは 2 つだけ

調査の結果、**ほとんどの値は導出できるか、コントローラのリセット値だった。**

| 値 | どこから来るか |
| --- | --- |
| 多重比 `0xA8` | **導出: 高さ − 1。** 既知の 9 品種すべてで一致 |
| 列オフセット | **導出: ガラスは RAM の中央。** 9 品種中 8 つで一致（★ 例外のみ上書き） |
| **COM ピン `0xDA`** | ★ **導出できない。** ガラスの COM 配線という事実。2 択 |
| プリチャージ `0xD9` | データシートのリセット値 `0x22` |
| VCOMH `0xDB` | データシートのリセット値 `0x20` |
| クロック `0xD5` | データシートのリセット値 |

**他ライブラリが送っている `0xF1`（プリチャージ）と `0x40`（VCOMH）は
データシートに無い値である。** `0x40` は VCOMH の表（00h/20h/30h）に載っていない。
1 つのライブラリの調整値が各社にコピーされている状態なので、TinyGFX は
リセット値を使う。**由来を説明でき、誰の作業成果でもない。**

#### 高さから COM ピンを推測していたのは間違いだった

`h == 32 ? 0x02 : 0x12` という導出を持っていたが、**反例が 2 つある。**

- **64x32** は h=32 なのに `0x12` が正解
- **128x64 alt0** は h=64 なのに `0x02` が正解

導出をやめ、データシートのリセット値を既定にしてパネルが上書きする形にした。

#### 同じドライバのパネルは 1 スケッチに 1 枚

2 枚 include すると **`#error` で止まる。** 止めないと `#pragma once` で 2 枚目が
黙って無視され、**1 枚目の値で 2 枚目を描く。** 絵は出るので気づけない。

ガードは**ドライバ単位**なので、TFT + OLED のように違うドライバの組は通る
（`tests/panels/` が両方を検査）。

**採らなかった案**:
- *実行時に設定を渡す（config 構造体 / init 列のポインタ）* — 使わないスケッチにも
  **+80〜88 B**（実測）。生成前提ならコンパイル時定数のままでよく、払う理由がない
- *ガラスごとにクラスを生成する（`#pragma once` を持たないヘッダ）* — 2 枚目の
  ガラスが **+160 B**（実測）で実現できるが、**同一ドライバ 2 枚を許すこと自体を
  やめた**ので不要になった
- *カタログを外部ツールから持ってくる* — **同梱しないとライブラリが使えない**

#### ドライバを足す代金（2026-08-30 実測、CH32V003）

| | 増分 |
| --- | ---: |
| **パネルを 1 枚足す** | **0**（include しなければコンパイルもされない） |
| **追加の初期化が要らない DCS ドライバ** | **+4 B**（ST7796） |
| ST7735 のパネル（GRAM 寸法 + オフセット付き） | +56 B |

**ST7735 にも初期化列を送らない。** 他ライブラリは frmctr / pwctr / ガンマを
送るが、**それらはデータシートのリセット値ではなく調整値**である
（Adafruit の FRMCTR1 は `0x01,0x2C,0x2D`、データシートのリセット値は
`0x05,0x3C,0x3C`）。SSD1306 のプリチャージと VCOMH をリセット値にしたのと
同じ理屈で、送らない。

必要になったときのために `DriverDcs` に「SLPOUT と COLMOD の間に列を差し込む」
フックを試作して測った。**使わないドライバには 0 バイト**（`init()` が
`nullptr` を渡すのでコンパイラが畳む）。**証拠が出てから入れる**ことにして、
いまは入れていない。

#### 副産物: example の不具合が 1 件見つかった

**240x240 の ST7789 は GRAM が 240x320 なので、回転 2 は GRAM の 80 行目から
始まる。** `setGramSize(240, 320)` を呼ばないとそれが 0 行目になり、回転 2 と 3 が
ずれる。`DriverST7789.h` のコメントには最初からそう書いてあったが、
**この repository の example は 4 本とも呼んでいなかった。**

パネルヘッダが呼ぶので直った。`tests/panels/` が回転 2 の開始行を固定している。
