# 設計決定

内部の記録。日本語のみ。**「なぜそうなっているか」の台帳。**

決定の内容そのものは [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) にある。ここには**理由と、採らなかった選択肢**を書く。

**まだ全部たたき台。** 実測で覆る前提のものには「**要実測**」と書く。

## 1. 確定させたい決定

### D1. 描画 API に virtual を 1 つも置かない

`TinyGFX` の描画メソッドはすべて非 virtual、ヘッダ内 inline。

**理由**: `--gc-sections` は呼ばれない関数を落とすが、**vtable から参照される関数は落とせない**。描画を virtual にすると、`fillRect` しか使わないスケッチにも `fillTriangle` や `drawCircle` が載る。CH32V003 の 16KB では致命的。非 virtual なら [REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §8 の「構成 A〜E の積み上げ」がそのまま成立する。

**採らなかった案**:
- *共通基底クラスに描画 API を virtual で持たせる（Adafruit_GFX 方式）* — パネル追加が楽で構造も素直。だが上記のとおり未使用 API を落とせず、TinyGFX の存在意義（V003 に載ること）を最初に潰す。
- *描画も含めて全部テンプレート* — サイズが読めなくなる。D2 参照。

**関連**: virtual を避けるだけでは足りない。参照の連鎖で落ちなくなる経路を塞ぐ規則が D15。

**代償**: `TinyGFX` を継承して描画を差し替える、という拡張ができない。スプライトのような「別の描画先」を後から足すときに、継承ではなく別クラスを書くことになる。**スプライトは非目標**（D13）なので今は許容する。

### D2. Panel と Bus だけを virtual にする。テンプレートにしない

**要実測。**

**理由**: 間接呼び出しのコストは**速度**であって**サイズ**ではない。速度は多少遅くてよい（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §3）。一方テンプレートはサイズが読めなくなるほうに効く。vtable 2 枚（合計 50 バイト前後）で、構成の見通しとビルドの軽さが買えるなら安い。

**採らなかった案**:
- *`TinyGFX<PanelST7789<BusSPI>>`* — 間接呼び出しが消えて理論上は最小・最速。だが inline 展開が呼び出し箇所ごとに転送ループを複製し、**かえって増えることがある**。「増分を細かく見て増やさない」という運用（[FOOTPRINT.ja.md](FOOTPRINT.ja.md)）と噛み合わない。型名とコンパイルエラーが重くなる副作用もある。
- *関数ポインタ表を手で持つ* — virtual と実質同じコストで、書くのが面倒なだけ。

**逃げ道**: `TINYGFX_STATIC_BUS` / `TINYGFX_STATIC_PANEL` で単一実装に固定し、virtual を消せるようにする（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.3）。**ただし Phase 0 で「virtual のままだと予算に入らない」と実測されるまで入れない。** 数字を見ずに複雑さを足さない。

### D3. Bus インターフェースに `writeColor(color, count)` を入れる

memo の Bus 案（`writePixels` のみ）から**変更**した。

**理由**: `writeColor` がないと `fillScreen` / `fillRect` が「画素数ぶんの `uint16_t` 配列」を要求する。240x320 なら 150KB で、SRAM 2KB の機種では原理的に不可能。数画素ずつのループで回避することもできるが、それは結局「同色連続転送」を上位で再実装しているだけで、Fast Backend が DMA で一気に流す道も塞ぐ。**インターフェースの最小性より、V003 で成立することを優先する。**

**採らなかった案**:
- *`writePixels` だけ残し、上位で小さなバッファを回す* — Bus は狭いままだが、バッファを誰が持つかの問題が上位に移動するだけ。静的バッファを持てば全スケッチが RAM を払う。
- *`fillRect` を Panel の責務にする* — Panel ごとに塗りつぶしを実装することになり、パネル追加のコストが上がる。

### D4. 色は RGB565 固定。型エイリアスを作らず `uint16_t` を生で使う

**理由**: 色深度を抽象化すると、変換テーブルか変換関数分岐が全経路に載る。対象パネルは全部 RGB565 なので、抽象化の対価に見合わない。型エイリアス（`tinygfx_color_t` 等）も、結局 `uint16_t` の別名でしかないなら**利用者が覚える名前が 1 つ増えるだけ**。

**採らなかった案**:
- *強い型（`struct Color565`）* — `fillRect(x, y, w, h, 0xFFFF)` のような取り違えを防げる。だが `pushImage` に渡す配列型まで波及し、`const uint16_t*` を素直に渡せなくなる。組み込みで生バッファを渡す用途が多いので相性が悪い。
- *`setColorDepth()` を持つ* — 1bpp / 8bpp パネルを将来入れるなら要る。だが今の対象に無く、非目標。

### D5. 座標は `int16_t`、転送長は `uint32_t`

**理由**: 座標は画面外・負値を許したいので符号付き。`int16_t` で ±32767、対象解像度に対して十分。一方 240x320 = 76,800 画素なので**転送長は 16bit では足りない**。ここを取り違えると 65,536 画素を超える塗りつぶしが静かに壊れる。

### D6. コストの高い機能は禁止せず、ヘッダで分離して値札をつける

`print` / `printf` / float 引数 / RGB888 変換などは**提供する**。ただしコアには入れず、`TinyGFX/Print.h` のような**別ヘッダ + 派生クラス**で出す。

**理由**: 「V003 に載る」と「便利に使える」は両立できる。要るのは禁止ではなく**選べること**と**選ぶ材料**。`#include` していない翻訳単位はリンクもされないので、ヘッダ分離が最も確実で、条件コンパイルの組み合わせ爆発も起きない。そのうえで「この機能は V003 でフラッシュ +N バイト」を実測して GUIDE に書けば、利用者が自分の予算で判断できる。

**採らなかった案**:
- *float 全面禁止* — 「V003 に載る」だけを守れるが、ESP32 でも `println(3.14f)` が使えないライブラリになる。対象環境の幅を自分で狭めている。
- *マクロで有効化（`TINYGFX_ENABLE_PRINT`）* — 分離はできるが、スイッチの組み合わせ数だけビルド構成が増え、テストで守れなくなる。ヘッダ分離なら構成が自然に 1 本道になる。
- *全部入れて「使わなければ落ちる」に任せる* — `Print` を継承した時点で vtable 経由になり落ちない。D1 と同じ罠。

**運用の義務**: 拡張ヘッダを 1 つ足すたびに、**CH32V003 での増分を実測して [FOOTPRINT.ja.md](FOOTPRINT.ja.md) に記録する。** 測っていない拡張は入れない。

### D7. 回転は MADCTL でやる。ソフトで座標変換しない

**理由**: 座標変換を全プリミティブの入口に置くと、フラッシュも実行時間も全経路で払う。対象コントローラは全部 MADCTL で回転できるので、**Panel が回転ごとの MADCTL 値を持ち、`width()`/`height()` を入れ替えるだけ**で済む。

**代償**: パネルが対応していない回転（一部の e-Paper 等）には使えない。対象外なので問題ない。原点オフセットが回転で変わる個体（ST7789 240x240 など）があるので、**Panel は回転ごとに 4 通りのオフセットを持つ**必要がある。

### D8. クリップ矩形を最初から入れる

MVP に入れる。memo では v0.2 相当だったのを**前倒し**。

**理由**: 画面外への描画をどこで落とすかは、後から足すと**全プリミティブに手が入る**。しかも各プリミティブが個別に画面外判定を書くと、そちらのほうが合計サイズが大きくなる。入口 1 箇所で落とすほうが小さく、正しい。

**逃げ道**: `TINYGFX_NO_CLIP` で判定を省ける。ただし画面外描画は未定義動作になる。**要実測** — 数バイトしか変わらないならスイッチ自体を消す。

### D9. 塗りつぶしは既定でバッファを持たない

`writeColor` の既定実装は 1 画素ずつの 16bit 転送。バッファ 0 バイト。

**理由**: 静的バッファを持つと、使わないスケッチも RAM を払う。SRAM 2KB では数十バイトも惜しい。速度は二番手（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §3）。

**逃げ道**: `TINYGFX_FILL_CHUNK` で**スタック上**の一時配列を使う。静的 RAM は増えない。ESP32 など余裕のある機種向け。

### D10. RST は Panel、CS / DC は Bus が持つ

**理由**: RST の波形（Low 保持時間、解除後の待ち）は**コントローラの初期化列とセット**でしか意味を持たないので Panel の持ち物。CS / DC は転送のたびに叩くもので、Fast Backend では GPIO 直叩きに置き換えたい。よって Bus の持ち物。

**代償**: CS を共有する複数デバイス構成（別チップと SPI を共有）では、Bus を分けるか、Bus 側に外部 CS 制御のフックが要る。**v0.x では未対応。** 要相談（§2）。

### D11. バイトスワップは Bus の責務

`pushImage` / `writePixels` は**ホスト側バイト順の `uint16_t` 配列**を受け取り、MSB first への変換は Bus が行う。

**理由**: 変換位置を上位に置くと、DMA でバッファをそのまま流したい Fast Backend が変換をやり直すことになる。Bus に寄せておけば、**すでに正しい並びのデータを持っている環境では変換を素通しにできる。**

**暫定**: LovyanGFX の `setSwapBytes` に相当する「入力はもう入れ替え済み」を伝える手段が要るかどうか。要相談（§2）。

### D12. フォントは明示的に `setFont()` するまで未設定

**理由**: 既定フォントを暗黙に指すと、文字を一切使わないスケッチにもフォントデータ（6x8 ASCII で約 570 バイト = V003 フラッシュの 3.5%）が載る。

**採らなかった案**:
- *既定フォントを常に持つ* — 使い勝手は良いが、上記のとおり払わない人が払う。
- *`TINYGFX_DEFAULT_FONT` を定義したときだけ既定を持つ* — **こちらのほうが良いかもしれない。** 未設定で `drawString` を呼んで何も出ないのは事故りやすい。要相談（§2）。

### D13. スプライト / オフスクリーンをコアに持たない

**理由**: 全画面バッファは 240x240 RGB565 で 115KB。V003 はもちろん、CH32V20x でも載らない。「ある機種でだけ動く API」をコアに置くと、ライブラリの前提が曖昧になる。

**将来**: やるなら別クラス・別ヘッダ。コアの API は変えない形で足せる。

### D14. 名前は LovyanGFX に寄せるが、互換表も互換レイヤも作らない

**理由**: 名前を寄せるのは**利用者が覚え直さなくて済むように**であって、移植互換のためではない。互換表を作った瞬間、LovyanGFX の仕様変更に追随する義務が生まれる。TinyGFX が背負うものではない。

**具体**: 対応表は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §11。文書では LovyanGFX の仕様を説明しない。

### D15. 「未使用なら落ちる」をリンカ任せにせず、構造で保証する

未使用機能が最終バイナリに載らないのは **`--gc-sections` の仕事**でよい。TinyGFX 側の責務は、**リンカが落とせる形を壊さないこと**。規則の一覧は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.4（R1〜R9）。

**理由**: 落ちなくなる原因はほぼ「参照の連鎖」で、しかも**気づきにくい**。`fillScreen` しか呼んでいないスケッチが 2KB 太っていても、原因は「コアのどこかに 1 行 `Serial.print` がある」だったりする。増分を細かく見る運用（[FOOTPRINT.ja.md](FOOTPRINT.ja.md)）と組み合わせないと、後から効いてくる。

**採らなかった案**:
- *「小さく書く」という心がけだけで運用する* — レビューで毎回すり抜ける。特に R4（デバッグ出力）と R9（関数内 static）は入れた本人に自覚がないまま入る。
- *全部を `#ifdef` で切る* — 確実だが構成数が爆発してテストで守れなくなる（D6 と同じ理由）。

**守り方**: 構成ごとに「載っていてはいけないシンボル」を最終バイナリで検査する `tests/linkprune/`。たとえば **構成 A（`fillScreen` のみ）のバイナリに `drawCircle` / フォントデータ / `Print` のシンボルが 1 つでもあれば fail。** これが D1 / D6 / D12 / R1〜R9 の実効的な担保になる。

### D16. ちらつき対策は「PanelMemory を挟む」で実現する。コアは変えない

LGFXVirtualCanvas と同じ帯レンダリングを最初から入れる。ただし**描画コアには一切手を入れない。**

`TinyGFXPanel` を実装した `TinyGFXPanelMemory`（RAM バッファへ書くパネル）を
実パネルの手前に挟み、`TinyGFXTileCanvas` が帯ごとに「クリア → 描画コールバック → 転送」を回す。

**理由**: フレームバッファが無い以上、消してから描くとちらつく。全画面バッファは
240x240 RGB565 で 115KB あり CH32V20x でも載らない。**帯ならバッファは幅 × 行数 × 2 バイト**で、
240px × 1 行 = 480 B。CH32V003 でも成立する。
そして TinyGFX の層構造では Panel が既に仮想化されているので、**新しい抽象を 1 つも足さずに実現できる**。

**測った値札**（[FOOTPRINT.ja.md](FOOTPRINT.ja.md) §5）: Flash +1,064 B、RAM +560 B（240×1 行）。
使わなければ 0 バイト（別ヘッダなので include しなければリンクされない）。

**副次的な効果**: 描画を `void (*)(TinyGFX&, void*)` の関数にする形になるので、
**同じ描画関数をホストのテストからも呼べる**。`TinyGFXPanelMemory` を全画面サイズで使えば
そのままフレームバッファ検証になる（[TEST_PLAN.ja.md](TEST_PLAN.ja.md) §2）。

**採らなかった案**:
- *別ライブラリにする* — LGFXVirtualCanvas が別ライブラリなのは LovyanGFX が外部だから。
  TinyGFX は両側とも自分のものなので、**別ヘッダに分ければフットプリント上は外部ライブラリと同じ**で、
  バージョン整合の手間だけが減る。
- *描画コアに仮想の描画先を持たせる* — D1 に反する。
- *ダーティ矩形だけを再描画する* — バッファ 0 で済むが、何が変わったかはアプリしか知らない。
  ライブラリの仕事ではない。**GUIDE で「いちばん安いちらつき対策」として案内する**（不透明背景の文字、
  消さずに上書き）。

**制約**: 描画コールバックは帯の数だけ呼ばれる。重い前処理をコールバックに書くとその回数だけ走る。

### D17. フォント形式は GFXfont に合わせる。データはライブラリに同梱しない

TinyGFX のフォント構造体は **Adafruit GFXfont と同じレイアウト**にする（`_GFXFONT_H_` ガードも同じ）。
そして**フォントデータはライブラリに 1 バイトも持たない。**

**理由（形式）**: フォントは [LGFXFontToolJs](https://www.npmjs.com/package/lgfx-font-tool) で生成する。
同ツールが出力できる形式のうち、
- **GFXfont** — デコーダが小さい（ビットカーソルを進めるだけ）。グリフ表が 7 B/字と重いが、
  サブセット化すれば字数自体が減るので効かない
- u8g2 — データは最小だが**デコーダが大きい**。V003 ではデコーダのほうが問題になる

「使う文字だけ埋め込む」運用が前提なら、**データ量よりデコーダの大きさが効く**。よって GFXfont。
既存の Adafruit GFX 用フォント資産をそのまま使えるのも利点。

**理由（同梱しない）**: プリセットを持つと、使う人が選んでいないフォントの分まで
リポジトリとレビューの対象になる。フォントは**スケッチ側に置くもの**にしておけば、
サブセット化の運用（プロジェクトで使う文字だけ）と自然に噛み合う。

**採らなかった案**:
- *独自の固定幅・列優先形式* — 同じ 32 文字で 192 B（GFXfont は 384 B）と小さい。
  だが LGFXFontToolJs が出力できないので変換ツールを自分で持つことになる。**互換性を取った。**
- *u8g2 形式* — 上記。将来 `TinyGFX/FontU8g2.h` として**別ヘッダで**足すことはできる。
  そのときも「include した人だけが払う」形は保てる。

**残っている作業**: [EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E4。
いまは `tools/gen_font.py` の 5x7（0x20-0x3F、32 文字）を測定用のつなぎとして使っている。

### D18. 既定の Bus はハードウェア SPI ではなくソフト SPI にする

`TinyGFXBusSoftSPI`（`pinMode` / `digitalWrite` のビットバン）を第一の実装として持つ。

**理由**: 主ターゲットの CH32V003 で、**Arduino 標準の SPI が使えない**ことが実測で分かった。

| コア | CH32V003 での状況 |
| --- | --- |
| `ch32-riscv-arduino:ch32riscv` | SPI ライブラリが**存在しない** |
| `WCH:ch32v` | SPI はあるが `PinMap_SPI_*` が無く**リンクできない** |
| `UIAP:ch32v` | 同上 |

「Arduino 標準 API だけで成立させる」という原則を突き詰めると、**確実にあるのは
`pinMode` と `digitalWrite` だけ**だった。ソフト SPI はどのコアでも必ず動く。

**代償**: 遅い。だが速度は二番手（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §3）。
速度が要る環境では `TinyGFXBusSPI`（ハードウェア SPI）に 1 行で差し替えられる。

**関連**: [EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E2 / E3。コア側が直れば
`TinyGFXBusSPI` が使えるようになるが、**それを待たずに進める**。
