# デバイスエミュレーションと画面キャプチャ — グランドデザイン

内部の記録。日本語のみ。**まだ実装していない。構造の検討まで。**

## 1. いまの状態

ホストのテストは既にデバイスを模していて、絵も撮れている。**足りないのは
仕組みではなく、再利用できる形になっていないこと。**

| | |
| --- | --- |
| 画面キャプチャ | `tgfxShot()` が PPM を書く。**17 スケッチで 63 枚**出ている |
| バスの覗き口 | ホストコアのフックが揃っている（SPI の `setTransferHook`、Wire の `setWriteHook` / `setReadHook`、GPIO の `setPinWriteHook`） |
| デバイスのモデル | **各テストが自前で書いている** |

問題は最後の行である。**同じ SSD1306 を 4 回書いている。**

| | モデル部 |
| --- | ---: |
| `tests/i2c/` | 103 行 |
| `tests/softi2c/` | 102 行 |
| `tests/monospi/` | 51 行 |
| `tests/sh1106/` | 120 行 |
| **計** | **376 行** |

`feedCmd`（コマンド解釈）と `putByte`（ページ走査）は**3 回ずつ**、ほぼ同じ
ものが書かれている。違うのは**バイトがどこから来たか**だけ —— Wire のフック、
ピンの復号、SPI のフック。

### 効いている制約が 2 つある

1. **キャプチャはモデルを書いたテストでしか撮れない。** 新しいパネルの絵を
   見たければ、まずそのパネルのモデルを書くことになる
2. **モデルが表示範囲しか持っていない。** コントローラの RAM 全体ではなく
   ガラスに見える範囲だけを持つので、**列オフセットのずれが「見えない」。**
   SH1106 の 132 列のうち 2 列ずれている、という絵が撮れない

## 2. 分ける軸 —— バイトの出どころと、デバイスの中身

重複の正体は、**独立した 2 つの関心事が 1 つの関数に混ざっている**ことである。

```
  トランスポート            バイトがどう届いたか
      ホストの Wire フック / SPI フック / ピン復号 /
      Arduino の I2C スレイブ / SPI スレイブ / トレース再生
          ↓  純粋 C++ の口
  デバイス                  何のデバイスか（Arduino に依存しない）
      SSD1306 / SH1106 / ST7789 / センサ …
          ↓
  読み出し                  何を取り出すか
      フレームバッファ → PPM / カウンタ / レジスタダンプ
```

**上と下がポートで、真ん中が持ち運べる核。** 同じ SSD1306 のモデルが、
ホストの Wire フックから来ても、ビットバンのピン復号から来ても、
**別基板の本物の I2C スレイブから来ても**同じように動く。

### TinyGFX 自身の鏡像になっている

```
  TinyGFX        描画 → ドライバ → バス → 線
  エミュレータ    線 → 枠組み → 解釈 → フレームバッファ
```

TinyGFX がバスとドライバを分けている理由（同じドライバを別のバスで動かす）と、
エミュレータがトランスポートとデバイスを分ける理由は**同じ**である。

## 3. デバイスの中身をさらに 2 つに割る

ここが 376 行の重複を消すところ。

| | 何をするか | バスで変わるか |
| --- | --- | --- |
| **枠組み（Framing）** | 届いたバイトが**コマンドか画素か**を決める | **変わる** |
| **解釈（Interpreter）** | コマンドを実行し、RAM を書き換える | **変わらない** |

SSD1306 の場合:

- **I2C** —— 先頭の制御バイトで決まる（`0x00` = コマンド、`0x40` = データ）
- **SPI** —— DC ピンの**レベル**で決まる。バイトの中には手掛かりが無い

**この差が枠組みの全部で、解釈は 1 行も変わらない。** いまの 4 つのモデルは
どれも解釈を書き直しているが、書き直す必要があったのは枠組みだけだった。

## 4. トランスポートの口

SPI と I2C の両方を覆う最小の語彙。

```c
// デバイス 1 個ぶんの口。Arduino の型は出てこない。
typedef struct EmuDeviceOps {
  // CS が下りた／I2C の START。meta はアドレス + R/W ビット
  void    (*select)(void* dev, uint32_t meta);
  // 1 バイト入れて 1 バイト返す。デバイスが線を駆動しないなら 0xFF
  uint8_t (*io)(void* dev, uint8_t in);
  // CS が上がった／I2C の STOP
  void    (*deselect)(void* dev);
  // 帯域外の線。DC・RESET・バックライトなど。**レベルであって、データではない**
  void    (*signal)(void* dev, uint8_t line, uint8_t level);
} EmuDeviceOps;
```

**DC を `io()` の引数にしない**のは、実物で DC が「バイトに付いてくる値」では
なく**線のレベル**だからである。レベルとして持てば、9 ビット SPI（DC を
9 ビット目に載せる変種）を足すときに枠組みだけで済む。

## 5. 画面のキャプチャ —— RAM 全体と表示窓を分ける

**コントローラの RAM 全体をモデルが持ち、ガラスに見える範囲を別に持つ。**

| | SSD1306 128x64 | SH1106 128x64 | ST7789 240x240 |
| --- | --- | --- | --- |
| RAM | 128 x 64 | **132** x 64 | 240 x **320** |
| ガラス | 128 x 64 | 128 x 64（**2 列内側**） | 240 x 240 |

読み出しは 2 通り出す。

```c
emu_display_ram(dev, out);      // RAM 全体。**ずれが目で見える**
emu_display_visible(dev, out);  // ガラスに出る範囲だけ。既存のゴールデンと同じ
```

**これがいまできないこと。** 列オフセットが 2 ずれていたら、RAM 全体を撮れば
絵が 2 列内側に立っているのがそのまま見える。表示窓だけのモデルでは、
「端に縦縞のゴミが出る」という間接的な症状としてしか現れない
（[PANEL_TUNING.ja.md](PANEL_TUNING.ja.md) §2）。

キャプチャの形式は **PPM のまま**にする。ライブラリが要らず、pytest 側は既に
PIL で読んでいて、`git diff` でバイナリとして扱われるだけで困っていない。
**SDL2 のような表示系は入れない** —— 撮るのと見るのは別の話で、見るほうは
pytest が失敗時に PPM を並べた HTML を吐けば足りる。

## 6. 核に課す制約

**そのまま MCU に載る**ようにしておく。別基板を I2C スレイブにしてデバイスを
演じさせる用途が最初から視野にあるため。

| | |
| --- | --- |
| 言語 | C++11。`<Arduino.h>` を含めない。C から呼べる口も残す |
| 確保 | **動的確保をしない。** RAM は呼び出し側が渡す（TinyGFX と同じ作法） |
| 出力 | 核は `printf` もファイル I/O もしない。PPM を書くのはホスト側の読み出し層 |
| 例外 | 使わない。RTTI も使わない |

## 7. ポートの一覧

| ポート | どこで動くか | 使いどころ |
| --- | --- | --- |
| ホストの Wire フック | ホスト | いまの `tests/i2c/` 相当 |
| ホストの SPI フック | ホスト | `tests/monospi/` 相当 |
| ピン復号（GPIO フック） | ホスト | ビットバン（`tests/softi2c/`）。波形まで含めて検査できる唯一の道 |
| **Arduino I2C スレイブ** | 実機 | 別基板にデバイスを演じさせる |
| **Arduino SPI スレイブ** | 実機（ESP32） | 同上 |
| トレース再生 | どこでも | 実機で録ったバイト列を後からホストで流し直す |

**最初の 3 つはいまのテストの書き換えで済む。** 後ろの 3 つが新しくできる
ようになること。

## 7.5 応答方向は「いま要らない」が「捨てると高い」

**ホストのテストで応答を使っているものは 1 つも無い**（2026-09-03 に確認）。
`tests/monospi/` は `setTransferHook` を張るがバイト数を数えるだけで、
返す値に意味を持たせていない。

つまり**キャプチャだけなら一方向で足りる。** ただし、そこが TinyGFX の
検査の穴でもある。

| 読み出しの API | ホストでの検査 |
| --- | --- |
| `readId` / `readId4` / `readRegister` | **無い**。`tests/hw/m5stack/` だけ |
| `readPixels` | **無い**。同上。しかも SDO が MISO に来ていない基板では skip |

**応答を模せるようになると、ここが初めてホストで検査できる。** 単なる
書き換えではなく、増える能力である。

### 口に残す代金はほぼゼロ

```c
uint8_t (*io)(void* dev, uint8_t in);   // 応答あり
void    (*write)(void* dev, uint8_t);   // 一方向
```

**違いは戻り値の型だけ。** モデルは当面 `0xFF` を返しておけばよく、必要になった
ものだけ実装すればいい。逆に一方向で決め打つと、後から広げるときに
**全モデルと全ポートが変わる。**

**だから口は双方向で切る。実装は片方向から始める。**

## 7.6 TinyM5Board が既に「2 つ目」だった（2026-09-03）

`~/dev/TinyM5Board` が同じことを先にやっていて、**表示以外・応答つき**で
動いている。§8 で「表示以外を 1 つ模した時点で出す」と書いた条件は、
**もう満たされている。**

```c
// tests/common_libs/tinym5_trace/src/tinym5_trace.h
struct Device {
  uint8_t (*onWrite)(uint8_t bus, uint8_t addr, const uint8_t *data, size_t len);
  size_t  (*onRead) (uint8_t bus, uint8_t addr, uint8_t *data, size_t len);
};
```

`RegFile` が 256 レジスタ + ポインタを持ち、AXP192 / AXP2101 / M5PM1 の
**チップ判定の分岐を両方向に走らせる**ために応答を返している。

### 向こうのほうが正しかった点

| | TinyM5Board | この文書の当初案 |
| --- | --- | --- |
| **バス番号** | `bus` を引数に持つ（M5 は I2C が 2 本） | **無かった。1 本前提だった** |
| **「居ない」と答える** | 戻り値 `2` で NACK。**アドレス検出の分岐を両方向に走らせられる** | **無かった。常に応答する前提** |
| I2C の粒度 | トランザクション単位（Wire のフックと同じ形） | バイト単位に潰していた |

### こちらのほうが正しかった点

| | この文書 | TinyM5Board |
| --- | --- | --- |
| **インスタンス** | `void* dev` を持つ | グローバル 1 個。**向こうのコメントも「2 個目には小さなリストが要る」と認めている** |
| **帯域外の線** | `signal()`（DC / RESET） | 無い（I2C だけなので要らなかった） |

### 設計の訂正 —— 統一する層が 1 つ高すぎた

当初案は SPI と I2C を 1 つの `io()` に潰そうとしていた。**これは間違い。**

- I2C は**アドレスと NACK** を持ち、Wire のフックはトランザクション単位
- SPI は**チップセレクトと全二重**を持ち、フックはバイト単位

片方をもう片方の形に偽装させることになる。**共有できるのは解釈器であって、
トランスポートの口ではない。**

```
  ポート（バスごと）→ 枠組み（バスごと）→ 解釈器（共有）→ 状態
```

`RegFile` も、枠組みを外に出せば **SPI のセンサにそのまま使える**
（BMP280 のような両対応チップ）。向こうにとっても得になる。

## 7.7 I2CDeviceDB が「エミュレータランタイム」の枠を空けている（2026-09-03）

`~/dev/I2CDeviceDB` は**データ基盤**であって、ライブラリでもエミュレータでも
ないと明言している。そのうえで:

> 特定言語向けアクセスライブラリ、**特定 MCU / OS 向けエミュレータランタイム**、
> 配布パッケージは**派生プロジェクトが持つ**

> Level5 デバイスプロファイル —— …**アクセスライブラリ / エミュレータ生成器が
> 読む正本**

**いま設計しているものは、その派生プロジェクトの枠そのもの。** 3 つの立ち位置が
既に決まっている。

```
  I2CDeviceDB          データの正本（chip profile / capture / scenario）
        ↓ 生成・検証
  エミュレータランタイム   ← この文書が設計しているもの
        ↑ 使う
  TinyGFX（表示）  TinyM5Board（初期化）
```

### 解釈器の分類が、向こうで既に付いている

I2CDeviceDB の最初の対象は ENV III で、**command 型の SHT30 と register-map 型の
QMP6988** を通すと書いてある。§3 で「枠組みと解釈」に割ったが、**解釈のほうも
2 種類**だったことになる。

| 解釈器の型 | 例 | データから生成できるか |
| --- | --- | --- |
| **レジスタマップ型** | QMP6988、AXP192 | **できる。** レジスタ表がそのままデータ |
| **コマンド型** | SHT30、SSD1306、ST7789 | 状態機械。生成は難しく、手書きが現実的 |

TinyM5Board の `RegFile` は**既にレジスタマップ型の実装**である。**生成器の
出力先として、そのまま使える形になっている。**

### 推測だったポートに、実物の入力が付いた

| ポート | 入力 |
| --- | --- |
| トレース再生 | I2CDeviceDB の `captures/`（**一次証拠として蓄積されている**） |
| 適合検査 | 同じく `scenarios/`（テストベクター） |

§7 で「今後できるようになること」として挙げたものが、**推測ではなく既にある
データの使い道**になった。

## 8. 置き場所 —— 決める必要がある

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. TinyGFX の `tests/common_libs/tgfx_emu/`** | すぐ始められる。実際の利用者（4 テスト）が最初から居る | TinyGFX の外から使えない。センサを足す動機が働きにくい |
| **B. 独立したライブラリ** | 最初から持ち運べる。他のプロジェクトからも使える | 利用者が 1 つのうちから公開の形を決めることになる |
| **C. A で形を固めてから B へ出す** | **実際の使用で形が決まる。** 2 つ目の利用者が現れた時点で出す | 一度移動する手間 |

**当初は C を推していたが、§7.6 を受けて B に変える。**

理由は「材料が表示系しかない」だったが、**TinyM5Board という表示以外の実装が
既にあり、しかも応答・バス番号・NACK まで通っている。** 待つ理由が消えた。

さらに、**この 2 つは同時に使われる**（M5 のボードを初期化してから TinyGFX で
描く）。同じ考えの実装を 2 つのライブラリに持つのは、いま 376 行の重複を
消そうとしているのと同じ形の問題を作ることになる。

### 最初に共有するのは「口」であって、実装ではない

**§7.6 / §7.7 を受けても、いきなり実装を 1 か所に集めるのは勧めない。**
TinyM5Board の `RegFile` は動いていて、TinyGFX はリリース前である。**どちらも
動いているものを止めて移す時期ではない。**

| 先に共有するもの | 後で移すもの |
| --- | --- |
| **口（ops の宣言とセマンティクス）** —— 小さなヘッダ 1 枚 | 解釈器の実装 |
| バス番号・NACK・`void* dev`・帯域外の線の意味 | PPM / トレースの読み出し |

**口は合意が安く、食い違いが高い。** 実装は使う側に置いたままでも、口さえ
同じなら後から寄せられる。逆に口が 2 種類できると、寄せるときに全部書き直しに
なる。

だから最初の成果物は **「3 つが合意した ops のヘッダ」1 枚**でよい。

### 移すときは「新規に設計する」のではなく「両方から抜き出す」

| 持ち寄るもの | どちらから |
| --- | --- |
| I2C の口（バス番号・NACK・トランザクション単位） | **TinyM5Board**（検証済み） |
| レジスタファイルの解釈器 | **TinyM5Board** |
| インスタンス（`void* dev`）と複数デバイスの振り分け | 新規（向こうも要ると認めている） |
| SPI の口・帯域外の線（DC / RESET） | **TinyGFX** |
| 表示デバイスの解釈器と RAM 読み出し | **TinyGFX** |
| PPM の書き出し | **TinyGFX**（読み出し層） |
| 文字のトレース出力 | **TinyM5Board**（読み出し層） |

**読み出しが 2 種類あることも、既に両方に実物がある** —— 向こうは
`output/trace.txt` の golden、こちらは PPM の golden。「読み出しもポート」
という §2 の主張が、推測ではなく実例で裏付けられている。

**ただし A の時点から「共有ライブラリのつもり」で書く。** 具体的には
§6 の制約（Arduino 非依存・動的確保なし・C から呼べる ops）と、§7.5 の
双方向の口。**これは規律であって、追加のコードではない。** 守っていれば
移動は `git mv` と `library.properties` の追加で済む。

### 出す時期の目安

「2 つ目の利用者が現れたら」では曖昧なので、条件を決めておく。

**表示以外のデバイスを 1 つ模した時点。** そこで初めて口が 2 種類の形に対して
試されたことになり、固める価値が出る。それまでは表示系だけの推測でしかない。

## 9. 受け入れ条件

書き換えが成立したと言える条件を先に決めておく。

1. **既存の 4 テストが 1 画素も変わらない。** 撮れている PPM がゴールデンなので、
   これは機械的に確かめられる
2. **モデル部の 376 行が、テストからは消える**（共通ライブラリへ移る）
3. **SSD1306 の解釈が 1 か所になる。** I2C・ソフト I2C・SPI の 3 経路が同じ
   解釈器を通る
4. RAM 全体のキャプチャで、SH1106 の 2 列のオフセットが**絵として見える**

  共通の `emu_read(dev, id, buf, len)` にするか、種別ごとに別の口にするか

  ホストだけなら関係しない
