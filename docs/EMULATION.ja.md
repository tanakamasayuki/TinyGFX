# 組込み検証プラットフォーム — あるべき姿からのグランドデザイン

内部の記録。日本語のみ。**まだ実装していない。**

**先にあるべき姿を決め、既存のものはそれに合わせて作り直す。** ここで言う
既存には、ホストコアのフック・各テストの自前モデル・TinyM5Board のトレース・
**I2CDeviceDB の現在の形も含む**。どれも素材であって錨ではない。いまあるものが
覆っているのはユースケースの一部にすぎない、という前提で全集合から立てる。

方針を 2 つ。

- **いまの工数より今後の工数のほうが大きい。** 足すたびに壊れないことを、
  速さや互換より優先する
- **契約はフレームワークにも実行形態にも依存させない。** Arduino にもさせない。
  核は ESP-IDF や素の C 環境でもそのまま動く。**Arduino は「最初から同梱されて
  いる 1 ポート」**であって、前提ではない。host-arduino-core はさらにその
  Arduino ポートの 1 実行形態にすぎない

## 1. あるべき姿

**組込みアプリケーションを、書かれたフレームワークのまま無改造で、実機なしで・
決定的に・観察可能な形で走らせ、実機とデータで裏を取れる基盤。**
Arduino スケッチも ESP-IDF アプリも同じ基盤に乗る。テストはこう書ける:

```
用意する   デバイスの模型を置く。刺激（ボタン押下・センサ値の変化・受信データ）を
          時刻つきで仕込む
走らせる   アプリをそのまま実行する（アプリもライブラリも一切改造しない）
確かめる   起きたこと（イベント列）と、残ったもの（画面・レジスタ・状態）を
          ゴールデンや scenario と突き合わせる
```

基盤の動詞は 4 つ。**この 4 つが直交していることが設計の芯。**

| 動詞 | 何か | 例 |
| --- | --- | --- |
| **観測** | 起きたことを 1 本の順序つき列として見る | トレース・golden・カウンタ |
| **応答** | スケッチの相手をする | PMIC が ID を返す、表示が画素を受ける |
| **刺激** | スケッチへ入力を与える | t=100ms でボタン押下、センサ値の傾斜、NMEA の着信 |
| **時計** | 上の 3 つを 1 本の決定的な時間軸に載せる | `delay(100)` は仮想で進む。刺激は時刻で発火する |

いまあるものは観測と応答の一部だけ。**刺激と時計は丸ごと欠けている**（課題 §5）。

### 1.1 要件は 2 系統 + 共通基盤

4 つの動詞は、**独立に価値のある 2 つの要件系統**と、両方が乗る共通基盤に
分かれる。**別の要件として扱う** —— 別々に作れて、別々に使えるため。

| 系統 | 動詞 | 単独で成立する使い方 |
| --- | --- | --- |
| **A. エミュレーション** | 応答・刺激 | スケッチの相手をする世界を作る。ログを一切取らなくても「動く」 |
| **B. ログ解析** | 観測 | 起きたことを調べる。**模型ゼロでも成立**する —— 実機キャプチャの解析、応答者の居ない run のトレース、golden 比較 |
| **S. 共通基盤** | 時計・環境 | 両系統が同じ時間軸・同じ環境の上に乗る |

独立の証拠: TinyM5Board のトレース golden はほぼ B だけで書けるし、
I2CDeviceDB のキャプチャ解析は A が 1 行も無くても成立する。逆に TinyGFX の
画素比較は A の読み出しが主で、B はあると便利なだけ。

**ただし環境への要求は 1 枚の票にまとめて出す**（§4.7）。タップ・委譲・注入・
時計はどれも環境の同じ場所に開ける穴で、系統ごとに別々に頼むと環境側が
2 度改造されるため。

境界の規約が 1 つ付く: **B はイベント列（直列化形式）だけを読む。模型の内部を
覗かない。** これを守る限り、A と B は別々に版を上げられる（§6-10）。

## 2. 役者

| 役者 | 使い方 |
| --- | --- |
| ライブラリ作者 | ドライバの回帰・分岐網羅・golden |
| **アプリ作者** | **製品スケッチを丸ごとホストで**。UI は模型の画面、センサは台本、時間は加速 |
| チップデータの整備者 | 実機キャプチャ → profile → 模型と scenario の生成 |
| CI | 上の全部をヘッドレス・決定的・並列で |
| 実機での検証者 | 同じ資産（模型・scenario・golden）を実機との突き合わせに使う |
| 教育・解析 | 再現可能なトレースを教材・リバースエンジニアリングの証拠に |

**アプリ作者が最大の空白。** いまの資産はぜんぶライブラリ作者向けにできている。

## 4. 概念モデル

```
          アプリ（無改造 —— Arduino スケッチ / ESP-IDF アプリ / …）
                            │ そのフレームワークの API
              ┌───── 環境（差し替え可能な 1 実装）─────┐
              │  host 実装 / 実機ブリッジ / 再生 / 将来の別実装  │
              └──── バインディング 1 枚で契約を満たす ────┘
                            │
   ┌─────────────────── 中立の契約 ───────────────────┐
   │  イベント列（連番・時刻・直列化可能）      ← 観測。リスナー N 個   │
   │  エンドポイント表（宛先 → 応答者 1）       ← 応答               │
   │  刺激スケジューラ（時刻 → 注入）           ← 刺激               │
   │  時計（仮想／実／記録）                                        │
   └────────────────────────────────────────────────┘
                            │
        バス・デバイス（枠組み＋解釈器＋状態）・読み出し・データ柱
```

### 4.1 観測と応答と刺激は別の口

いまのフックは 1 つの関数ポインタが観測と応答を兼ね、刺激は存在しない。分ける。

| | 観測（リスナー） | 応答（エンドポイント） | 刺激（スケジューラ） |
| --- | --- | --- | --- |
| 数 | 何個でも | 宛先につき 1 | 台本 1 本（時刻順） |
| 向き | 出来事 → 外 | 問い → 答え | 外 → スケッチ |
| 時制 | **事後でも成立**（記録を後で流せる） | その場のみ | 時刻で発火 |
| 変更 | **できない**（読み取り専用） | 応答を決める | 入力を作る |

刺激が注入するものもイベントになる（トレースに写らない操作を作らない）。

### 4.2 イベント列 = トレース形式 = キャプチャ形式

イベントは直列化可能な形で定義する。**ライブの観測・保存した golden・実機の
キャプチャ・再生の入力が、全部同じ 1 つの形式**になる。道具（整形・diff・
集計）が 1 セットで済み、U12・U17・U20 が同じ仕組みに落ちる。

語彙の初期セット（**追加のみ**。§6-1）:

**語彙はハードウェアの言葉で書き、API の言葉で書かない。** `pinMode(INPUT_PULLUP)`
ではなく「GPIO 設定: 方向=入力・プル=上」、`ledcWrite` ではなく「PWM: duty」。
**新しいイベントの合格条件は「Arduino と ESP-IDF の両方から、意味を失わずに
写れること」** —— 片方の API 名が語彙に漏れたら、それはもう中立ではない。

| ドメイン | イベント |
| --- | --- |
| GPIO | 設定（方向・プル）/ 出力 / 入力（結果込み）/ 割り込み発火 |
| I2C(bus) | トランザクション 1 件（addr・R/W・データ・ACK/NACK・stop） |
| SPI(bus) | 設定（モード・クロック）・CS 上げ下げ・転送（往復） |
| UART(port) | 設定・送信列・受信列 |
| アナログ | PWM / DAC の設定と出力、ADC の読み（結果込み） |
| **時間** | 待ち・時刻ジャンプ（**待ちも手順の一部**として写す）。単位は µs |
| 刺激 | 注入の記録（何を・いつ・どこへ） |
| 診断 | バス衝突・宛先不在・模型が検出した契約違反 |

全イベントは**文脈タグ**（main ／ 割り込み中）を持つ（§4.10）。

### 4.3 エンドポイントの 4 つの形

「デバイス」はバスの種類で宛先の付き方が違う。**この 4 形で Arduino API の
入出力をほぼ覆える**（覆えない残りは §9 の境界）。

| 形 | 宛先 | 例 |
| --- | --- | --- |
| アドレス型 | (bus, addr) | I2C の PMIC・センサ・OLED |
| 選択型 | (bus, cs ピン) | SPI の TFT・SD・タッチ |
| ストリーム型 | (port) | UART の GPS・モデム |
| レベル型 | (ピン集合) | ボタン・エンコーダ・1 線もの |

### 4.4 デバイス = 枠組み + 解釈器 + 状態

| 層 | 何をするか | 変わる軸 |
| --- | --- | --- |
| 枠組み | バイトを「コマンド／データ」に分ける（I2C は制御バイト、SPI は DC 線） | バスで変わる |
| 解釈器 | コマンドを実行して状態を書き換える | デバイスで変わる |
| 状態 | RAM・レジスタ。**呼び出し側が確保** | — |

解釈器は 2 型: **register-map 型**（データ駆動 —— profile から生成できる）と
**command 型**（手書きの状態機械: 表示・SHT30 系）。両対応チップは同じ解釈器を
両枠組みから使う。

### 4.5 時計 —— 離散イベントシミュレーションの意味論

仮想時計の規則は 1 行で書ける: **スケッチが待つと、時計は「次に予定がある
時刻」まで跳ぶ。** `delay(100)` は実に眠らず、間に刺激の予定（t=50ms の
ボタン）があればそこで発火してから進む。`millis()` ポーリングのビジーループは
規定の粒度で進める（未決 §10）。これで U7 / U9 / U11 が決定的になる。

時計は差し替え: 仮想（既定・決定的）／実時間（ソケット等が要るとき）／記録
（再生時はキャプチャの時刻）。

### 4.6 環境は 2 軸 —— フレームワーク × 実行形態

「環境」と呼んでいたものは実は 2 軸の組で、契約はどちらの軸も知らない。

| | ホスト実行 | 実機 | 記録 |
| --- | --- | --- | --- |
| **Arduino** | host-arduino-core（**同梱ポート第 1 号**） | 実機タップ／スレイブ | — |
| **ESP-IDF** | IDF の linux ターゲット（将来のポート） | 同上 | — |
| （フレームワーク無し） | — | — | 再生環境 |

バインディングは組ごとに 1 枚。**模型・golden・scenario・解析道具は、どの組でも
同じものが使える**（U20）。

### 4.7 環境は性質を宣言する

環境ごとにできることが違う。契約は**能力の宣言**を持ち、テストは要る能力を
宣言して足りなければ skip（arduino-cli 不在 skip と同じ流儀）。表の列は
実行形態の代表例（§4.6 の 2 軸のうち、能力を決めるのは主に実行形態のほう）。

| 能力 | host 実装 | 実機ブリッジ | 再生 |
| --- | --- | --- | --- |
| 観測 | 全ドメイン・同期 | 覗ける線だけ・**事後** | 記録どおり |
| 応答 | できる | その場の核だけ（U16） | できない |
| 刺激 | できる | 物理入力のみ | 記録の再現 |
| 時計 | 仮想 | 実 | 記録 |

### 4.8 環境への要求票は 1 枚 —— 中身は 2 系統ぶん

エミュレーション（A）とログ解析（B）は別要件だが、**環境に開ける穴は同じ場所**
なので、要求票はまとめて 1 枚で出す。多重化・整形・golden・PPM・スケジューラは
すべて中立側にあり、新しい環境の参加コストが最小になる（U20）。

| # | 環境がすること | 系統 |
| --- | --- | --- |
| E1 | **完全なタップ 1 本**: 見える操作すべてを契約のイベントにして流す | B（A の診断にも効く） |
| E2 | **応答の委譲**: 応答が要る箇所でエンドポイント表に訊く | A |
| E3 | **刺激の受け口**: スケジューラからの注入を自分の世界に反映する（ピンを変え、割り込みを起こし、受信バッファに積む） | A |
| E4 | **時計の提供** | S（両方） |

E1 だけ実装した環境は「解析専用」（実機タップがまさにこれ）、E2〜E4 まで
実装すれば「エミュレーション可能」。**部分実装が正当な姿**であることを、
能力の宣言（§4.7）が支える。

### 4.9 層の実体 —— 何枚あって、それぞれ何を知っているか

縦に全部並べるとこうなる。**環境側は 3 枚、エミュレーション側は状態まで 2 枚。**

```
  アプリ（無改造）
      │ Arduino API                        …フレームワークの言葉
  ① フレームワーク実装（host-arduino-core / 将来の別実装）
      │ タップ IF                           …まだ Arduino の言葉のまま
  ② フレームワーク中間層（Arduino 用は同梱第 1 号。共有ライブラリ）
      │ 契約                                …ここからハードウェアの言葉
  ③ 契約（イベント列・エンドポイント表・刺激・時計）
      │ プロトコル別 ops（4 形）
  ④ 枠組み（I2C 制御バイト / SPI+DC / ストリーム / レベル）
      │ コマンド・データの列
  ⑤ 解釈器（register-map 型 / command 型）
      │
  ⑥ 状態（呼び出し側が確保した RAM・レジスタ）
      └→ 読み出し（RAM・表示窓・レジスタダンプ → PPM・トレースはホスト側の道具）
```

#### ①と②を分ける —— Arduino の意味論を 1 か所に集める

②が**両面を持つ翻訳器**で、ここが「他のライブラリ（実装）が使い回す共通処理」。

| 面 | 言葉 | 中身 |
| --- | --- | --- |
| 上面（①が呼ぶ） | **Arduino のまま** | `onPinMode(pin, mode)`・`onWireTransaction(bus, addr, buf, len, stop) → status`・`onSpiTransfer(bus, out) → in`・`onDelay(us)` … |
| 下面（③を呼ぶ） | **ハードウェアの言葉** | `INPUT_PULLUP` → 方向=入力・プル=上、`endTransmission` → I2C トランザクション 1 件、CS の追跡、割り込み発火の依頼 |

こう割ると、①は**タップの場所と時計の委譲だけ**を持つ薄い存在になり、
Arduino の意味論（mode の値、Wire の作法、CS がただの GPIO であること）は
**②の 1 か所**に集まる。host-arduino-core を別のホスト実装に替えても、
実機の Arduino にタップを仕込んでも、②は同じものが使える。
ESP-IDF ポートは「①' + ②'」の別ペアで、③から下は共通。

**①と②の間に層は作らない。②と③の間にも作らない。** 継ぎ目は「両側が
独立に変わる」ところにだけ置く（下の基準）。

#### ③と④のつなぎ —— エンドポイント表は 4 形で型付き

契約のエンドポイント表は**プロトコル別の小さな ops を 4 種**持つ（§4.3 の
4 形と 1:1）。汎用の「デバイス」型を 1 つ作って振り分けを中でやる、は
しない —— 型で分かれていれば間違った接続はコンパイルで落ちる。

```
attachI2c(bus, addr,  I2cDeviceOps*, state)
attachSpi(bus, csPin, SpiDeviceOps*, state)
attachUart(port,      UartDeviceOps*, state)
attachPins(pin集合,    PinDeviceOps*, state)
```

④の枠組みは「この ops を実装して、⑤の解釈器を呼ぶ」だけの薄い皮。
SSD1306 なら I2C 枠組み（制御バイト 0x00/0x40）と SPI 枠組み（DC 線）が
同じ解釈器を呼ぶ —— 376 行の重複を消す分割そのもの。

#### 逆流路 —— デバイスは線を駆動するだけ（INT 線）

センサの「データ準備完了で INT を引く」は、デバイスから見れば
**ピンのレベルを変える**こと以上ではない。枠組みに `driveLine(line, level)` の
callback を渡しておき、解釈器が呼ぶと**世界の注入点（E3）**へ届く。
割り込みが起きるかどうかはデバイスの関知外（§4.10）。デバイスが環境を
直接触る道は作らない。

#### 継ぎ目を増やさない基準

**継ぎ目は、両側が独立に変わるときだけ置く。** 上の 5 つの継ぎ目はそれぞれ:

| 継ぎ目 | 独立に変わる両側 |
| --- | --- |
| ①/② | 実装が変わる（host / 別ホスト / 実機タップ）× Arduino の意味論は固定 |
| ②/③ | フレームワークが変わる（Arduino / ESP-IDF）× 契約は固定 |
| ③/④ | プロトコル 4 形 × デバイスの種類 |
| ④/⑤ | バスが変わっても解釈器は変わらない（実測: 376 行の重複が証拠） |
| ⑤/⑥ | 確保の場所が変わる（ホストの静的領域 / MCU の RAM） |

この表に **2 軸を書けない継ぎ目は作らない**。「将来のために」だけの抽象は、
変わる軸が現れたときに置く。

### 4.10 線と割り込みの意味論 —— デバイスは線を駆動するだけ

**デバイスの世界は線で終わる。** INT を「上げる」のではなく、ピンのレベルを
変える。その先はデバイスの関知外で、環境側の帰結にすぎない:

- その線に割り込みが**掛かっていれば**、環境がハンドラを発火する
- 掛かっていなければ、アプリがポーリング（digitalRead）で拾うかもしれない
- 誰も見ていないかもしれない —— それでも線は変わり、**イベントには写る**

線が変わる元は 3 つあり、**全部同じ注入点（E3）を通る**。

| 元 | いつ |
| --- | --- |
| 台本（刺激スケジューラ） | 予定の時刻が来たとき |
| デバイス（`driveLine`） | 解釈の帰結として、その場で |
| テストコードの直接操作 | 走行中なら刺激として写す（§4.11-2） |

注入点がやることは 3 つ: ①レベルを更新する（digitalRead が見る）
②イベントに記録する ③その線にハンドラが掛かっていれば発火を**予約**する。
①②は無条件、③だけが条件つき —— **割り込みは経路ではなく帰結**である。

**予約したハンドラがいつ走るか**は環境の宣言に含める。同期・決定的な環境
（host）の規則はこう置く:

- **API 呼び出しの切れ目**と**時間が進む点**（`delay` / `millis` 参照 / yield）で
  発火する。API 呼び出し（I2C トランザクション等）は**アトミック** —— 途中で
  割り込まない
- 計算だけのループ（時間も API も触らない）には割り込めない。**実機との意図的な
  差**であり、そこに依存するテストはそもそも非決定的なので書かせない
- `noInterrupts()` 中は保留し、解除の点で発火する
- ハンドラの中の API 呼び出しも普通にイベントになる。**イベントには
  main / 割り込み中 の文脈タグを付ける**（解析で「ISR から Wire を叩いている」が
  見える —— 実機で事故る典型がトレースに写る）

デバイス起点の線の変化は、それを起こしたトランザクションの**完了直後**が
最初の発火点になる（アトミック規則の帰結）。実機より整いすぎているが、
決定的であることを優先する（§9 の境界）。

共有 INT 線（オープンドレインの wired-AND で複数デバイスがぶら下がる形）は
当面**1 線 1 駆動者**とし、2 つ目の駆動者は診断イベントで報せる。要るように
なったら駆動者ごとのレベルを注入点が合成する（未決）。

### 4.11 デバイスの検分と仕込み —— 汎用リフレクションは作らない

デバイスの中身を見る・仕込む口は**要る**。無いと arrange（センサ値を先に
入れておく）も assert（画素・レジスタの確認）も書けない。ただし核に汎用の
リフレクション API は置かない。

| 型 | 検分・仕込みの口 |
| --- | --- |
| register-map 型 | **番地で均一**: `get(reg)` / `set(reg, value)`。scenario のデータ駆動 assert がそのまま書ける |
| command 型 | **デバイスごとの型付き口**: 表示なら RAM 全体・表示窓・`preload(画像)`。SHT30 なら「次に返す測定値」 |

規則を 3 つ:

1. **検分は状態を変えない**（const）。イベントも出さない —— 見ただけで
   トレースが変わると golden が壊れる
2. **走行前の仕込みは自由**（arrange はテストの支度）。**走行中に裏から状態を
   弄るなら、それは刺激としてイベントに写す** —— トレースに写らない世界の変化を
   作らない（§4.1 の原則の適用）
3. 何を公開するかは**デバイスの作者が決める**。核が強制するのは「命名と
   置き場所（読み出し層）」だけ。B 系統（ログ解析）はこれらに触れない（§6-10）

## 6. 拡張しても破綻させないための規約

**ここが本体。** 機能は後から足せるが、規約は後から直せない。

1. **イベントは追加のみ。** 種類もフィールドも増やすだけ。意味を変えない・
   消さない。リスナーは知らない種類を読み飛ばす。守る限りバージョン番号は
   要らない（D35 と同じ理屈 —— 名前と型で食い違いが落ちる）
2. **デバイス種・環境種の列挙を作らない。** enum とスイッチ文ができた時点で、
   足すたびに中心が変わる。すべて ops（vtable）＋状態の開いた集合
3. **観測は応答を変えられない。** リスナーに戻り値を持たせない。一度でも
   越えると登録順が意味を持ち、多重登録が壊れる
4. **契約にどのフレームワークの型も API 名も入れない。** Arduino も例外に
   しない。語彙はハードウェアの言葉（§4.2）で、DC 線・Wire の癖・ホストの事情は
   バインディングとデバイスの枠組みに閉じ込める。イベントを足すときの検査は
   「Arduino と ESP-IDF の両方から意味を失わず写れるか」
5. **核は純粋 C++。** どのフレームワークのヘッダも含めない・動的確保なし・
   例外/RTTI なし・I/O なし・C から呼べる。バッファは常に呼び出し側が渡す
   （U16 と ESP-IDF ポートが死ぬため）
6. **中心に固有名詞を溜めない。** SSD1306 の模型はカタログに置いてよいが、核は
   どのデバイスの名前も知らない。register-map の中身はデータ柱が正本で、
   コードに写経しない
7. **golden は人が読める形式を既定に。** 文字トレースと PPM。独自バイナリを
   増やさない（diff できることが保守の半分）
8. **プロトコルを無理に統一しない。** 4 形（§4.3）はそれぞれの語彙で。共有する
   のは解釈器と読み出しであって、口ではない
9. **台本（刺激・障害・scenario）はコードでなくデータ。** 「n 回目を NACK」を
   C++ で書き始めると、データ柱（生成・共有・実機との突き合わせ）から切れる
10. **ログ解析はイベント列だけを読む。** 模型の内部・エンドポイント表・
   スケジューラに触る解析道具を作らない。この線が、エミュレーション（A）と
   ログ解析（B）を**別々に版上げできる**根拠になる

## 7. 既存資産の位置づけ —— 全部「合わせる側」

| 既存 | 生き残るもの | 作り直すもの |
| --- | --- | --- |
| host-arduino-core | Arduino API の実装本体 | フック層・時計。**環境の 1 実装**として B1〜B4 を実装 |
| TinyGFX のテスト | golden の PPM（受け入れ条件そのもの） | 4 つの自前モデル（計 376 行）→ カタログの模型へ |

## 8. 段階と受け入れ条件

| 段階 | 系統 | 作るもの | 受け入れ条件 |
| --- | --- | --- | --- |
| 1 | B+S | **契約**（イベント・リスナー・時計。エンドポイント・刺激は宣言のみ）＋**再生環境**（最小の環境実装） | 記録イベント列の再生でリスナー多重・golden 比較が動く。**環境ゼロ・模型ゼロでログ解析が成立する**証明（B の独立）。U20 を初日から強制 |
| 2 | S | **Arduino ポート第 1 号** = host-arduino-core のバインディング（E1〜E4、仮想時計） | 既存リポジトリのテストが新しい口で通り、`delay` を含むテストが**速くなる** |
| 3 | A | I2C バス＋register-map 解釈器＋文字トレース読み出し | TinyM5Board 相当の golden が新経路で一致 |
| 4 | A | command 型解釈器（表示）＋PPM 読み出し | **TinyGFX の既存 PPM が 1 画素も変わらない**。376 行が消える。SH1106 の 2 列が RAM の絵に写る |
| 5 | A | SPI 枠組み＋応答方向 | `readId` / `readPixels` がホストで検査できる（初） |
| 6 | A | 刺激スケジューラ＋レベル型・ストリーム型 | ボタン台本と UART 台本のテストが立つ（U7 U10 U11 の最小形） |
| 7 | A | 障害注入（データ駆動のデコレータ） | 検出分岐の両側・NACK・短読が台本で書ける |
| 8 | A+B | scenario ランナー＋データ柱との形式合意 | 同じ scenario が模型に対して通る。capture 形式 = イベント直列化形式になる |
| 9 | A+B | 実機系（スレイブポート = A、実機タップ = B） | 別基板の模型に実機がアクセスし、段階 8 と同じ scenario が通る |

**段階 1 を「契約＋再生」にしたのが要点。** 最小の環境が再生であることで、
契約が最初から host 専用でないことを強制される。host はその次。

## 9. スコープの境界

- **タイミングの検証はしない。** 待ちが「あったこと」は記録するが、「足りて
  いるか」は実機でしか分からない（[MANUAL_TEST.ja.md](MANUAL_TEST.ja.md)）
- **波形レベル・電気層の模倣はしない。** NeoPixel のようなタイミング符号、
  PWM の波形、**I2C のクロックストレッチやバス調停**は対象外。API 層から
  見えないものは模さない。ただし**API に漏れてくる帰結は表現できる** ——
  ストレッチの帰結は「タイムアウト状態」や「busy の NACK」であり、それは
  応答（状態コード）と時計（busy 期間）で書ける。それで足りない検証
  （本物のストレッチとビットバン実装の相性など）は実機の領分
- **性能・フットプリントの測定はこの基盤の仕事ではない**（実ツールチェーンで測る。
  [FOOTPRINT.ja.md](FOOTPRINT.ja.md) の領分）

## 10. 未決

- **名前とリポジトリ構成。** 契約＋核で 1 リポジトリ、模型カタログを同居させるか
  分けるか
- **イベントの表現と直列化形式。** タグ付き構造体か口の束か。テキスト行か
  バイナリか。データ柱の capture 形式と**同時に**決める（別々に決めると
  U12/U17 の「同じ形式」が崩れる）
- **ビジーループ時の時計の進め方**（`while (millis() < x)` の粒度）
- **仮想時計の既定**を全テスト仮想にするか opt-in にするか
- **割り込みの細目。** 発火点の方針は決めた（§4.10）が、ネスト（ISR 中の発火）を
  許すか、優先度を持つかは未決。最初は「ネスト無し・FIFO」から始めるのが安全
- **UART の Serial（USB コンソール）の扱い** —— テスト報告と刺激対象を分ける線
- **ESP-IDF ポートの時期。** IDF にはホスト実行（linux ターゲット）があるので
  置き場はある。作るのは需要が出てからでよいが、**語彙の中立性（§4.2 の合格
  条件）はイベントを足すたびに紙上で検査する** —— ポートが無い間に語彙が
  Arduino に寄るのがいちばん静かな腐り方
- **pytest 側の共有**（HTML レポート等）をプラグインに切り出す時期
