# TinyFont — フォント形式

内部の記録。日本語のみ。**形式の定義と、そう決めた実測。**

TinyGFX はフォントデータを 1 つも同梱しない（[DECISIONS.ja.md](DECISIONS.ja.md) D17）。
ここで決めるのは**受け取る形**だけ。生成は [LGFXFontToolJs](https://www.npmjs.com/package/lgfx-font-tool) が行う。

## 0. 対象範囲 — **高さ 16 画素以下のピクセルグリッドフォント**

TinyFont はこの帯のためだけの形式。**外に出たら u8g2 か GFXfont を使うほうがよい。**

これは妥協ではなく**実測上の変曲点**で、H≈16 で 3 つの独立した機構が同時に反転する。

| 機構 | ≤12px | 16px | 24px 以上 |
| --- | --- | --- | --- |
| グリフごとの bbox | **無意味**（8px では足すと増える） | −14% | 24px で −27% |
| RLE 圧縮 | 効かない | 1.4% | 24px で 8%、40px で 29%、75px で 66% |
| u8g2 の総量 | **TinyFont の勝ち** | 逆転 | 24px で −36% |

だから §5「圧縮しない」も §6「bbox を採らない」も、**この 1 つの前提から導かれる**。
16px を超えたところで両方とも成り立たなくなる。数字は §6。

## 1. 中心の考え方

> **選択は実行時ではなく生成時に済ませ、結果をデータで表す。**

決めることは 2 つだけ。どちらも**ポインタが `nullptr` かどうか**で表す。

| 選択 | `nullptr` のとき | 非 `nullptr` のとき |
| --- | --- | --- |
| `codes`（索引） | **連続** — `first` から `count` 個 | **疎** — 昇順のコード表を二分探索 |
| `glyphs`（グリフ表） | **固定ピッチ** — 全グリフ共通の幅・送り幅 | **可変ピッチ** — 4 バイト/字 |

4 通りの組み合わせすべてを 1 つのデコーダが扱う。分岐は各 1 か所で、
**両方に対応するコストは合計 76 バイト**（§4 の実測）。

## 2. 構造

```cpp
struct TinyGFXGlyph {   // 可変ピッチのときだけ。4 バイト固定
  uint8_t offsetLo, offsetHi, width, xAdvance;
};

struct TinyGFXFontTiny {
  const uint8_t*      bitmap;
  const TinyGFXGlyph* glyphs;  // nullptr = 固定ピッチ（表を持たない）
  const uint16_t*     codes;   // nullptr = 連続索引
  uint16_t first, count;
  uint8_t  width, height, xAdvance, yAdvance;
  int8_t   xOffset, yOffset;   // yOffset = 行の上端からのグリフ上端
  uint8_t  bytesPerGlyph;
};
```

**24 バイト。** 高さ・xOffset・yOffset をグリフごとに持たないのが GFXfont との一番の差。

スケッチが `setFont()` に渡すのはこれではなく、形式に依らない `TinyGFXFontRef`:

```cpp
static const TinyGFXFontTiny myFontData = { ... };
static const TinyGFXFontRef  myFont = { &myFontData, &tinygfxFontTinyOps, nullptr };
```

`ops` が形式ごとのデコーダを指し、`next` が連鎖の次を指す（**形式が違ってよい**）。
仕組みは §8、コアから見た形は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §9。

ビットマップは「行を連結した MSB first のビット列、グリフ間はバイト境界揃え」で
GFXfont と同じ並び。既存の Adafruit 資産はツール側で変換できる。

固定ピッチのときグリフ n の先頭は `bitmap + n * bytesPerGlyph`。表を引かない。

## 3. データ量

グリフ 1 字のビットマップを b バイトとすると:

| 形式 | データ量 |
| --- | --- |
| GFXfont（参考） | 12 + n × (b + 7) |
| TinyFont 固定ピッチ・連続 | 24 + n × b |
| TinyFont 固定ピッチ・疎 | 24 + n × (b + 2) |
| TinyFont 可変ピッチ・連続 | 24 + n × (b + 4) |
| TinyFont 可変ピッチ・疎 | 24 + n × (b + 6) |

### ASCII 全部（n=95、5x7 なので b=5）

| 形式 | データ量 | GFXfont 比 |
| --- | --- | --- |
| GFXfont | 1,152 B | — |
| **固定ピッチ・連続** | **499 B** | **−653 B（−57%）** |
| 固定ピッチ・疎 | 689 B | −463 B |
| 可変ピッチ・連続 | 879 B | −273 B |

**ASCII の固定ピッチフォントでは、GFXfont のグリフ表がデータの 58% を占めていて、
しかも中身は全字同一。** ここを落とすのが一番効く。

### 実データでの比較（u8g2 も相手にする）

| | TinyFont | u8g2 | GFXfont | BFF |
| --- | --- | --- | --- | --- |
| 半角 4x8 固定・連続 95 字 | **404** | 764 | — | 1,130 |
| 合成 5x7 固定・連続 95 字 | **499** | 994 | 1,349 | 1,236 |

**u8g2 相手でも −47%。** ただしこれは**固定ピッチのときだけ**。

### 可変ピッチになった瞬間に負ける

刈り込んだ半角 95 字で、u8g2 に対し **12px で −17%、16px で −22%**。
**TinyFont の強みは「表が消えること」だけ**で、表が出た時点で
u8g2 のビットフィールド + RLE には勝てない。

### だから生成側の方針が形式と同じくらい重要

| 方針 | 理由 |
| --- | --- |
| **刈り込むな。セル幅で出せ**（`width = xAdvance`） | 詰め物は増えるが、グリフ表 4 B/字が丸ごと消えるほうが大きい。半角 4x8 で 722 → **404 B**（−318 B） |
| **半角と全角で 2 フォントに割り、`next` で繋げ** | 割っただけでは可変のまま。**セル幅とセットで初めて**両方が固定ピッチになる |

2 つ揃えると 8px の混在サブセットが 2,349 → **1,471 B（−37%）**。
u8g2 の 2,201 B より 33% 小さく、デコーダは 684 B のまま。
**V003 に実際に載る帯だけを見れば、TinyFont が最強。**

### CJK のサブセット（n=500、16x16 なので b=32）

| 形式 | データ量 |
| --- | --- |
| **固定ピッチ・疎** | **17,024 B** |
| 可変ピッチ・疎 | 19,024 B |
| GFXfont | **不可能に近い** |

GFXfont は `first`〜`last` が連続でなければならない。U+4E00〜U+9FA5 に散った 500 字を
収めるには 20,902 件のグリフ表（**146 KB**）が要る。実際に使う 500 字ぶんは 1 KB。
**疎索引はここで桁違いに効く。**

## 4. 実測（CH32V003 / -Os / 32 グリフ 5x7）

`tests/constructs/d`（構成 C + 文字）で測った。データ量は算術で分かるので、
**コード量 = Δflash − Δデータ**。

| 構成 | flash | 文字機能ぶん | うちデータ | うちコード |
| --- | --- | --- | --- | --- |
| C（文字なし） | 10,776 | — | — | — |
| **d（固定ピッチ・連続）** | **11,620** | **+844** | 184 | **660** |
| d_rec（可変ピッチ） | 11,748 | +972 | 312 | 660 |
| d_sparse（固定・疎） | 11,684 | +908 | 248 | 660 |
| （旧）GFXfont | 11,856 | +1,080 | 396 | 684 |

**TinyFont は GFXfont より 236 バイト小さい。** データで −212、コードで −24。
4 通りを扱うようになったのにコードが減ったのは、`setFont()` の ascent 走査が
消えたのと、グリフ表が 7 → 4 バイトになったため。

### `next` 連鎖のコスト

半角と全角を別フォントに割って繋ぐ仕組み（§2 の `next`）を足したときの差。

| | flash | 差 |
| --- | --- | --- |
| 連鎖なし | 11,620 | — |
| **連鎖あり（現在）** | **11,644** | **+24 B**（うち構造体の +4 B、コード +20 B） |

8px の混在サブセットで 878 B 減る（2,349 → 1,471）のに対して 24 B。**入れて損はない。**

### 分岐そのもののコスト

```sh
-DTINYGFX_FONT_SPARSE=0    # 疎索引を落とす
-DTINYGFX_FONT_RECORDS=0   # 可変ピッチを落とす
```

| 構成 | flash | 削減 |
| --- | --- | --- |
| 両方あり（既定） | 11,620 | — |
| 疎なし | 11,564 | **−56 B** |
| レコードなし | 11,596 | **−24 B** |
| 両方なし | 11,544 | −76 B |

**結論: 既定で両方入れておく。** 76 バイトは、ASCII で 653 バイト、CJK で 145 KB
という節約に対して誤差。スイッチは「どうしても」のときのためだけに残す。

> 別途の測定では疎索引のコードを +124 B としていた。こちらの実測は +56 B。
> 実装が違う（こちらは uint16 の表を二分探索するだけ）。**どちらにせよ結論は変わらない。**

## 5. 圧縮しない（**≤16px の中でだけ**）

RLE の利得は高さで決まる。

| フォント | RLE 単独の利得 |
| --- | --- |
| JapanGothic_16 | 1.4% |
| JapanGothic_24 | 8% |
| JapanGothic_40 | 29% |
| DejaVu72 (ASCII) | 66% |

**16px 以下ならデコーダのバイト数に見合わない。** これが「圧縮しない」の根拠で、
§0 の対象範囲と同じ 1 つの前提から出ている。**24px を超えると崩れる**ので、
そこは u8g2 の領分にする。

## 6. 採らなかったもの

### 6.1 グリフごとの bbox

`glyphs` を 4 → 7 バイトにして、グリフごとに高さ・xOffset・yOffset を持つ案
（GFXfont / u8g2 方式）。

**連続索引のときは恒等式で負ける。** span = n、codes = 0 なので
TinyFont+bbox − GFXfont = ヘッダの差 24 − 12 = **常に +12 B**。フォントの中身によらない。
対象範囲を広げることは「GFXfont をヘッダ 12 B 太らせて作り直す」ことにしかならない。

高さ別の実測（日本語混在 190 字、データのみ）:

| フォント | TinyFont | 半/全分割 | u8g2 | TinyFont+bbox |
| --- | --- | --- | --- | --- |
| JapanGothic_8 | 2,349 | **2,090** | 2,201 | 2,510 |
| JapanGothic_12 | 3,431 | **3,174** | 3,165 | 3,255 |
| JapanGothic_16 | 5,110 | 4,944 | **4,408** | 4,470 |
| JapanGothic_24 | 10,158 | 9,257 | **7,356** | 8,000 |
| JapanGothic_40 | 26,144 | 24,700 | **13,429** | 18,954 |
| DejaVu72 (ASCII) | 37,765 | — | **6,646** | 19,628 |

**8px では bbox を足すと増える**（2,349 → 2,510）。16px で −14%、24px で −27%。
つまり bbox が効き始める場所は、u8g2 が総量で勝ち始める場所とほぼ同じ。
**その帯では u8g2 を使えばよい。**

### 6.2 コードの再マップ（連番へ振り直す）

疎索引比で 9% しか縮まないうえ、**文字列リテラルがそのまま使えなくなる。**

### 6.3 32bit オフセット

16bit で 64KB。それを超えるフォントは対象範囲（§0）の外。

### 6.4 GFXfont をそのまま食う

ASCII で 653 B 損する（§3）。ビットマップの並びは同じなのでツール側で変換できる。

## 7. u8g2 デコーダを足したらいくら増えるか — **測った**

残っていた未測定はこれだけだった。「16px で u8g2 に勝つには、そのデコーダが
TinyFont より 388 B 以上大きいことを示せばよい」という形の問題。

**答え: 越えられない。u8g2 デコーダは TinyFont とほぼ同じ大きさだった。**

### 実測（CH32V003 / -Os）

| 構成 | flash | 文字機能ぶん | データ | **コード** |
| --- | --- | --- | --- | --- |
| C（文字なし） | 10,772 | — | — | — |
| **d（TinyFont / drawString）** | 11,644 | +872 | 188 | **684** |
| d_u8g2c（u8g2 / drawChar のみ） | 11,628 | +856 | 163 | **693** |
| d_u8g2（u8g2 / drawString、UTF-8 込み） | 11,772 | +1,000 | 163 | 837 |

**u8g2 のデコーダは 693 B。TinyFont の 684 B より 9 バイト大きいだけ。**

比較が公平になるよう、u8g2 側も TinyFont と同じく `fillRect` / `drawFastHLine` の
ランで描いている。試作は `tests/common_libs/tgfx_test/src/tgfx_u8g2.h`。

### 正しさは確認済み

コード量だけ測っても意味がないので、**LGFXFontToolJs が同じフォント・同じ文字列を
描いた絵と一致すること**を先に通した（`tests/u8g2/`）。参照データは
`tools/gen_u8g2_ref.mjs` が生成する。

- ASCII（コード < 256、`start_pos_upper_A` / `lower_a` の飛び先つき）— 一致
- CJK（Unicode 区画のブロック飛び先表）— 一致

### この結果が意味すること

**コード量はほぼ引き分けなので、境界はデータ量だけで決まる。** §0 の H≈16 が
そのまま総量の境界になる。

| 高さ | データ差 | コード差 | 総量 |
| --- | --- | --- | --- |
| 8px | TinyFont が 730 B 小さい（1,471 vs 2,201） | +9 B | **TinyFont の勝ち** |
| 12px | ほぼ互角（3,174 vs 3,165） | +9 B | **互角** |
| 16px | u8g2 が 536〜702 B 小さい | +9 B | **u8g2 の勝ち** |
| 24px 以上 | u8g2 が 1,900 B 以上小さい | +9 B | **u8g2 の勝ち** |

「16px 以上ではコードの差が効いて逆転する」という望みは**無い**。
だから **§0 の線引き（H≤16）をそのまま採用してよい。**

### ついでに分かったこと — UTF-8 デコードが要る

`drawString` の UTF-8 デコードは **+153 B**（837 − 684）。

**これは形式に依らない。** TinyGFX の `drawString(const char*)` はいまバイトを
そのままコードとして扱っているので、**疎索引の TinyFont で CJK を出すには
UTF-8 の入口が要る**。u8g2 を選んでも同じだけ払う。

→ 未着手。CJK を実際に出す段になったら足す（[DECISIONS.ja.md](DECISIONS.ja.md) Q12）。

### 試作をどう扱うか

`tgfx_u8g2.h` は **`tests/` 側に置いてあり、ライブラリには入れていない。**
u8g2 形式にも対応するかは未決（そちらのツール側の議論待ち）。
対応するなら、この試作をそのまま `src/TinyGFX/FontU8g2.h` に移せばよい。
ただし**コアが 2 つのフォント型を知ることになる**ので、そこの作り方は別途決める。

## 8. 複数のフォント形式に対応する — **未使用分は 1 バイトも載らない**

### 仕組み

**コアはフォント形式を 1 つも知らない。** フォント側が自分のデコーダ（`TinyGFXFontOps`）を
指していて、コアは連鎖をたどって呼ぶだけ。**include していない形式のデコーダは
どこからも参照されないので落ちる。**

### 実測（CH32V003 / -Os）

| 構成 | flash | 文字機能ぶん | データ | **コード** |
| --- | --- | --- | --- | --- |
| C（文字なし） | 10,772 | — | — | — |
| **d（TinyFont だけ）** | 11,808 | +1,036 | 208 | **828** |
| d_u8g2（u8g2 だけ） | 12,064 | +1,292 | 187 | **1,105** |
| d_both（両方） | 12,988 | +2,216 | 395 | 1,821 |

**TinyFont のスケッチに u8g2 を足すと +1,180 B。使わなければ +0 B。**

### 落ちていることの証拠

`nm` で最終バイナリのシンボルを数えたもの。`tests/linkprune/` が毎回検査する。

| 構成 | TinyFont のシンボル | u8g2 のシンボル |
| --- | --- | --- |
| d（TinyFont だけ） | 3 | **0** |
| d_u8g2（u8g2 だけ） | **0** | 3 |
| d_both | 4 | 3 |

### 仕組みそのものの代金 — +144 B

形式を差し替えられるようにした代わりに、**単一形式の利用者も 144 バイト払う**。

| | flash | データ | コード |
| --- | --- | --- | --- |
| 直結（形式 1 つ固定・旧実装） | 11,644 | 188 | 684 |
| **差し替え可能（現在）** | 11,808 | 208 | **828** |

内訳:

- **+20 B はデータ**（`TinyGFXFontRef` 12 B + ops 表 12 B − 構造体から抜いた `next` 4 B）
- **+124 B はコード。** 大半は「定数畳み込みが効かなくなったぶん」。
  以前はフォント構造体がリテラルとして見えていたので、コンパイラが
  `glyphs == nullptr` / `codes == nullptr` を**コンパイル時に解決して分岐ごと消していた**。
  関数ポインタ越しになると `const void*` が不透明になり、畳めなくなる。

**取り戻せる。** 変種が決まっているなら分岐を落とせる:

| | flash | 差 |
| --- | --- | --- |
| 既定（両方あり） | 11,808 | — |
| `-DTINYGFX_FONT_SPARSE=0` | 11,744 | −64 B |
| `-DTINYGFX_FONT_RECORDS=0` | 11,764 | −44 B |
| 両方なし | **11,692** | **−116 B** |

つまり **純粋な間接呼び出しの代金は約 28 B**（11,692 − 11,644 − 20）で、
残りは「畳めなくなった分岐」。固定ピッチ・連続索引しか使わないと分かっている
プロジェクトはスイッチで元に戻せる。

### 判断

**144 B（スイッチで 28 B まで縮む）を払って、形式を自由に増やせるようにする。**

TinyFont は H≤16 の帯でしか勝てない（§0）ので、**その外を扱う道は要る**。
形式を足すたびにコアが太る作りだと、その道は塞がる。

## 9. LGFXFontToolJs への依頼

[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E4 にまとめてある。要点:

1. **TinyFont 形式のエンコーダ**（`encodeCSource({format: 'tinyfont'})` 相当）
2. **索引とグリフ表を自動で選ぶ**（連続に収まるなら連続、固定ピッチなら表を省く）。
   選んだ結果をヘッダのコメントに書いてくれると、利用者がデータ量を把握できる
3. **PROGMEM 属性**をビットマップ・グリフ表・コード表・`TinyGFXFont` の 4 つすべてに付ける
4. **決定的な出力**（同じ入力 → バイト一致）。CI で `git diff --exit-code` して守るため

## 10. つなぎの実装

`tools/gen_font.py` が測定用に 5x7（0x20-0x3F の 32 字）を 3 変種で吐く。

```sh
python3 tools/gen_font.py --mode fixed
python3 tools/gen_font.py --mode records --symbol ... --out ...
python3 tools/gen_font.py --mode fixed --sparse --symbol ... --out ...
```

**変種を変えても描画結果が 1 画素も変わらないこと**は `tests/text/` が検査している。
