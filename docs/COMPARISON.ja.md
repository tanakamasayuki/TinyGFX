# 既存の GFX ライブラリとの比較

> English: [COMPARISON.md](COMPARISON.md)

TinyGFX の API と設計が妥当かを確かめるために、主要な GFX ライブラリを
調べた記録。**「他がやっているから」ではなく「なぜそうなっているか」**を
見て、TinyGFX が違う理由を言えるようにするのが目的。

## 何と比べたか

| ライブラリ | 版 | 調べ方 |
| --- | --- | --- |
| **Adafruit_GFX** | 手元 | ソース |
| **U8g2** | 2.36.19 | **ソース + 実測ベンチ**（唯一、同じ絵を両方で書いて比較した） |
| **LovyanGFX** | 1.2.26 | ソース |
| **M5GFX** | 0.2.27 | ソース |
| **TFT_eSPI** | — | README |
| **Arduino_GFX**（moononournation） | — | README |
| **GxEPD2** | — | README |
| **embedded-graphics**（Rust） | — | ドキュメント |

## 一覧

| | TinyGFX | Adafruit_GFX | U8g2 | LovyanGFX | TFT_eSPI | Arduino_GFX |
| --- | --- | --- | --- | --- | --- | --- |
| 描画 API 数 | **47** | 64 | 126 | **175** | 多 | 多 |
| コアの仮想関数 | **0** | 18 | 0（C の関数ポインタ） | 3 | 少 | 少 |
| 色深度 | **RGB565 のみ** | 1 / 8 / 16 | 1bpp | **9 種**（1/2/4/8 パレット、灰 8、565/666/888/8888） | 1 / 8 / 16 | 複数 |
| パネル | **5** | 別ライブラリ | 多数 | **約 45** | 18+ | **40+** |
| バス | 3（ソフト SPI / SPI / I2C） | ドライバ次第 | SPI / I2C / パラレル | **9 種** | SPI / 8bit / 16bit パラレル | SPI / 8bit / 16bit / RGB |
| プラットフォーム | **`architectures=*`** | 広い | 広い | **17** | 5 系統 | 約 20 |
| ヘッダオンリー | **はい** | いいえ | いいえ | いいえ | いいえ | いいえ |

**TinyGFX は API の数でも対応の広さでも最小。** それが狙いで、比較の目的は
「足りない」を探すことではなく、**足りないことの理由が言えるか**を確かめる
ことにある。

## 設計の軸

### 1. ドライバが実装するもの（シーム）

ここがいちばん違う。

| | ドライバが必ず書くもの | 任意で速くできるもの |
| --- | --- | --- |
| **Adafruit_GFX** | `drawPixel`（純粋仮想）**1 つだけ** | `drawFastHLine` / `drawFastVLine` / `fillRect` / `writePixel` ほか |
| **U8g2** | `ll_hvline`（バッファへの水平／垂直ラン） | — |
| **embedded-graphics** | `draw_iter`（画素の並びを受け取る）**1 つだけ** | `fill_contiguous` / `fill_solid` / `clear` |
| **LovyanGFX** | `Panel_Device` の一式 | 多数 |
| **TinyGFX** | `setWindow` + `writeColor` + `writePixels` | **`fillRect`** |

**「必須 1 つ + 任意の特殊化」は embedded-graphics と同じ形。** TinyGFX が
`fillRect` をシームにしたのは独自の思いつきではなく、同じ問題に同じ答えが
出ている。

**Adafruit_GFX の `drawPixel` 必須は最も移植が楽だが、最も遅い。**
既定の `fillRect` は画素を 1 つずつ置くので、まとめ書きの効くパネルでは
桁が違う。だから実際のドライバは結局 `fillRect` を上書きしている。

**U8g2 だけプリミティブが「ラン」**で、窓の概念がない。ページ方式の
1bpp バッファに対しては、これが最も素直
（[OPTIMIZE.ja.md](OPTIMIZE.ja.md) H）。

### 2. 色の扱い

**TinyGFX はコアに色深度の抽象を持たない**（[DECISIONS.ja.md](DECISIONS.ja.md) D4）。
API は常に `uint16_t` の RGB565 で、1bpp への変換は SSD1306 のパネルが
「0 でなければ点灯」で行う。

LovyanGFX は 9 種類の色深度を実行時に切り替えられる。Adafruit は
`GFXcanvas1` / `8` / `16` という別クラスにしている。

**どちらも「2 つ持つ」構造で、基準機には載らない。** ただし
**灰階調やパレットのパネルを足すときに、この判断は再検討が要る**。
いま SSD1327（4bpp）を足そうとすると、パネル側で 565 から 4bpp に落とす
ことになり、階調の情報がすでに失われている。

### 3. バッファリング

| | |
| --- | --- |
| **U8g2** | ページバッファ + `firstPage` / `nextPage` の「絵のループ」 |
| **GxEPD2** | 同じ形。**「U8G2 と同じくページ描画」と明記**。テンプレート引数でページ数を選ぶ |
| **Adafruit_GFX** | `GFXcanvas1/8/16`。オフスクリーンのキャンバス |
| **LovyanGFX / TFT_eSPI** | `Sprite` / `LGFX_Sprite`。色深度も選べる |
| **TinyGFX** | `TileCanvas`（帯）+ `PanelMemory`（オフスクリーン） |

**帯描画は U8g2 / GxEPD2 と同じ考え方**で、TinyGFX では
「帯で描いても全面バッファと 1 画素も違わない」ことをテストで固定している
（`tests/tile/` と `tests/i2c/`）。

**スプライト相当は `TinyGFXPanelMemory` で既にできる** — RAM バッファを
パネルとして `TinyGFX` を構築し、描いて、`pushImage()` で画面に戻す。
`pushSprite` という名前の API が無いだけ。**これは文書化の不足であって
機能の不足ではない。**

### 4. 文字 — 「2 系統ある」問題

**LovyanGFX も Adafruit_GFX も、同じことをする関数群を 2 つ持っている。**

| | 系統 A | 系統 B |
| --- | --- | --- |
| **LovyanGFX** | `setCursor` + `print` / `println`（流し込み） | `drawString(s, x, y)`（位置指定） |
| | `drawCenterString(s, cx, y)` | `setTextDatum(TC)` + `drawString` ← **同じことが 2 通り** |
| **Adafruit_GFX** | `drawPixel` / `drawLine` …（自分でトランザクションを開く） | `writePixel` / `writeLine` …（呼び手が `startWrite` 済みの前提） |

TinyGFX はどちらの重複も持たない。

- **揃え**: `drawCenterString` / `drawRightString` だけ。`setTextDatum` は
  入れない。**datum は `drawString` が毎回参照する状態**になり、揃えを
  一度も使わない人まで `textWidth` を引き込む。CH32V003 で実測 **+204 B**
  対 **+0 B**（[API.ja.md](API.ja.md)）
- **draw / write の二重系**: `startWrite()` / `endWrite()` は**入れ子を数える**
  ので、外側で 1 回開けば内側の描画がそのまま入れ子になる。関数を 2 系統
  用意する必要がない

### 5. Print との関係

**`Adafruit_GFX : public Print`** — 継承しているので、基底クラスが常に
`Print` のインターフェースを持つ。

TinyGFX は `TinyGFX/Print.h` に分けてある。**include しなければ 1 バイトも
載らない。** これは飾りではなく、`print(float)` が基準機で
**FLASH を 2,724 バイト溢れさせる**（実測）ため、基底に置けない。

### 6. 読み出し

**Arduino_GFX は「読み出しをしない」ことを設計判断として明記している**
（フットプリントと速度のため。すべてのパネルが読めるわけでもない）。

TinyGFX は読める — ただし `TinyGFXPanelDcs::readPixels()` として、
**呼ばなければ生成されない**インラインメンバに置いてある。全体で払うのは
バスの `readSequence` の 8 バイトだけ。**1 画素 150us** なのでデバッグと
検証の道具であって描画経路ではない。

実際これは効いていて、実機のゴールデン比較（`tests/hw/m5stack/`）と
回転の写像の検証（M2 の自動化）は読み出しでしか成立しない。

## U8g2 — 唯一、実測で殴り合った相手

他は API とソースを読んだだけだが、**U8g2 とは同じ絵を描くスケッチを両方
書いて実測した。** モノクロで最も使われていて、TinyGFX と狙いがいちばん
近いため。

### 同じ絵、同じボード（Arduino Uno、SSD1306 128x64 I2C）

枠・塗り・円・線・三角・`"1234"` を描く。2026-08-29 実測。

| | flash | RAM |
| --- | ---: | ---: |
| **TinyGFX（全面バッファ）** | **8,036** | 1,406 |
| **TinyGFX（帯 1 ページ）** | **8,040** | **510** |
| U8g2（`_F_` 全面） | 11,020 | 1,626 |
| U8g2（`_1_` ページ） | 11,018 | 730 |
| （参考）TinyGFX 描画なし | 5,308 | 1,380 |
| （参考）U8g2 描画なし | 8,064 | 1,556 |

- **合計で 2,984 B 小さい**
- **起動時点で 2,756 B 小さい。** U8g2 は u8x8 層とコントローラ記述を
  引きずる
- **帯の RAM が 220 B 少ない**（510 対 730）
- **帯にしても flash がほとんど増えない**（+4）。U8g2 のページ方式は
  構造として組み込まれているので同等

### 構造の違い

U8g2 の核は**プリミティブが 1 本だけ**であること。

```c
u8g2_DrawHVLine(u8g2, x, y, len, dir)   // 水平か垂直のラン
```

箱も円もビットマップも文字も、全部これに集まる。クリップはそこで 1 回。
その先は関数ポインタで 3 段に分かれる。

| 層 | 実装 | サイズ |
| --- | --- | ---: |
| クリップ | `u8g2_DrawHVLine` 1 本 | 342 |
| 回転 | `draw_l90_r0` 〜 `r3` + `mirrorr_r0` | 32（r0） |
| **バッファ配置** | `ll_hvline_vertical_top_lsb` / `..._horizontal_right_lsb` | 218 |

**低レベルの書き込みは 2 つだけで、名前が「色深度」ではなく
「バッファの並び」を指している。** 「モノクロ用」という層は存在しない
（[OPTIMIZE.ja.md](OPTIMIZE.ja.md) H）。

C の関数ポインタなので仮想関数は 0。**`u8x8` という文字専用の軽い層**を
別に持っていて、図形が要らない用途はそちらだけ使える。

### フォント形式 — RLE

U8g2 のフォントは**形式そのものがランレングス**（`bits_per_0` /
`bits_per_1`）で、デコーダはラン長を読んで `DrawHVLine` を呼ぶだけ。
CellFont は生のビットマップなので、こちらのデコーダはビットを走査して
ランを見つける。

**ここで「形式を RLE に変えれば縮む」と考えたが、測ったら違った。**
同じ実装の中で形式だけ差し替えた比較（AVR、コードサイズ）:

| | CellFont（生ビットマップ） | u8g2 形式（RLE） |
| --- | ---: | ---: |
| 合計 | **1,218** | **1,170** |

**差は 48 B。** ビットスキャンが消えて `draw` は 254 B 減るが、ビット
読み出しと索引に 370 B 取られて相殺する。**CellFont 仕様 §13.2 の
「圧縮しない」判断はこちらの実測でも支持された。**

### どちらが勝っているか

| | |
| --- | --- |
| **U8g2 が勝つ** | **フォントデコーダの実装。** 同機能で約 310 B 対こちらの約 1,000 B。形式で説明できるのは 48 B だけで、残りは詰め方の差 |
| | パネルとコントローラの網羅。1bpp 系はほぼ全部ある |
| | `u8x8` という軽い別層を持っている |
| **TinyGFX が勝つ** | 合計 2,984 B、起動時点 2,756 B、帯の RAM 220 B |
| | ヘッダオンリー。**使わない API は 1 バイトも載らない** |
| | カラーも同じ API で扱える（U8g2 はモノクロ専用） |

### U8g2 から取り入れたもの

**`fillRect` をシームにする設計は、U8g2 の構造を読んで決めた。**
「バッファ持ちのパネルはランを、直接 GRAM のパネルは矩形を欲しがる」
という第 1 軸の整理も同様（[OPTIMIZE.ja.md](OPTIMIZE.ja.md) H）。

実測すると、シーム化でモノクロが CH32V003 で 76〜92 B 縮んだ。

## 取り入れる価値があるもの（実測済み）

調査の結果、**足す価値がありそうなのは 1 つだけ**だった。

| | CH32V003 での実費 | 誰が持っているか |
| --- | ---: | --- |
| **1bpp ビットマップの描画** | **+120 B** | Adafruit（`drawBitmap` / `drawXBitmap`）、U8g2、LovyanGFX |
| `drawNumber` | +168 B | LovyanGFX、TFT_eSPI |
| `setTextWrap`（自動折り返し） | 未測定 | Adafruit |
| `drawEllipse` / `fillEllipse` | 未測定 | Adafruit、LovyanGFX |
| `drawArc` | 未測定 | LovyanGFX、TFT_eSPI |

**1bpp ビットマップが最も筋がいい。** アイコンの自然な形式で、モノクロ
パネルでは `pushImage`（16bpp）より素直。他の 3 つはどれも持っているので、
互換性の観点でも足す理由がある。

**まだ足していない。** 要ると分かってから足す。

## 取り入れないもの

| | 理由 |
| --- | --- |
| 色深度の実行時切り替え | コアに 2 つ持つ構造が戻る（D4）。ただし灰階調パネルを足すときは再検討 |
| `setTextDatum` | 使わない人が +204 B 払う（実測） |
| `Print` の継承 | `print(float)` が基準機で 2,724 B 溢れる（実測） |
| draw / write の二重系 | `startWrite()` が入れ子を数えるので要らない |
| 画像デコーダ（JPG / PNG / BMP / QOI） | デコーダだけで基準機の FLASH を使い切る |
| アンチエイリアス（TFT_eSPI / LovyanGFX） | 中間色が要る。1bpp では成立せず、色深度の抽象が要る |
| タッチ（LovyanGFX は 11 種） | 責務の外（[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §5） |

## この調査で見つかった自分の穴

1. **オフスクリーン描画が文書化されていない。** `PanelMemory` + `pushImage`
   でスプライト相当ができるのに、README にも API にも書いていない。
   **API を足す前に、あることを書く**
2. **1bpp ビットマップが無い。** 上記のとおり +120 B。優先度は高い
3. **`setTextWrap` が無い。** `TinyGFXPrint` は `\n` は見るが右端では
   折り返さない。Adafruit にはある。未測定
4. **色深度の判断は「いまは正しい」であって「永久に正しい」ではない。**
   SSD1327（4bpp）や灰階調の e-paper を足すときに、パネル側で 565 から
   落とす形が破綻する。**そのときが D4 を見直す時期**
