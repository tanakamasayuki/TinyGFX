# 要件

内部の記録。日本語のみ。**何を作るライブラリで、どこまでを責務にするか。**

たたき台。確定していない項目には「**暫定**」と書く。

## 1. 一言でいうと

> **LovyanGFX に似た書き味の描画 API を、フラッシュと RAM が極端に少ない MCU でも載るところまで削ったライブラリ。**

速度は主目的ではない。**同じスケッチが CH32V003 でも ESP32 でもビルドでき、フラッシュ増分が読めること**を最優先にする。

## 2. 背景

- CH32V 系のように Arduino Core はあるが、高機能 GFX ライブラリの最適化対象になっていない MCU でも同じ描画コードを使いたい。
- 既存の高機能 GFX は MCU 固有レジスタ・DMA・バス最適化への依存が大きく、未対応 MCU への移植コストが高い。
- 単純な SPI LCD 用途では、巨大な抽象化やフレームバッファは要らないことが多い。
- CH32V003 はフラッシュ 16KB / SRAM 2KB。**ここに載るかどうかがライブラリの成否**であり、既存ライブラリはここを狙っていない。

## 3. 設計原則

| 原則 | 内容 |
| --- | --- |
| **フットプリント最優先** | 迷ったら小さいほうを選ぶ。速度・機能・設計の美しさより先にサイズ。 |
| **使わない機能は 0 バイト** | 呼ばない API がフラッシュに載らない構造にする。リンカの `--gc-sections` が落とせる形を保てばよい（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7）。 |
| **依存をまわりまわらせない** | 軽い機能から重い機能へ**辿れる参照を作らない**。`fillScreen` しか使っていないのに文字や `Print` が載る、を構造で防ぐ（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7.4）。 |
| **高い機能は禁止せず、値札をつけて分ける** | float や `print` のようにフラッシュを大きく食う機能も**提供する**。ただし**既定構成には入れず**、**増分を実測して文書に書く**（§4）。 |
| **動的確保をしない** | `malloc` / `new` / `String` / 標準コンテナを使わない。 |
| **フレームバッファ前提にしない** | 画面へ直接ストリーム描画する。全画面バッファを要求しない。 |
| **Arduino 標準 API だけで成立** | 既定実装は `pinMode` / `digitalWrite` / `SPI` / `delay` のみ。 |
| **速度は二番手** | 多少遅くてよい。速さが要る環境だけ Fast Backend を差す。 |
| **名前は LovyanGFX に寄せる** | 決めの問題でしかない箇所は、既存ユーザーが迷わない名前にする。仕方ない差は互換を捨てる。 |
| **Panel と Bus を分ける** | MCU × LCD の組み合わせ爆発を避け、同時にテストの差し込み口にする。 |

## 4. コストの高い機能の扱い（この設計でいちばん重い判断）

CH32V003 のフラッシュは 16KB。実測として、**`Serial.print()` に float を 1 回渡すだけでフラッシュの約半分が持っていかれる**。浮動小数点の書式化ルーチンとソフトウェア浮動小数点演算がまとめてリンクされるため。

**だからといって float を禁止はしない。** 便利な機能は用意する。守るのは次のルール。

### 4.1 三つのルール

1. **既定構成に入れない。** コアを `#include` しただけでは、浮動小数点も `Print` もリンクされない。使う人が**明示的に別ヘッダを取り込んだときだけ**載る。
2. **値札を測って書く。** 「この機能は CH32V003 でフラッシュ +N バイト」を実測し、[FOOTPRINT.ja.md](FOOTPRINT.ja.md) と利用者向け GUIDE の両方に書く。**測っていない機能は追加しない。**
3. **代替の軽い道を必ず用意する。** float 版を出すなら整数版も出す。`print(3.14f)` があるなら `drawString` で書ける道も残す。

### 4.2 どこに何を置くか

| 層 | 方針 |
| --- | --- |
| **コア**（`TinyGFX.h` と描画プリミティブ） | 整数演算のみ。シグネチャにも内部計算にも浮動小数点を出さない。円・線は Bresenham 系 |
| **拡張ヘッダ**（`TinyGFX/Print.h` など） | `Print` 継承、`printf`、float 引数のオーバーロード。**取り込んだ人だけが払う** |
| Fast Backend | MCU 固有。コストは実装ごとに記録 |

分離の手段は**マクロではなくヘッダとクラス**にする。`#include` していない翻訳単位のコードはそもそもリンクされないので、これがいちばん確実で、条件コンパイルの組み合わせ爆発も起きない。

### 4.3 守り方

**既定構成のビルドで、リンクマップに浮動小数点シンボルと `malloc` が出ないことをテストで守る**（[TEST_PLAN.ja.md](TEST_PLAN.ja.md) Tier 2 `linkprune`）。拡張ヘッダを取り込んだ構成では出て当然なので、そちらは対象にしない。

### 4.4 要確認（Phase 0）

CH32V003 のコアは乗除算命令を持たない構成と思われる。もしそうなら `/` や `%` はソフトウェアルーチン呼び出しになるので、**コアの描画アルゴリズムから除算を排除する**必要がある。ビルドマップに除算ルーチンが出るかを最初のスパイクで確認する。

## 5. 責務境界

TinyGFX が持つのは **「座標 → パネルへのバイト列」** まで。

| 担当する | 担当しない |
| --- | --- |
| 座標計算、クリップ、回転 | タッチ入力、ボタン、UI ウィジェット |
| プリミティブ描画（点・線・矩形・円） | JPEG / PNG / BMP のデコード |
| 固定幅ビットマップ文字の描画 | 日本語フォント資産の管理、プロポーショナル整形 |
| RGB565 の画像転送 | SD カード・ファイルシステム |
| パネル初期化とウィンドウ設定 | 画面遷移・レイアウト管理 |
| Bus 抽象と Arduino SPI 実装 | DMA スケジューリング（Fast Backend の内側に閉じる） |

## 6. 対象環境

| 区分 | MCU | Flash / RAM | 位置づけ |
| --- | --- | --- | --- |
| **基準機** | **CH32V003** | **16KB / 2KB** | **ここに載らない設計は却下する。フットプリント判断の基準。** |
| 将来の基準機 | CH32V003（新コア） | 16KB / 2KB | `ch32-riscv-ug/ArduinoCore-CH32`。**base が 624 B と圧倒的に軽く、ハードウェア SPI も動く。** リリースされたら基準機を移す（[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E7） |
| 主ターゲット | CH32V20x | 64KB〜/ 20KB〜 | 実用ライン |
| 移植性の参照機 | ESP32 | 潤沢 | Arduino SPI が安定。ホスト以外の動作確認先 |
| 移植性の参照機 | RP2040 | 潤沢 | 同上（暫定・優先度低） |
| 対応 | **Arduino Uno R3 (AVR)** | 32KB / 2KB | **実測で全構成が載る。** フラッシュは余裕、効くのは RAM。フォントは PROGMEM 必須（[DECISIONS.ja.md](DECISIONS.ja.md) D19） |

### 6.1 言語は C++11

| コア | 標準 |
| --- | --- |
| **arduino:avr** | **`-std=gnu++11`** ← **これが下限を決めている** |
| esp32 ほか | `gnu++14` / `gnu++17` |

**C++11 より新しい機能は使わない。** AVR を対応環境に入れている限りここは
動かせない（Arduino AVR コアは長年 `gnu++11` のまま）。

実測（2026-08-28 時点、`src/` 全体）: `nullptr` 43 / `override` 53 /
`constexpr` 3 / `= default` 2。**C++14 以降の機能は 0 件、`std::` も 0 件。**

設計に効くところ:

- **変数テンプレートが無い**（C++14）。テンプレート型ごとに定数オブジェクトを
  用意する書き方は、クラステンプレートの static メンバ経由になり汚くなる
  （[OPTIMIZE.ja.md](OPTIMIZE.ja.md) I のフォント ops がこれに当たった）
- `if constexpr` が無い。コンパイル時分岐は特殊化か SFINAE
- **`using X = Y;` のエイリアスは使える**（エイリアステンプレートも C++11）
- 例外・RTTI は無効（`-fno-exceptions`）。AVR は `-fno-threadsafe-statics`。
  関数内 static は `__cxa_guard_acquire` を呼ぶので避ける（R9）

C ではない。ヘッダオンリーの C++ ライブラリ。

## 7. 対象パネル

| 状況 | コントローラ | 接続 | 想定解像度 | 備考 |
| --- | --- | --- | --- | --- |
| **実機確認済み** | **ILI9342C** | SPI | 320x240 | M5Stack Core / BASIC の内蔵。**標準の検証機**（D22）。回転も読み戻しで自動検証（M2） |
| **実装済み** | **ST7789** | SPI | 240x240 / 240x320 / 135x240 | パネルごとの原点オフセットの扱いを含む。**実機未確認**（M1） |
| **実装済み** | **ST7735** | SPI | 128x160 / 128x128 / 80x160 | 同じ IC が 4 種類のガラスに載っていて、**オフセットが 3 通り・色順が 2 通り**。`panels/` が 5 枚ある。初期化列は送らず、データシートの電源投入時の値のまま（D34） |
| **実装済み** | **ST7796** | SPI | 320x480 | ST7789 の兄弟。電源投入時の値で立ち上がる |
| **実装済み** | **ILI9341** | SPI | 240x320 | ILI9342C と同じ `DriverDcs` の上。違うのは GRAM が縦長・反転既定 off・X ミラーの 3 点だけ。**実機未確認**（M5） |
| **実装済み** | **SSD1306** | I2C / SPI | 128x64 / 128x32 | モノクロ 1bpp。フレームバッファは利用者が用意する（D21） |
| **実装済み** | **SH1106** | I2C / SPI | 128x64 | SSD1306 と同じ `DriverPaged` の上。132 カラム RAM のオフセットとページ単位の転送だけが違う。**配線はホストで検証済み**（`tests/sh1106/`）、**実機未確認**（M6） |

**パネルは 2 つの基底の上に乗る**（[OPTIMIZE.ja.md](OPTIMIZE.ja.md) H の第 1 軸）。

| 基底 | 何を持つか | 乗るもの |
| --- | --- | --- |
| `DriverDcs` | DCS プロトコル。MADCTL、原点オフセット、色順、ミラー、読み戻し | ST7789 / ILI9341 / ILI9342C |
| `DriverPaged` | ページプロトコル。1bpp バッファ、帯、dirty 追跡、回転、バイト単位の塗り | SSD1306 / SH1106 |

`DriverDcs` の上にコントローラを 1 つ足す代金は **+0 バイト**（実測、CH32V003）。
`init()` と `display()` だけが各コントローラの持ち物。

カラーパネルは **RGB565・16bit カラー**のみ対象。パラレル接続、8bit/18bit カラー、
e-Paper は対象外。モノクロは SSD1306 系（ページ単位のフレームバッファ）だけを見る。

## 8. フットプリント予算

**総量ではなく「空スケッチ（base）からの増分」で管理する。** CH32V003 は base だけで
5,892 B（フラッシュの 36%）あり、総量の予算は意味のある数字にならない
（[EXTERNAL_REQUESTS.ja.md](EXTERNAL_REQUESTS.ja.md) E2-b）。

実測値と予算は [FOOTPRINT.ja.md](FOOTPRINT.ja.md) §5 にある。2026-08-27 時点の要点:

| 構成 | Δ Flash | 判定 |
| --- | --- | --- |
| 全プリミティブ + 文字 + 画像（構成 E） | **+6,484 B** | 載る（残り 10,492 B の 62%） |
| + 帯レンダリング（構成 T） | +7,548 B | 載る |
| + `println(float)` | 約 +8,652 B | **載らない**（4,280 B 溢れる） |

TinyGFX オブジェクト自体の RAM は 3 オブジェクト合計で **+68 B**（実測）。

## 9. 利用モデル

想定する典型スケッチ。

1. パネルとピンを宣言する
2. `begin()`
3. `setRotation()`
4. `fillScreen()` して、矩形と文字を置く
5. `loop()` で変わったところだけ描き直す

**全画面の再描画を毎フレーム行う使い方は想定しない。** フレームバッファがないので、それをやると転送時間がそのまま見える。

## 10. 非目標

- **LovyanGFX 完全互換を目指さない。** 名前は寄せるが、互換レイヤは作らない。移植の互換表も用意しない。
- **全 MCU での最高速を保証しない。** 標準 Backend は「正しく動く」、Fast Backend は「必要な環境で速くする」。
- **スプライト / オフスクリーン / レイヤ合成をコアに入れない。** RAM がない機種で成立しないため。将来やるなら別ヘッダ・別クラスとして分離する。
- **JPEG / PNG デコード、ベクタフォント、アンチエイリアスを入れない。**
- **色深度の抽象化をしない。** RGB565 固定（[DECISIONS.ja.md](DECISIONS.ja.md) D4）。
- **実行時のパネル差し替えをサポートしない。** ビルド時に決まっていればよい。

## 11. 最小リリース（v0.1）の合格条件

1. CH32V003 + ST7789 240x240 の実機で、`fillScreen` / `fillRect` / `drawPixel` が正しく出る
2. 同じスケッチが ESP32 でもピン定義の変更だけでビルド・動作する
3. 構成 B のフラッシュが予算内（§8）
4. **既定構成の**リンクマップに浮動小数点シンボルと `malloc` が出ない
5. ホストのテストで、出力コマンド列から復元した画像が期待どおり

## 12. 用語

| 用語 | 意味 |
| --- | --- |
| **Bus** | MCU 側の転送手段。SPI の叩き方と DC / CS の制御を持つ。 |
| **Panel** | LCD コントローラ。初期化列、MADCTL（回転）、原点オフセット、ウィンドウ設定を持つ。 |
| **Fast Backend** | 特定 MCU 向けにレジスタ直叩き・DMA で書いた Bus 実装。任意。 |
| **構成 A〜E** | §8 のフットプリント積み上げ単位。 |
| **基準機** | CH32V003。フットプリント判断はここの数字で行う。 |
