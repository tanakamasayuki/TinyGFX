# 用語集

> English: [GLOSSARY.md](GLOSSARY.md)

TinyGFX が使う語を 1 か所に定める。**読み手が最初に引く文書**なので、
API.ja.md と同じく日英を用意する。

**語彙とコードは一致している**（2026-08-30 に改名を完了）。

## 1. 利用者が選ぶもの

利用者が名前を書くのは **2 つだけ**。バスとパネル。

### バス（Bus）

**バイトをどうやってパネルまで運ぶか。**

**2 種類ある。分かれ目は「何を渡すか」であって、ハードかソフトかではない。**

| 種別 | 渡すもの | 実装は誰のものか | 初期化するのは | クラス |
| --- | --- | --- | --- | --- |
| **ペリフェラルバス** | Arduino のペリフェラル（`SPIClass&` / `TwoWire&`） | **コア** | **利用者** | `TinyGFXBusSPI` / `TinyGFXBusI2C` |
| **ピンバス** | ピン番号 | **TinyGFX**（`pinMode` / `digitalWrite` で叩く） | **TinyGFX** | `TinyGFXBusSoftSPI` / `TinyGFXBusSoftI2C` |

#### ペリフェラルバス

**利用者のもの。** `SPI.begin()` も `Wire.begin()` も利用者が呼び、初期化済みの
インスタンスを渡す。TinyGFX はそれを初期化しない
（[DECISIONS.ja.md](DECISIONS.ja.md) D24）。同じ線に SD カードがぶら下がって
いても、同じ `SPI` を渡すだけで共存する。

**TinyGFX が握るピンは DC と CS だけ。** どちらもそのパネル専用のピンである。

#### ピンバス

**TinyGFX のもの。** 渡されたピンを `pinMode` で出力にして自分で叩く。
ソフト SPI なら SCK・MOSI・DC・CS の 4 本すべてを握る。**そのピンは他の用途に
使えない。**

存在理由は大きさではなく**ピン**である。ハードウェアのペリフェラルは決まった
ピンにしか出ないので、CH32V003 のようにピンの少ない部品では、そこを別の用途に
回したいことがある。

#### 「ソフト」が意味すること

**`TinyGFXBusSoftSPI` の「ソフト」は「TinyGFX 自身がビットバンする」という
意味であって、「ソフトウェア実装はこちらだけ」という意味ではない。**

`TinyGFXBusSPI` が受け取るのは「そのコアが `SPI` と呼んでいるもの」であって、
**それがハードウェアのペリフェラルかどうかを TinyGFX は知らないし、知る必要も
ない。** コアによってはソフトウェア実装の `SPI` を提供している。利用者が
`SPIClass` を継承した独自のソフト SPI を渡すこともできる。どちらでも
ペリフェラルバスとして同じように扱われる。

**「ハードウェア／ソフトウェア」で分類しないのはこのためである。** 分類の軸は
所有者 —— 渡したものは利用者が面倒を見る、渡さなかったものは TinyGFX が握る。

### パネル（Panel）

**買った製品そのもの。** 「0.96 インチ 128x64 の I2C OLED」に相当するもの。

`TinyGFXDriverSSD1306_128x64` のように、**コントローラ名と寸法で名前が付く。**
カタログから 1 枚選んで include する。

```cpp
#include <TinyGFX/panels/SSD1306_128x64.h>
```

パネルはプリセット（§3）であって、ドライバ（§2）ではない。**同じドライバでも
ガラスが違えば別のパネル**であり、多重比・列オフセット・COM 配線が変わる。

**1 つのドライバにつき 1 スケッチ 1 パネル。** 同じドライバで違うパネルを 2 枚
include するとコンパイルが止まる（§3）。違うドライバどうし（TFT + OLED）は通る。

## 2. 内部の層

利用者は名前を書かない。**ドキュメントで層を指すために名前が要る**ので定める。

### ターゲット（Target）

**描画コアが画素を渡す先の抽象。** 窓（矩形）と画素を受け取るもの。

`TinyGFXTarget`。`TinyGFX lcd(x)` の `x` はこれ。

パネルもターゲットだが、**RAM バッファもターゲット**である。だから
「コントローラ IC」を意味する語は使えない。帯レンダリング（`TinyGFXTileCanvas`）
は RAM のターゲットをパネルの手前に挟む仕組みで、これが成立するのは
ターゲットが抽象だからである。

### プロトコル（Protocol）

**コマンド体系。** どういうバイト列でパネルに絵を渡すか。**2 つしかない。**

| プロトコル | 中身 | 使うドライバ |
| --- | --- | --- |
| **DCS プロトコル** | 窓 + 画素。MIPI DCS の `0x2A` CASET / `0x2B` RASET / `0x2C` RAMWR。色は RGB565 | ST7789 / ST7735 / ST7796 / ILI9341 / ILI9342 |
| **ページプロトコル** | ページ + ビット。1 バイトが縦 8 画素。フレームバッファを持ち、`display()` で送る | SSD1306 / SH1106 |

**新しいコントローラを足しても、たいていプロトコルは増えない。** ST7796 も
GC9A01 も DCS プロトコルなので、増えるのはパネルのカタログだけで、
ライブラリのコードは 1 行も増えない。

**クラス名には出さない。** 呼び方としてだけ使う。実体は
`TinyGFXDriverDcs` / `TinyGFXDriverPaged` という、そのプロトコルを実装した
ドライバの共通部分である。

### ドライバ（Driver）

**コントローラ IC。** SSD1306、ST7789、SH1106。

`TinyGFXDriverSSD1306`。プロトコルの共通部分に、その IC 固有の癖を足したもの。

「ドライバ」はデータシートの自称でもある。

- SSD1306: 「Segment/Common **Driver** with Controller」
- ST7789: 「Single-Chip **Controller/Driver** for 262K-Color TFT-LCD」

**同じプロトコルでも、転送のしかたが違えば別のドライバ。** SSD1306 と SH1106 は
どちらもページプロトコルだが、SSD1306 は範囲指定（`0x21`/`0x22`）で一括に流し、
SH1106 にはその命令が無いのでページごとにカーソルを置く。**この差はデータで
なくコードなので、ドライバとして分ける。**

### 層の並び

```
スケッチ
  ↓  選ぶ
バス ──────────── どうやって運ぶか
  ↓
パネル ────────── 何を買ったか            ← プリセット（データ）
  ↓  中身は
ドライバ ──────── どの IC か              ← ライブラリ（コード）
  ↓  実装する
プロトコル ────── どういうコマンド体系か   ← ライブラリ（コード）
  ↓  満たす
ターゲット ────── 窓と画素を受け取るもの   ← 抽象
  ↑
描画コア（TinyGFX）
```

## 3. 設定

### プリセット（Preset）

**パネルヘッダが持っている値の組。** カタログはライブラリに同梱する。

**フォントとは方針が逆である。** フォントはデータを 1 バイトも同梱しない
（[DECISIONS.ja.md](DECISIONS.ja.md) D17）が、パネルのプリセットは同梱する。
理由は 2 つとも当てはまらないから。

| | フォント | パネルのプリセット |
| --- | --- | --- |
| 大きさ | 数百〜数千バイト | **約 30 バイト** |
| 何で決まるか | そのプロジェクトで使う文字 | **買った製品**（有限のカタログ） |
| 同梱しないとどうなるか | 使う文字を選ぶ手間が増える | **最初の 1 枚が出ない** |

**プリセットは導出できる値を持たない。** §4 のとおり、ほとんどはガラスの
寸法から出るか、コントローラのリセット値そのものである。

### 二重 include の禁止

同じドライバのパネルを 2 枚 include すると **`#error` で止まる。**

止めないと `#pragma once` で 2 枚目が黙って無視され、**1 枚目の値で 2 枚目を
描く。** 絵は出るのでずれに気づけない。**黙って間違うより、コンパイルを
止めるほうがよい。**

ガードは**ドライバ単位**。TFT と OLED のように違うドライバを 2 枚使う構成は通る。

## 4. パネルの設定項目

**多くは導出できるか、コントローラのリセット値である。**
プリセットが実際に持つ必要があるのは ★ の 2 つだけ。

### ページプロトコル（SSD1306 / SH1106）

| 項目 | コマンド | どこから来るか |
| --- | --- | --- |
| 多重比 | `0xA8` | **導出: 高さ − 1**（既知の 9 品種すべてで一致） |
| 列オフセット | — | **導出: ガラスは RAM の中央**（`(RAM 幅 − 幅) / 2`）。★ 中央でない品種は上書き |
| **COM ピン配置** | `0xDA` | ★ **2 択。** データシートのリセット値は `0x12`（Alternative）、もう一方が `0x02`（Sequential）。**ガラスの COM 配線という物理的事実** |
| プリチャージ | `0xD9` | データシートのリセット値 `0x22`（Phase1=2, Phase2=2） |
| VCOMH | `0xDB` | データシートのリセット値 `0x20`（0.77×Vcc） |
| クロック分周 | `0xD5` | データシートのリセット値 |

### DCS プロトコル（ST7789 / ILI934x …）

| 項目 | コマンド | どこから来るか |
| --- | --- | --- |
| GRAM 原点オフセット | `0x2A` / `0x2B` に加算 | モジュール固有 |
| GRAM 寸法 | — | コントローラ固有（240x320 など） |
| 色順 RGB / BGR | `0x36` bit3 | ガラスの配線 |
| 反転 | `0x21` / `0x20` | パネルの性格（IPS は反転が多い） |
| ミラー X / Y | `0x36` bit6/7 | モジュールの実装向き |
| ダミーリード bit 数 | `0x2E` の前 | コントローラ固有 |

## 5. ハードウェアの語

| 語 | 意味 |
| --- | --- |
| **GRAM** | コントローラが持つ画像メモリ。**ガラスより大きいことがある**（135x240 のガラスに 240x320 の GRAM など）。だから原点オフセットが要る |
| **多重比（multiplex ratio）** | 何本の COM 線を走査するか。実質「高さ」 |
| **COM ピン配置** | ガラスの COM 線の並び方。Sequential（順番）と Alternative（交互）がある。間違えると 1 行おきの縞になる |
| **セグメント反転（segment remap）** | 左右の向き。`0xA0` / `0xA1` |
| **COM 走査方向** | 上下の向き。`0xC0` / `0xC8` |
| **MADCTL** | DCS の `0x36`。回転・ミラー・色順を 1 バイトで表す |
| **タブ（tab）** | **ST7735 だけの習慣。** モジュールに貼ってある保護フィルムの引き手の色（緑・赤・黒）で品種を呼ぶ。他のパネルには存在しない概念なので、TinyGFX では使わない |

## 6. その他

| 語 | 意味 |
| --- | --- |
| **描画コア** | `TinyGFX` クラス。仮想関数を 1 つも持たない（[DECISIONS.ja.md](DECISIONS.ja.md) D1） |
| **帯レンダリング** | `TinyGFXTileCanvas`。画面を横帯に分け、小さな RAM バッファに 1 帯ずつ描いて転送する。ちらつき対策 |
| **値札** | ある機能を使うと増えるフラッシュのバイト数。**基準機 CH32V003 での実測**（[FOOTPRINT.ja.md](FOOTPRINT.ja.md)） |
| **基準機** | CH32V003（Flash 16KB / SRAM 2KB）。最適化がぶつかったときはここが勝つ |
